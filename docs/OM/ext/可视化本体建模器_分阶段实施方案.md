# 可视化本体建模器 — 分阶段实施方案

> 目标：把当前"改 JSON 文本框"的本体维护方式，渐进替换为可视化建模界面，
> 并让「全域 / 行业 / 案件」三层结构真正落地。
>
> 版本：v1.0　|　基线：`ontology_v4 @ 25371e68`（`_v4_new/investigation-ontology_v4`）
> 替换策略：**渐进式**（新界面与 JSON 页并存，逐文件切换，可回退）

## 〇、核查基线（本方案所有判断的事实依据）

### 0.1 现有"编辑页面"本质是 JSON 编辑器 🔴

| 页面 | 行数 | 实际交互 |
|---|---|---|
| `ModelDesignerView.vue` | 280 | objects / links / views **三个 textarea** |
| `PolicyMaskingView.vue` | 373 | policies.json **textarea** |
| `RuleWorkshopView.vue` | 345 | 规则列表 + 单条规则 **JSON textarea** |
| `EtlPipelineView.vue` | 255 | 整份 bindings **textarea** |
| `DataElementsView.vue` | 208 | 字典表格 + **JSON 文本框** |
| `PackageView.vue` | 445 | 导入导出（非建模） |
| `KnowledgeView.vue` | 244 | 知识包编辑 |

**结论**：用户改一个属性，要在几百行 JSON 里肉眼定位，还要记住 `pk` / `name_property` / `data_element` / `jian_source` 这些字段名与关系。**这不是建模，是手敲配置。**

### 0.2 schema 资产：9 个已有，10 个缺失

```
✅ 有 schema：actions · bindings · functions · links · objects
              policies · proposal · rules · views
❌ 无 schema：case_knowledge · data_elements · derived_properties
              dimensions · enum_space · jians · llm_policy
              scoring · states · thresholds · verify_playbooks
```

**9 个 schema 是现成的表单元数据**——可驱动标签、控件、必填、枚举下拉。

### 0.3 🔴 但 schema 覆盖不全，纯驱动会漏字段

`objects.schema.json` 声明的对象字段：`name / title / pk / kind / name_property / properties / runtime`

实际 `objects.json` 出现但 **schema 未声明**：

| 字段 | 出现位置 | 后果 |
|---|---|---|
| `jian` | `org` 等对象 | 纯驱动表单**看不见** |
| `jian_source` | `org` 等对象 | 同上 |
| `metadata_props` | `org` 对象 | 同上 |

**所以"schema 驱动"不能直接当"完整表单"用**——必须补这三类字段的声明，或做成"已知字段表单 + 未知字段兜底展示"。这是阶段 1 的关键风险。

### 0.4 属性结构很扁（好消息）

```jsonc
// objects.schema.json 的 properties 定义
"oneOf": [
  {"enum": ["string","integer","decimal","date","boolean","timestamp","duration_days","enum","json"]},
  {"type":"object", "properties":{
      "type": {...}, "composite": {"type":"boolean"}, "data_element": {"type":"string"}}}
]
```

属性只有 **3 个可视化维度**（类型 / 是否复合 / 绑定数据元）。表单极简，成本远低于预估。

### 0.5 数据元绑定已在使用

`reqd_case/objects.json` 实测 **9 处**绑定：

```
person.phone → DE_PHONE      person.id_card → DE_IDCARD
transaction.amount → DE_AMOUNT   transaction.date → DE_DATE
call.phone_raw → DE_PHONE    call.date → DE_DATE
case_ledger.case_type → DE_CASE_TYPE   case_ledger.case_date → DE_DATE
```

数据元自带 `format` / `mask` / `clean_rule` / `checksum` / `sensitive`——**选中即继承，这正是可视化相对手填的最大收益点**。

### 0.6 🔴 行业层不存在

```
ontology/
├── _shared/      ✅ 已建（7 个全域数据元）
├── default/      ✅
├── reqd_case/    ✅
└── _industry/    ❌ 不存在
```

`pack_meta.json` 里有 `industry: 金融`，但**只是标签，无目录、无合并逻辑**。
**三层结构缺中间层**——行业数据元建了也没地方放。

### 0.7 写端点现状

| 可写 | 端点 |
|---|---|
| objects / links / views | `model_designer.py:128,167` + `views.py:53` |
| policies | `access_config.py:72` |
| data-elements / etl-pipeline | `etl.py:97,158` |
| rules（单条） | `rule_workshop.py:122` |
| **不可写** | actions / functions / states / jians / scoring / dimensions / derived_properties / enum_space / verify_playbooks / thresholds / llm_policy |

### 0.8 导航现状：本体散在 4 组

```
数据治理  → 数据元 · ETL管道 · 映射校验 · 质量检查 · 隔离区
研判模型  → 模型设计器 · 规则工坊 · 知识包 · 权限与遮蔽
高级工具  → 案件包
数据接入  → 接入建议
```

用户不知道这 8 个页面改的是同一个东西的不同切片。

## 四、S2 L1 对象建模器（5.2 人日）★ 核心

> 把 `objects.json` + `links.json` 从 textarea 变成真正的建模界面。

### S2-1 对象列表（0.5）

左栏：对象类型清单（`obj_person` / `obj_org` / `obj_transaction`…），显示 title / kind / 属性数 / 是否 runtime。
支持新增 / 复制 / 删除（删除需影响面提示）。

### S2-2 属性表格（1.5）★ 最高价值

中栏表格，每行一个属性：

| 列 | 控件 | 说明 |
|---|---|---|
| 名称 | 文本框 + `^[a-z_]+$` 校验 | |
| 类型 | **下拉**（9 种：string/integer/decimal/date/boolean/timestamp/duration_days/enum/json） | 手填 → 选择 |
| 数据元绑定 | **下拉**（从三层合并后的数据元列表选） | 选中即继承 format/mask/clean_rule |
| 复合列 | 勾选框 | |
| 操作 | 删除 | |

**降难度核心**：改一个属性从"在几百行 JSON 里定位 + 记住 `data_element` 这个 key"变成"表格里点一下下拉"。

### S2-3 对象元信息（0.5）

`title` / `pk`（下拉选已有属性）/ `kind`（entity·event 单选）/ `name_property`（下拉）。
**🔴 必须补 `jian` / `jian_source` / `metadata_props` 三个 schema 未覆盖字段**——否则可视化后这些字段会丢（见 §0.3）。

### S2-4 关系图（2.0 + 0.2）

右栏：对象间 link 的可视化连线（增删端点、方向、**基数**）。

> **决策（§11-1）**：同阶段加 cardinality（+0.2 人日）。`links.json` 目前只有端点，不加则关系图只能表达"有无关系"，表达不了一对多——而关系图是 S2 的核心卖点，省这 0.2 不划算。
> 冲突策略沿用 REQ-05 结论：**警告而非硬失败**（取证数据常脏，不该因声明不符拒绝装载）。

技术选型：复用 `frontend/src/domain/` 的确定性布局（画布已验证的 barycenter 思路），**不用力导向**——建模图同样要求"打开位置稳定"。

### S2-5 保存与校验（0.5）

复用 `_validate_in_temp`（先写临时目录 → 跑 `load_pack` → 通过才落盘）。
保存后按改动类型**分级提示重跑 BUILD**（新增对象类型/pk 变更 = 强提示；改 label = 轻提示）。

### S2 验收（可独立跑）

```
UC-S2-1  新增对象类型 obj_test（2 属性）→ 保存 → objects.json 结构正确
UC-S2-2  属性绑定 DE_IDCARD → 落盘为 {"data_element":"DE_IDCARD"}，非手填
UC-S2-3  修改含 jian 的对象 → jian/jian_source 不丢失    ★ 防 schema 漏字段
UC-S2-4  关系图增删 link → links.json 同步
UC-S2-5  新增对象类型后 → 出现"必须重跑 BUILD"强提示
```

## 九、渐进替换的切换规则（重要）

每个文件切换时遵守：

| 规则 | 说明 |
|---|---|
| **并存期双向一致** | 新界面与 JSON 页读写同一文件，切到哪边数据都不丢 |
| **逐文件切换** | 一次只切一个文件（先 objects，再 links…），不批量 |
| **JSON 页不立即删** | 保留至少一个版本周期，作为逃生舱（与 `EscapeHatchView` 定位一致） |
| **未知字段兜底** | 新界面遇到 schema 未覆盖字段（如 `jian`），**原样保留并在 UI 提示**，不静默丢弃 |
| **可回退** | 每个文件可单独回退到 JSON 编辑 |

**最后一条最关键**——§0.3 已经证明 schema 覆盖不全，**"未知字段原样保留"是渐进替换的安全底线**，否则会出现"用新界面保存一次，jian 字段就没了"的静默数据丢失。
