## 二、背景与问题定义

### 2.1 现状实测（写本 PRD 前核查的结论）

**本体被切成 4 块，散在 4 个导航组**（`nav/sections.ts` 按**业务阶段**分组，不是按对象分组）：

| 导航组 | 本体页面 |
|---|---|
| 数据治理 | 数据元 · ETL管道（bindings）· 映射校验 · 质量检查 · 隔离区 |
| 研判模型 | 模型设计器（objects/links）· 规则工坊 · 知识包 · **权限与遮蔽（policies）** |
| 高级工具 | 案件包 |
| 数据接入 | 接入建议 |

**8 个本体编辑页散在 4 组**，用户不知道它们改的是同一个东西的不同切片。这就是「找不到家」的具体证据。

### 2.2 用户痛点（原话转述）

> 「整体的组织层次应该是更加清晰的，非常同意你将它们集中在一起的这么一个理念。」

拆解为三个可设计的具体问题：

| # | 痛点 | 本 PRD 对应功能 |
|---|---|---|
| P1 | 不知道本体文件一共有多少个、哪些能改、哪些只读 | F1 本体总览树 |
| P2 | 改一个文件要在导航里翻四个组 | F2 统一入口 App |
| P3 | 改数据元时不知道自己动的是全域层还是案件层 | F3 来源标注 |

### 2.3 可用资产（决定实现方式）

| 资产 | 说明 |
|---|---|
| 9 个 JSON Schema | `actions / bindings / functions / links / objects / policies / proposal / rules / views` —— 可作文件清单与状态基础 |
| 8 个现有编辑页 | **不重写**，作为编辑器挂载进壳 |
| `EscapeHatchView` | 已有「逃生舱」定位先例，与 JSON 页保留策略一致 |

## 四、术语

| 术语 | 定义 |
|---|---|
| **本体文件** | 构成案件本体的 19 个 JSON 文件（`objects` / `links` / `policies` / `rules` / `data_elements` …） |
| **可写 / 只读** | 是否有后端写路由。当前 8 个可写，11 个只读 |
| **来源层** | 该文件（或其条目）归属 全域 / 行业 / 案件 哪一层 |
| **挂载** | 把现有编辑页作为 iframe 或路由组件嵌入壳的右侧区域，不改动其内部逻辑 |
| **独立 App** | 独立的顶层入口，不在主导航侧栏里占一个组 |

### 5.2 左栏：本体文件树（F1）

按**语义分组**，不按文件名平铺：

| 分组 | 文件 |
|---|---|
| 对象模型 | `objects` · `links` · `views` |
| 数据 | `data_elements` · `bindings` |
| 研判 | `rules` · `functions` · `verify_playbooks` · `dimensions` |
| 治理 | `policies` · `actions` · `states` · `llm_policy` |

- 点击左栏文件 → 右侧渲染**现有对应编辑页**

- 只读文件 → 右侧渲染只读视图 + 「暂无编辑界面」提示

### 5.4 顶部条（F3）

- 案件名 · **当前本体版本**（`A1B2C3D4…`）
- 版本沿革入口（S0-3 完成前置灰）

## 六、功能详情

### F1 本体总览 API（0.5 人日）

**F1.1 接口**

```
GET /cases/{case_id}/ontology/overview
```

**F1.2 返回字段（每项一个文件）**

| 字段 | 说明 | 来源 |
|---|---|---|
| `name` | 文件名（如 `objects`） | 目录扫描 |
| `group` | 语义分组 | 静态映射表（§5.2） |
| `writable` | 是否有写路由 | 静态映射表（0.7 节实测） |
| `has_schema` | `schemas/` 下是否有对应 schema | 目录扫描 |
| `source_layer` | `shared` / `industry` / `case` | 三层合并结果（**依赖 S0-1**） |
| `item_count` | 条目数 | 读文件 |
| `updated_at` | 最后修改 | 文件 mtime |

> `writable` 现阶段用静态映射表（已实测），不做运行时反射探测——避免为 1 个接口引入复杂度。

### F2 统一入口 App（0.5 人日）

**F2.1 入口位置**

- 顶部导航新增「本体管理器」入口（**不是侧栏第七组**，见 §7 R1）
- 从案件上下文进入，携带 `case_id`

**F2.2 挂载机制**

- 路由：`/ontology-manager/:caseId/:file`
- 右侧按 `file` 渲染现有组件
- 现有页面**不改动**，通过 props 接收 `caseId`

**F2.3 并存保证**

- 原有 4 个导航组**保持不变**
- 用户既可从原导航进入，也可从管理器进入
- 🔴 **功能不回退**（见 §7 R2）

### F3 来源标注（0.3 人日）

**F3.1 文件级标注**

左栏每个文件标来源层标签：

```
data_elements   [全域] [行业] [案件]
```

含义：该文件在三层中均存在声明（或仅部分层存在）。

**F3.2 条目级标注**

进入可写文件后，顶部显示当前编辑范围所属层。

**F3.3 标准域警示**

编辑 `_shared` / `_industry` 条目时，顶部警示条（文案见 §8.3）。

## 七、红线与硬约束（源自核查，非偏好）

| # | 红线 | 依据 | 违反后果 |
|---|---|---|---|
| **R1** | 🔴 **做成独立 App，不加侧栏第七组** | 本体管理是**配置态**不是**作业态**：低频且危险，不该混进日常办案导航，也不该让侧栏再膨胀 | 导航继续膨胀，配置与作业混淆 |
| **R2** | 8 个现有页面**零改动挂载，功能不回退** | 渐进替换原则（用户确认）；重做是纯浪费 | 引入回归风险 |
| **R3** | 只读文件**明确标 🔒 并提示「暂无编辑界面」** | 不标注会让用户以为坏了 | 用户困惑 |
| **R4** | 编辑标准域条目**必须显示「影响所有案件」警示** | 三层结构带来新风险：用户不知道自己动的是哪层 | 静默影响全部案件 |
| **R5** | 左栏分组用**语义分组**，不按文件名平铺 | 用户痛点是「组织层次不清晰」，平铺解决不了 | 回到现状 |

## 八、文案规则

### 8.1 通用规则

- 状态图标必须配文字说明（不能只靠颜色/图标）
- 版本号展示前 8 位 + 「…」
- 「只读」不说「禁用」，说「暂无编辑界面」（后者说明是能力未开放，前者像权限问题）

### 8.2 只读文件提示（F2.3）

> 「`actions.json` 暂无可视化编辑界面，可通过案件包导出后编辑。可视化界面将在后续版本开放。」

### 8.3 标准域警示（F3.3 / 对应 S0 §8.3）

> 「⚠️ 你正在修改**全域层**数据元，此改动将影响**所有案件**。」

行业层：

> 「⚠️ 你正在修改**行业层**（金融）数据元，此改动将影响**所有采用该行业包**的案件。」

### 8.4 无 schema 标记提示

> 「`jians.json` 暂无结构声明（schema），后续开放编辑时字段校验可能不完整。」

### 8.5 版本沿革入口（S0-3 未完成时）

> 「版本沿革（待 S0-3 完成后开放）」

### 8.6 空态文案

> 「当前案件没有本体文件。请通过案件包导入，或从模板创建。」

## 九、状态机

### 9.1 页面级状态

```
加载中 → 就绪 / 空 / 错误 / 无权限
            ↓ 点击文件
        编辑器加载中 → 编辑器就绪 / 挂载失败
```

| 状态 | 说明 | 允许的转移 |
|---|---|---|
| `加载中` | 请求总览 API | → 就绪 / 空 / 错误 / 无权限 |
| `就绪` | 左栏渲染出 19 项 | → 点击文件 |
| `空` | 案件无本体文件 | → 导入 |
| `错误` | API 失败 | → 重试 |
| `无权限` | 案件不可访问 | — |
| `编辑器加载中` | 右侧挂载中 | → 编辑器就绪 / 挂载失败 |
| `挂载失败` | 现有页面渲染异常 | → 重试 / 回 JSON 页 |

### 9.2 文件状态（左栏每项）

| 状态 | 图标 | 说明 |
|---|---|---|
| 可写 | ✅ | 有写路由 |
| 只读 | 🔒 | 无写路由 |
| 无 schema | ⚠ | `schemas/` 下无声明（可与上两者叠加） |

### 9.3 来源层状态

| 状态 | 说明 |
|---|---|
| 仅案件 | 该层独有 |
| 三层共有 | 全域 + 行业 + 案件均声明 |
| 被覆盖 | 案件层覆盖了上层同名条目 |

## 十、异常与边界处理

| 编号 | 场景 | 处置 | FAIL 判据 |
|---|---|---|---|
| E1-1 | 总览 API 失败 | 错误态 + 「重试」按钮 | 白屏 |
| E1-2 | 案件无本体文件 | 空态 + §8.6 文案 + 导入引导 | 空白无提示 |
| E1-3 | 某文件被手工删除 | 该项标「缺失」，**不阻断整体加载** | 整体崩溃 |
| E1-4 | 某文件 JSON 解析失败 | 该项标「解析失败」，**不阻断整体** | 整体崩溃 |
| E2-1 | 现有编辑页挂载失败 | 「挂载失败」+ 重试 + 「在 JSON 页打开」逃生入口 | 无逃生入口 |
| E2-2 | 深链接指向不存在的文件 | 回落左栏首项 + 轻提示 | 白屏 |
| E3-1 | S0-1 未完成（无行业层） | 来源层只显示「全域 / 案件」，**不报错** | 报错 |
| E3-2 | 编辑标准域未显示警示 | 🔴 违反 R4 | 无警示 |
| E3-3 | 无 schema 文件被误标记为可编辑 | 违反 R3 | 可编辑 |

> **E1-3 / E1-4 是渐进替换期的高频场景** —— 用户可能手工改坏了某个 JSON，总览必须能**局部降级**而不是整体崩。
