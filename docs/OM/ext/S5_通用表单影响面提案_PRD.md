## 二、背景与问题定义

### 2.1 现状实测（写本 PRD 前核查的结论）

| # | 发现 | 证据 |
|---|---|---|
| 1 | **schema 覆盖不全** | 19 个本体文件，仅 9 个有 schema，**10 个缺失** |
| 2 | **有校验无影响面** | `_validate_in_temp` 只回答「这一份 JSON 能不能装载」，**不回答波及什么** |
| 3 | **删属性无防呆** | 删掉一个属性，历史线索里引用它的证据链怎么办 —— **没有任何处理** |
| 4 | `proposal.schema.json` 已存在 | 说明提案机制**设计过但未实现** |
| 5 | 12 个本体文件无写路由 | `actions` / `functions` / `states` / `jians` / `scoring` … |

**10 个无 schema 文件**：

```
case_knowledge · data_elements · derived_properties
dimensions · enum_space · jians · llm_policy
scoring · states · thresholds · verify_playbooks
```

> ⚠️ 上列中 `llm_policy` **永不开放编辑**（S4 R4），补 schema 仅为完整性，**不生成表单**。

### 2.2 为什么影响面分析是 Palantir Ontology Manager 的核心价值

| | Palantir Ontology Manager | 本项目现状 |
|---|---|---|
| 保存前 | 告诉你「这个改动影响 3 个应用、17 个下游依赖」 | ❌ 无 |

**取证场景有一条 Palantir 没有的致命点**：

> **删掉一个属性，历史线索里引用它的证据链怎么办？**

Palantir 面向业务运营，数据可以重跑；本项目面向举证，**已固证的线索不能因本体改动而失效**。这是影响面分析在本项目的特殊必要性。

### 2.3 用户痛点

| # | 痛点 | 本 PRD 对应功能 |
|---|---|---|
| P1 | 改一个条目不知道波及什么 | F3 影响面分析 |
| P2 | 12 个文件连表单都没有 | F1 补 schema + F2 通用表单 |
| P3 | 标准层改动没有发布流程 | F4 提案轻量版 |
| P4 | schema 漏字段会静默丢失 | F5 未知字段兜底 |

## 四、术语

| 术语 | 定义 |
|---|---|
| **影响面** | 改一个本体条目后，受影响的规则 / 视图 / 函数 / 已物化 `obj_*` 表 / 已生成线索的集合 |
| **依赖图** | 本体条目之间的引用关系图，影响面分析的输入 |
| **提案（Proposal）** | 标准域改动的一种载体：提出 → 看影响面 → 发布 |
| **轻量版提案** | 有「提案 → 影响面 → 发布」闭环，**但无多人评审流** |
| **未知字段兜底** | schema 未覆盖字段的原样保留与展示机制 |

## 六、功能详情

### F1 补 10 个 schema（1.5 人日）

**F1.1 清单**

| 文件 | 是否生成表单 |
|---|---|
| `case_knowledge` | ✅ |
| `data_elements` | ✅（S3 已硬编码，可转通用） |
| `derived_properties` | ✅ |
| `dimensions` | ✅ |
| `enum_space` | ✅ |
| `jians` | ✅ |
| `scoring` | ✅ |
| `states` | ✅（S4 已有专用编辑器，schema 供通用回退） |
| `thresholds` | ✅ |
| `verify_playbooks` | ✅ |
| 🔴 `llm_policy` | ❌ **仅补 schema，永不生成表单** |

**F1.2 补 schema 的方法**

- 从**实际 JSON 反推**，不从文档猜
- 🔴 每个文件必须列出「实际出现但 schema 未声明」的字段（沿用 §0.3 教训）

### F2 通用 schema 驱动表单（1.5 人日）

**F2.1 渲染规则**

见 §5.3 类型映射表。

**F2.2 校验**

- `required` → 必填
- `enum` → 下拉限定
- `pattern` → 正则校验，失败阻止保存

**F2.3 适用范围**

- 优先覆盖 S2–S4 未做的文件
- 🔴 **不替换** S2–S4 已做的专用编辑器（objects/links/rules/policies/actions/data_elements）—— 专用体验更好

### F3 影响面分析（2.0 人日）★ 本阶段核心价值

**F3.1 依赖图构建**

```
本体条目 ──引用──> 规则 / 视图 / 函数 / 对象属性
已生成线索 ──引用──> 对象属性（经 source_row / fact）
已物化表 ──对应──> 对象类型
```

**F3.2 影响面输出**（五类）

| 类别 | 说明 | 严重度 |
|---|---|---|
| 🔴 **已生成线索** | 引用了该条目的线索，**并标出哪些已固证** | 最高 |
| 🟡 规则 | 引用该条目的规则 | 高 |
| 🟡 视图 | 引用该条目的视图 | 中 |
| 🟢 已物化表 | 需重跑 BUILD 的 `obj_*` 表 | 中 |
| ⚪ 函数 | 引用该条目的函数 | 低 |

**F3.3 🔴 宁可多报不可漏报**

影响面分析若漏报，用户会基于错误信息做决策 —— **比不报更危险**。

无法确定的引用（如动态 `source_sql` 里的字符串引用）**一律计入**并标「不确定」。

**F3.4 已固证线索的特殊标记**

> 这是本项目特有、Palantir 没有的能力：影响面要能区分「改了影响分析」和「改了影响举证」。

### F4 提案与发布，轻量版（1.0 人日）

**F4.1 流程**

| 步骤 | 内容 |
|---|---|
| ① 提出 | 标准域改动写入草稿（不生效） |
| ② 影响面 | 自动计算并展示 F3 面板 |
| ③ 发布 | **人工点击确认**才生效 |

**F4.2 与完整版的区别**

| | 轻量版（本版） | 完整版（不做） |
|---|---|---|
| 提案 | ✅ | ✅ |
| 影响面 | ✅ | ✅ |
| 发布 | ✅ | ✅ |
| 多人评审 / 会签 | ❌ | ✅ |
| 驳回 / 评论 | ❌ | ✅ |

**F4.3 🔴 绝不自动发布**

提案发布必须人工触发（见 §7 R4）。

### F5 未知字段兜底（0.5 人日）

**F5.1 机制**

- 渲染时对比 schema 声明字段与实际字段
- 未覆盖字段在表单底部**只读展示**（JSON 片段）
- 保存时**原样回写**

**F5.2 提示**

见 §8.5。

## 七、红线与硬约束（源自核查，非偏好）

| # | 红线 | 依据 | 违反后果 |
|---|---|---|---|
| **R1** | 🔴 影响面**宁可多报不可漏报**；不确定的引用一律计入并标注 | 漏报会让用户基于错误信息决策，比不报更危险 | 误判安全 |
| **R2** | 🔴 影响面必须**区分「已固证线索」**并单独标出 | 本项目特有：改了影响分析 vs 改了影响举证 | 悄悄破坏证据链 |
| **R3** | 🔴 **不做已生成线索的自动迁移** | 自动迁移会让「证据」在无人知晓的情况下变化，直接违反举证要求 | 举证失效 |
| **R4** | 🔴 提案**绝不自动发布**，必须人工触发 | 与「AI 不自动生效」「采纳进草稿区」同一条红线 | 未经确认的标准变更 |
| **R5** | 通用表单**不替换** S2–S4 的专用编辑器 | 专用体验更好，替换是回退 | 体验回退 |
| **R6** | 🔴 `llm_policy.json` **永不生成表单** | S4 R4 | 出网内容失控 |
| **R7** | 补 schema **从实际 JSON 反推**，不从文档猜 | §0.3 已证明 schema 会漏字段 | 再次漏字段 |

## 八、文案规则

### 8.1 通用规则

- 影响面数字必须**可点击展开**，不能只给一个总数
- 「不确定」的引用必须显式标出，不混在确定项里
- 不承诺未执行的行为

### 8.2 影响面标题（F3）

> 「影响面分析　·　共 7 处受影响（含 1 条已固证线索）」

### 8.3 已固证线索警示（R2）★

> 「⚠️ **L001 已固证**。本体变更不会自动迁移已固证线索的证据内容。
> 变更后请复核该线索的证据链是否仍然成立。」

### 8.4 不确定引用（R1）

> 「另有 2 处**可能**受影响（来自动态 SQL 引用，无法确定），建议一并复核。」

### 8.5 未知字段提示（F5）

> 「本文件有 2 个界面未覆盖字段，已原样保留：
> `jian`、`jian_source`（可在 JSON 页编辑）」

### 8.6 提案发布确认（F4.3）

> 「确认发布该提案？发布后将影响 **N 个案件**（全域层改动）。
> 此操作不可自动回退，请在版本沿革中记录后再发布。」

### 8.7 无影响面时

> 「未检测到受影响的下游依赖。
> （影响面分析覆盖规则/视图/函数/物化表/已生成线索，不覆盖动态 SQL 中的未解析引用）」

## 九、状态机

### 9.1 影响面分析

```
触发（保存前）→ 计算中 → 已完成 / 部分完成 / 计算失败
                              ↓
                         用户确认 → 继续保存 / 取消
```

| 状态 | 说明 |
|---|---|
| `计算中` | 遍历依赖图 |
| `已完成` | 五类影响全部算出 |
| `部分完成` | 某类（如线索）扫描超时 → **标注并继续**，不静默 |
| `计算失败` | 🔴 **警示**：影响面未知 ≠ 无影响，须显式告知 |

> **「计算失败」绝不能显示「无影响」** —— 见 §8.7 反向写法。

### 9.2 提案流程（轻量版）

```
草稿（draft） → 影响面已生成 → 待发布 → 已发布
                                  ↓
                              可废弃（discarded）
```

| 状态 | 说明 | 转移 |
|---|---|---|
| `draft` | 已提出未算影响面 | → 影响面已生成 / discarded |
| `影响面已生成` | 已展示 F3 面板 | → 待发布 / discarded |
| `待发布` | 用户点了发布，等待确认 | → 已发布 / 回退到影响面已生成 |
| `已发布` | 变更生效 + 版本历史 +1 | 终止态 |
| `discarded` | 废弃 | 终止态 |

### 9.3 通用表单

```
加载 → 就绪 / 空 / schema 缺失 → 编辑 → 校验 → 保存
                    ↑
              schema 缺失时用 F5 兜底（降级，不阻断）
```

## 十、异常与边界处理

| 编号 | 场景 | 处置 | FAIL 判据 |
|---|---|---|---|
| E1-1 | 补 schema 时又发现未声明字段 | **必须列出**并补进 schema（R7） | 漏字段 |
| E1-2 | 实际 JSON 与 schema 长期不一致 | 标「schema 可能过期」 | 静默 |
| E2-1 | 文件无 schema（未补完） | **降级为 F5 兜底展示**，不阻断 | 白屏或阻断 |
| E2-2 | schema 与数据冲突（类型不符） | 警告 + 用实际类型渲染 | 崩溃 |
| **E3-1** | 影响面计算超时 / 部分失败 | 标注「部分完成」+ 列出未算出部分 | **显示「无影响」** |
| **E3-2** | 影响面完全计算失败 | 🔴 显式警示「影响面未知，不等于无影响」 | 显示「无影响」 |
| E3-3 | 动态 SQL 引用无法确定 | **计入** + 标「不确定」 | 漏报 |
| E3-4 | 删除被已固证线索引用的属性 | **不阻止**，但必须显示 §8.3 警示 | 静默通过 |
| E3-5 | 影响面为 0 | 显示 §8.7（含覆盖范围说明） | 只显示「0 处」 |
| E4-1 | 提案未看影响面直接发布 | **阻止**（流程顺序：影响面在发布前） | 可跳过 |
| E4-2 | 提案自动发布 | 🔴 **不可能**（R4） | 自动发布 |
| E4-3 | 提案发布后影响面变化 | 提示「影响面已变化，建议重新评估」 | 静默 |
| E5-1 | 未知字段被通用表单保存 | **原样保留** | 丢失 |
| E5-2 | `llm_policy` 被通用表单渲染 | 🔴 **不可能**（R6） | 出现表单 |

> **E3-1 / E3-2 是本 PRD 最重要的两条**：影响面分析失败时若显示「无影响」，用户会以为安全 —— **这是典型的危险方向静默失败**。

## 十一、权限

| 动作 | 要求 |
|---|---|
| 查看影响面 | 案件可访问 |
| 编辑标准域本体 | `is_ontology_admin=1` **且** rank ≥ 偏将 |
| 提出提案 | 同上 |
| **发布提案** | 同上（**本版不引入独立评审人角色**） |
| 废弃提案 | 提出人本人 或 本体管理员 |

> 轻量版**不引入独立评审人角色** —— 提案与发布同一人，靠「影响面必须看过 + 人工确认」兜底。完整评审流等真实协作需求出现再加。

## 十二、验收用例（每条可独立跑）

| 编号 | 用例 | 预期 | FAIL 判据 |
|---|---|---|---|
| UC-S5-1 | 补完 schema 后逐个核对实际 JSON | 10 个文件**无未声明字段** | 有漏字段 |
| UC-S5-2 | 用通用表单打开 `jians.json` | 按类型渲染出控件 | 无法渲染 |
| UC-S5-3 | 通用表单 `required` 留空保存 | **阻止** | 保存成功 |
| UC-S5-4 | 通用表单 `pattern` 不匹配 | **阻止** | 保存成功 |
| UC-S5-5 | 打开无 schema 文件 | **F5 兜底展示**，不白屏 | 白屏 |
| UC-S5-6 | 通用表单含未知字段 → 保存 | 字段**原样保留** + §8.5 | 丢失 |
| UC-S5-7 | 打开 `llm_policy.json` | 🔴 **无表单**，仅只读展示 | 出现表单 |
| **UC-S5-8** | 删除被 3 条线索引用的属性 | 影响面列出 **3 条线索** | 漏报 |
| **UC-S5-9** | 上例中 1 条已固证 | **单独标出「已固证」** + §8.3 警示 | 未区分 |
| **UC-S5-10** | 影响面计算部分失败 | 标「部分完成」+ 列出未算出部分 | **显示「无影响」** |
| **UC-S5-11** | 影响面完全失败 | 🔴 显式警示「影响面未知，不等于无影响」 | 显示「无影响」 |
| UC-S5-12 | 动态 SQL 引用 | **计入** + 标「不确定」 | 漏报 |
| UC-S5-13 | 影响面为 0 | 显示 §8.7 含覆盖范围说明 | 只显示「0 处」 |
| UC-S5-14 | 影响面数字点击 | **可展开**看具体条目 | 不可展开 |
| UC-S5-15 | 未看影响面直接发布提案 | **阻止** | 可跳过 |
| UC-S5-16 | 提案发布 | **人工点击才生效**，无自动路径 | 自动发布 |
| UC-S5-17 | 提案发布后查版本历史 | **新增一条**（含操作人/理由） | 无记录 |
| UC-S5-18 | 废弃提案 | 状态转 `discarded`，本体未变 | 本体被改 |
| UC-S5-19 | 通用表单打开 `objects.json` | 🔴 **仍是 S2 专用编辑器**，未被替换 | 被替换 |

> **UC-S5-9 / UC-S5-10 / UC-S5-11 是三条最关键的用例**，对应 R2 与「失败不等于无影响」。
>
> **UC-S5-19 防的是「通用表单把专用编辑器的体验打回去」** —— 这是通用化的典型副作用。
