## 二、背景与问题定义

### 2.1 现状实测（写本 PRD 前核查的结论）

| # | 发现 | 证据 |
|---|---|---|
| 1 | **行业层不存在** | `ontology/` 下只有 `_shared` / `default` / `reqd_case`；`pack_meta.json` 里的 `industry: 金融` **只是标签，无目录、无合并逻辑** |
| 2 | **写的是副本不是标准** | 全部写路由走 `snapshot_paths(ctx, case_id)` → `snap_dir`；`PACK_ROOT`、`_shared`、模板包**零写路由** |
| 3 | **版本是假凭据** | `fingerprint()` 全库只在建案（`cases.py:97`）与导包调用，**写路由一个都不调** |
| 4 | **指纹清单不全** | `_FINGERPRINT_FILES` 只算 8 个文件，`data_elements.json` 不在其中（而它 Web 可写）；`_shared` 完全不参与 |
| 5 | **审计记错了版本** | `model_designer.py` 写接口记 `data_version`（数据 BUILD 次数），**未记本体快照版本** |
| 6 | **正在产生错误后果的假承诺** | `ConfigConfirmDialog` 对 `dangerous=true` 一律显示「保存后自动触发 RESCAN」，7 个页面用它，**但只有 `rule_workshop.py:191` 真正入队** |

### 2.2 用户痛点（原话转述）

> 「增加本体管理员。建议用户重跑 build，由于 ontology 是有版本的，历史案例随着老版本走，新案件随着新版本走。」
> 「当前不考虑已有案件，所有的已有案件都是测试数据。」

拆解为四个可设计的具体问题：

| # | 痛点 | 本 PRD 对应功能 |
|---|---|---|
| P1 | 三层全域化缺中间层，行业数据元建了没地方放 | F1 三层落地 |
| P2 | 谁都能改标准，改标准无门槛 | F2 本体管理员能力位 |
| P3 | 改了本体但版本凭据说没改，举证时无法自证「这份本体是哪个版本」 | F3 版本机制修复 |
| P4 | 弹窗说「自动重跑」，实际没跑，用户以为机器语义已更新 | F4 保存反馈修正 |

### 2.3 可用资产

| 资产 | 说明 |
|---|---|
| `fingerprint()` | 已存在，目录内容 → 12 位指纹，无需新写哈希逻辑 |
| `shutil.copytree` 快照 | `cases.py:85-101` 建案即物理复制 + 锁定，**历史案件随老版本走已天然成立** |
| `is_admin` 布尔位 | W-024 平台审计已有先例，可完全照搬 |
| 追加式迁移范式 | `repo_sqlite.py:208` 已有 ALTER TABLE 追加列的现成写法 |

## 四、术语

| 术语 | 定义 |
|---|---|
| **三层** | 全域层 `_shared` → 行业层 `_industry/{金融,医疗}` → 案件层（快照）。**合并优先级：案件 > 行业 > 全域** |
| **本体版本** | 案件快照目录内容的指纹，形如 `A1B2C3D4E5F6`（12 位） |
| **版本历史** | 该案件快照历次本体变更的**追加式**记录链，每条含版本、操作人、理由、变更文件、时间 |
| **本体管理员** | `meta_users.is_ontology_admin = 1` 的用户；与 rank 联合判定 |
| **标准域** | `_shared` / `_industry` / 模板包 —— 改了影响**所有案件** |
| **案件域** | 案件快照 —— 改了只影响**本案件** |
| **假承诺** | UI 声称会自动执行、实际未执行的文案 |

## 六、功能详情

### F1 `_industry` 三层结构落地（1.0 人日）

**F1.1 建目录与元数据**

- 在 `ontology/` 下新建 `_industry/` 目录
- 首批建两个行业包：`金融`、`医疗`
- 每个行业包含 `pack_meta.json`（至少含 `industry` 字段）与 `data_elements.json`

**F1.2 加载器改造**

- 现有加载器只做 `pack → 案件快照` 两层
- 改为三层：`_shared` → `_industry/{industry}` → 案件快照
- **合并优先级固定：案件 > 行业 > 全域**（见 §7 R1）

**F1.3 案件层可覆盖**

- 案件层若声明同名数据元，覆盖行业层与全域层
- 界面侧（S1-3）需标出覆盖关系

### F2 本体管理员能力位（0.5 人日）

**F2.1 数据列**

```
meta_users.is_ontology_admin   INTEGER DEFAULT 0
```

- 沿用 `is_admin` 先例，独立布尔位
- 🔴 **不新增 rank 等级**：`access.py` 注释明写 ROLE_RANK 与 ROLE_CLEARANCE「禁止直接互比」，新增 rank 要维护两张表，正是它自己警告的漂移风险

**F2.2 门禁双条件**

```
可写标准域  ⟺  is_ontology_admin = 1  且  ROLE_RANK[role] >= 偏将
```

- 与 `core/policy.py:95`（`role in roles 且 clearance >= min_clearance`）既有模式同构
- **双条件意义**：光是本体管理员不够（还得有办案资格），光是偏将也不够（不能改标准）

**F2.3 迁移**

- 用 `repo_sqlite.py:208` 的追加式 ALTER TABLE 范式
- 🔴 **meta.db 是用户库不是测试数据** —— 即使前提③作废全部案件数据，此列仍需安全追加，不得重建表

### F3 版本机制修复（1.0 人日）

**F3.1 编辑后重算指纹**

- 所有本体写路由落盘成功后，调用 `fingerprint(snap_dir)` 重新计算
- 更新案件 `current_ontology_version`

**F3.2 追加版本历史**（🔴 追加，非覆盖）

新表 `pack_snapshot_history`，每条记录：

| 字段 | 说明 |
|---|---|
| `case_id` | 案件 |
| `version` | 本次指纹 |
| `prev_version` | 上一版本（首条为 null） |
| `operator` | 操作人 |
| `reason` | 变更理由（必填，复用现有理由输入） |
| `changed_files` | 变更文件清单 |
| `snapshot_ref` | **完整快照引用**（见 §7 R2） |
| `created_at` | 时间 |

**F3.3 指纹清单扩容**

现有 `_FINGERPRINT_FILES` 8 个文件，本次纳入：

| 新增纳入 | 理由 |
|---|---|
| `data_elements.json` | Web 可写（`DataElementsView`），不纳入则改了数据元版本号纹丝不动 |
| `_shared` 目录内容 | 全域数据元改了，所有案件版本都应变化 |
| `_industry` 目录内容 | 同上（F1 建层后） |

> 前提③下**无需迁移已有案件**，清空测试数据重建即可。

**F3.4 审计字段补充**

- 审计事件同时记 `data_version`（现状，保兼容）与 `ontology_version`（新增）
- 🔴 **不替换** `data_version` —— 旧审计记录的解析逻辑不动，避免破坏既有审计链

### F4 保存反馈修正（0.3 人日）

**F4.1 删除假承诺文案**

- `ConfigConfirmDialog` 中「保存后自动触发 RESCAN 重跑」文案**仅在确会入队时显示**
- 判据：`dangerous=true` **且** 该写路由确实调用入队

**F4.2 分级提示**（详见 §8.2）

按改动类型给不同强度提示，不承诺自动执行。

## 七、红线与硬约束（源自核查，非偏好）

| # | 红线 | 依据 | 违反后果 |
|---|---|---|---|
| **R1** | 合并优先级**固定**为 案件 > 行业 > 全域，**不可配置** | 若可配置，同一份数据在不同案件可能解析出不同结果，破坏可复现性 | 取证结论不可复现 |
| **R2** | 版本历史**只追加、不覆盖**；且须保存**完整快照引用** | 版本机制唯一目的是举证；只存元数据等于「知道改过但拿不出改前是什么」，回溯性存疑 | 举证时无法自证 |
| **R3** | 🔴 **禁止出现「保存后自动触发 RESCAN」类文案，除非确已入队** | 现有 7 个页面正在产生此错误：用户以为机器语义已更新，`obj_*` 表其实还是旧的甚至不存在 | 危险方向的假承诺 |
| **R4** | `is_ontology_admin` 用**能力位不改 rank** | `access.py` 明令两把尺子禁止互比 | 权限体系漂移 |
| **R5** | **不迁移已有案件**（前提③：均为测试数据） | 用户明确指示 | 无谓工作量 |
| **R6** | `meta.db` 的 schema 变更走**追加式 ALTER**，不重建 | 用户库可能含真实账号 | 账号数据丢失 |

## 八、文案规则

### 8.1 通用规则

- 不承诺未执行的行为
- 涉及「影响所有案件」的改动必须显式警示
- 版本号一律展示前 8 位 + 「…」（如 `A1B2C3D4…`），完整值悬停可见

### 8.2 保存反馈分级文案（F4.2）

| 改动类型 | 强度 | 文案 |
|---|---|---|
| **结构变更**：新增/删除对象类型、改 `pk`、改属性 `type` | 🔴 强 | 「本体已保存。**需重跑 BUILD 才生效** —— 新增对象类型不重跑会导致 `obj_*` 表不存在。」+「前往任务中心」按钮 |
| **展示变更**：改 `title` / 描述 / 数据元 `clean_rule` | 🟡 轻 | 「本体已保存，**下次 BUILD 生效**。」 |
| 其余 | — | 「本体已保存。」 |

### 8.3 标准域改动警示文案（F1.3 / S1-3 使用）

> 「⚠️ 你正在修改**全域层**数据元，此改动将影响**所有案件**。」

### 8.4 版本沿革文案（S1-3 版本视图使用）

> 「当前本体版本 `A1B2C3D4…`　·　共 3 次变更　·　最后变更：张三，2026-09-14 10:22，改 `objects.json`」

### 8.5 权限不足文案（F2）

> 「403 · 需要本体管理员权限（且职级 ≥ 偏将）才能修改标准层本体。」

## 九、状态机

### 9.1 案件本体版本状态

```
        建案
         ↓
   [v1 已锁定] ──编辑保存──> [待重算指纹]
                                │ 重算成功
                                ↓
                          [v2 已锁定]  （v1 存入历史）
                                │ 重算失败
                                ↓
                        [版本异常] ──> 告警 + 保留 v1
```

| 状态 | 说明 | 允许的转移 |
|---|---|---|
| `v1 已锁定` | 建案时 `copytree` + `fingerprint` 完成 | → 待重算指纹 |
| `待重算指纹` | 写路由落盘成功，正在重算 | → v(N+1) 已锁定 / 版本异常 |
| `v(N+1) 已锁定` | 新版本生效，旧版本入历史 | → 待重算指纹 |
| `版本异常` | 重算失败（IO / 权限） | 保留上一版本 + 告警，不静默 |

### 9.2 三层加载状态

| 状态 | 说明 |
|---|---|
| `无行业层` | `pack_meta.industry` 为空或行业包不存在 → **只用 全域 + 案件 两层**，不报错 |
| `三层完整` | 全域 + 行业 + 案件 |
| `合并冲突` | 同名条目被覆盖 → 记录覆盖关系，供 S3-2 可视化 |

### 9.3 权限判定状态

| 状态 | 条件 |
|---|---|
| 可写标准域 | `is_ontology_admin=1` 且 rank ≥ 偏将 |
| 仅可写案件域 | rank ≥ 偏将（现状不变） |
| 只读 | 其余 |
| 403 | 越权访问写端点 |

## 十、异常与边界处理

| 编号 | 场景 | 处置 | FAIL 判据 |
|---|---|---|---|
| E1-1 | `pack_meta.industry` 指向不存在的行业包 | **降级为两层**，记日志，**不报错阻断** | 加载失败 |
| E1-2 | 案件层与行业层同名数据元 | 案件层覆盖，记录覆盖关系到合并结果 | 行业层反客为主 |
| E1-3 | `_industry` 目录不存在（旧快照） | 同上，降级两层 | 崩溃 |
| E2-1 | 非本体管理员访问标准域写端点 | 403 + §8.5 文案 | 返回 200 |
| E2-2 | `is_ontology_admin` 列不存在（旧库） | 走追加式迁移，**不重建表** | 账号数据丢失 |
| E3-1 | 重算指纹失败（IO 错误） | 保留上一版本 + 显式告警 | 静默沿用旧版本 |
| E3-2 | 版本历史写入失败 | 🔴 **回滚本体写入**，两者必须原子 | 本体已改但无版本记录 |
| E3-3 | 连续三次编辑 | 历史应为 v1→v2→v3 **三条记录** | 只剩一条（覆盖写） |
| E3-4 | 指纹清单扩容后老案件版本号变化 | 前提③：**不处理**，清空测试数据重建 | — |
| E4-1 | `dangerous=true` 但未真入队 | 文案不得出现「自动触发」 | 仍显示该文案 |
| E4-2 | 新增对象类型后未重跑 BUILD | 强提示 + 一键跳转任务中心 | 无提示或轻提示 |

> **E3-2 是最容易被漏的**：本体写入成功但版本历史写入失败，会造成「改了但说不清改了什么」——比不改更危险。必须原子。

## 十一、权限

| 动作 | 要求 |
|---|---|
| 编辑案件域本体 | rank ≥ 偏将（现状不变） |
| 编辑标准域（`_shared` / `_industry` / 模板包） | `is_ontology_admin=1` **且** rank ≥ 偏将 |
| 查看版本历史 | 案件可访问即可 |
| 授权本体管理员 | 平台管理员（`is_admin=1`） |

> **为什么不加 rank**：rank 是「能看什么数据、办什么案」，本体管理员是「能改什么标准」——**两者正交**。一个主办可能是本体管理员，也可能不是。

## 十四、待确认（实施前需明确）

| # | 事项 | 建议 |
|---|---|---|
| 1 | **版本历史存完整文件快照（+0.5 人日）还是只存元信息？** | 建议**存完整快照引用**。版本机制唯一目的是举证，只存元数据等于「知道改过但拿不出改前是什么」，回溯性存疑。若你接受元信息够用，可省 0.5 人日 |
| 2 | 行业包是否需要版本化（一个行业多个版本共存）？ | 建议**不版本化**，保持一个行业一个当前版本，与案件快照机制解耦 |
| 3 | 新增行业（如「税务」）是由管理员在 Web 建，还是发版时加目录？ | 建议**先发版加目录**，Web 建行业包归入 S5 通用表单 |
| 4 | `prev_version` 为 null 的首条记录，`reason` 填什么？ | 建议填「建案快照」，与用户填写的理由区分开 |
