01项目定位与三条禁令

这不是一个聊天助手，也不是一个"AI 断案"产品。它是一个跑完就出结构化产物的侦查推演内核。

系统把多源异构的原始数据（银行流水、通话记录、招投标档案、工商登记、轨迹出行、公开 OSINT、举报材料）统一编译成一套语义层（obj_* 对象表 / lnk_* 链接表）， 在其上执行声明式规则，产出带溯源 ID 的线索（clue），再经去重、优先级排序、交叉升格，进入人工处置看板。全程确定性，同一份输入必然产出同一份输出。

三条硬性禁令（写在 AGENTS.md，并由代码强制）

禁令代码中的强制点
① 不自己写业务 SQL core/store.py 维护 _FORBIDDEN_TABLES（银行流水/通话记录/招投标档案/工商信息/轨迹出行/公开OSINT/举报材料），命中即抛 DirectSourceAccessError；scripts/audit_straight_sql.py 做静态扫描，CI 组 audit 强制通过。绕过方式只有 unsafe=True 通道，且必须带 operator + reason 并落 meta_unsafe_query。
② 不把原始明细搬进上下文 Function 只返回聚合结果与溯源 ID；core/row_uri.py 用 dataset@version#partition/rowid 内容寻址定位原行，需要时再 resolve_row_uri 回捞，而不是把明细灌进提示词。
③ 不下定性结论、不置"已立案" core/access.py 的 HUMAN_ONLY_STATUSES = frozenset({"已立案"})；core/action_executor.py 的 FORBIDDEN_OPERATORS = {system, ai, assistant, model, bot, auto, llm}；MCP clue_transition 额外拦截 agent: 前缀操作人。所有返回体强制挂 needs_human_review / 定性_policy / disclaimer 红线字段。

02五条设计原则

确定性优先于智能
核心链路（入库 → 语义层 → 规则 → 线索 → 处置）不依赖任何大模型。LLM 只是可选增强层（草案、解释、对齐），且有一键降级开关与影子模式（REQ-040）。
声明是数据，实现是代码
"查什么、怎么判定、谁能看"全部写在 ontology/<pack>/*.json；Python 只提供编译器、执行器与原子能力。换数据源、加规则不改检测器代码。
类型层与管道层分离
objects.json / links.json 定义"是什么"（类型层），bindings.json 定义"数据从哪来"（管道层）。二者解耦，同一套业务语义可挂不同数据源。
失败要留痕，不许静默
零命中四分类、脏值降级计数、结构降级、派发失败——全部进 run_diagnostic 与 RunHealth，与 findings 主列表物理分离，绝不污染线索、绝不参与交叉升格。
未声明即拒绝（fail-closed）
对象/链接未在 policies.json 声明策略 → 运行时一律拒绝；policies.json 文件缺失 → 全拒而非放行；schema_version != 2 → 装载期硬失败。
写路径唯一
所有写操作（状态迁移、决策、归并、人审驳回）只能经 ActionExecutor；Function 层是只读的，SQL 白名单强制首词必须是 SELECT/WITH。

05语义层：Ontology 编译内核

这是整个项目最有价值的资产。它把"数据"翻译成"业务语义"，并让翻译规则本身成为可版本化、可审计的数据。

八段声明（schema_version = 2）

声明文件层内容与工程意义
objects.json类型层Object 是什么：pk、kind（entity|event）、name_property、properties{属性: 值类型}。不含任何数据来源信息。值类型经 TYPE_SQL 驱动物化列类型。
links.json类型层Link 是什么：端点对象、边属性。只表达关系，检测判据一律不写在这里（如 lnk_time_window 不含"整数金额/排除公司"判据，过滤在 R6）。
bindings.json管道层数据从哪来：object_bindings（source / source_sql / clean / optional）+ link_bindings（build_sql）。换数据源、换案件只改这里。
rules.json规则手册rule_text（分析师写的自然语言判据，LLM 可读、随线索落产物可审计）+ function / params（唯一的机器挂钩）。
functions.json能力目录Function 声明。SQL 实现强制 SELECT/WITH 白名单 + {{param}} 模板参数；py 实现必须在 core/functions.FUNCTION_IMPLS 注册。
actions.json写路径可写动作声明：角色、必填参数、副作用、终态。allowed_from 由 states.json 反向派生（单一事实来源）。
views.json语义视图Object Views 按角色投影，查询时派生、不物化、不改写 obj_*。权限仍按 base_object 判定，不复制到视图层。
policies.json权限面对象级 / 链接级策略 + 属性级敏感列遮蔽。未声明一律 fail-closed。

另有配置/知识文件（非八段）：thresholds.json、case_knowledge.json、dimensions.json、enum_space.json、jians.json、states.json、scoring.json、derived_properties.json、data_elements.json、llm_policy.json、clean_rules.json。其中 case_knowledge.json 是人名唯一合法存放处——SQL 模板硬编码人名会被 scripts/scan_hardcoded_names.py 扫出。

编译流程中的三个关键机制

① 代理键的幂等分配（ontology.py:978）

  • event 型（transaction / call / trackpoint）：按行内容排序后取 sha1(行内容)[:12]，同内容追加 _02/_03 后缀。
  • entity 型（person / org / account…）：按 name_property 值排序后分配 sha1(名称)[:12]——新增名字不会改变已有键。
  • 自引用（pk == name_property，如 clue）：直通源自然键。
  • 意义：语义层可以反复重建，主键不漂移，历史线索与审计记录始终对得上。

② 脏值降级不中断（TRY_CAST）

  • 默认 TRY_CAST，脏值降级为 NULL 并记 obj_x.prop<-raw: N 行不可转 进 RunHealth；on_cast_error=fail 才硬失败；quarantine 态整行剔除落 build_quarantine。
  • 缺列预检：DESCRIBE 源表，必填列缺失硬失败；optional_columns 内缺失则渲染类型化 NULL 保持列集列序。
  • 多源 UNION 走 _prune_union_sql() 按已挂载表裁剪分支，避免一个分支缺失拖垮整个 BUILD。

③ 版本时钟与增量（REQ-001 / REQ-018）

  • 双 watermark：源端（源表时间列 MAX）vs 语义层。差异即 STALE + affected_objects；读网关默认拒绝陈旧数据（StaleOntologyError）。
  • 输入哈希 = sha256（按 pk 排序的全行 JSON）；参数哈希含 rules params + functions parameters + views 声明。
  • 增量重建 materialize_changed()：先对象后链接 → TEMP 暂存表 → 行级 diff → 只重写增删行 → 只重算 affected_rules。entity_mapping 是受保护表，重建不清除人工归并结果。

只读红线与防注入

SQL 白名单：_FORBIDDEN_SQL 正则命中 INSERT / UPDATE / DELETE / DROP / CREATE / ALTER / ATTACH / DETACH / COPY / TRUNCATE / GRANT / REVOKE 即拒；_assert_readonly() 另要求首词必须是 SELECT 或 WITH。
模板参数双向核对：SQL 中的 {{param}} 与 parameters 声明必须一一对应（多一个少一个都硬失败）；integer 拒 bool、boolean 严格 isinstance、date 须匹配 YYYY-MM-DD；string 类型必须声明 enum 白名单，自由文本一律拒绝。装载期与运行期共用同一决策点。

零命中不是"没发现"，而是四分类（REQ-G-002）

分类级别含义
data_absentinfo依赖的数据本来就没有——不是"干净"，是"没数据"
config_missingwarning配置缺失导致规则跑不起来
empty_result_suspectwarning数据齐全却零命中，可疑，需要人工确认
clean_scaninfo确属干净——必须由分析师在 rules.json 显式声明 zero_is_clean，不许系统自行解释
这是本项目最能体现专业度的一处设计。调查系统最危险的失败模式不是"漏报"，而是"把没查当成查清了"。这套四分类把"零命中"强制暴露给分析师，而不是让它安静地消失在空列表里。

07业务模型：五间 × 五维 × 庙算

《孙子兵法》的"五间"与"庙算"被工程化成了可计算的覆盖度模型。

五间（jians.json，声明式、新增不改 Python）

间类证据来源对象权重默认密级侦查含义
因间org、bid_project31利用敌方的既有关系网络——工商登记、招投标参与关系
内间tipoff53来自内部的举报线索——权重最高、密级最高（clearance 3）
反间transaction21从对手的资金往来中反向获取信息
死间osint_article、org40公开情报——密级最低但可对外引用
生间call、trackpoint11当场取得的动态信息——通话、轨迹

交叉升格（cross_levels，映射关系硬编码不可配）： 1 个独立源 → 观察 2 个独立源 → 线索 3 个及以上 → 可立案依据候选 —— 注意是"候选"，仍不是"已立案"。

五维覆盖（dimensions.json）

资金 通讯 行为 关系 时间 —— 庙算引擎（core/hypotheses.py）用五维 × 五间构成覆盖矩阵，做假设枚举、维度覆盖度、间类覆盖度、冲突检测。 覆盖缺口会独立报警（REQ-G-008/009/024），且"实证缺口"与"阈值边界"分开报警——没查过和查了没中，是两回事。

08线索生命周期与处置闭环

闭环机制

  • 人审闭环（REQ-016）：review 裁决 → plan_from_review 算影响面 → materialize_changed 增量重建 → 只重算受影响规则 → 发 finding.changed。entity_mapping 受保护，重建不清人工归并。
  • defer 回捞（REQ-017）：三类唤醒条件（on_dataset / after / evidence_count_gte，OR 语义），条件不可解析时留痕告警而非静默跳过。
  • 异常线索通道（REQ-G-019）：诊断产生的线索强制 is_anomaly=True、级别"待核实"，绝不参与五间交叉升格——防止系统故障被误当成侦查发现。
  • 案例库（REQ-031）：沉淀片段需过四道质量门（终态 / 脱敏 / 适用条件 / legal_basis）才能入库。

五条出口统一管控

AccessContext（frozen dataclass，operator 必填）贯穿 网关 / Function / Action / MCP / 导出 五个出口。 network="isolated" 时 can_llm_call() 返回 False——物理隔离网络下 LLM 调用被强制关闭。 MCP 会话身份由环境变量 SUNZI_OPERATOR / SUNZI_ROLE / SUNZI_CLEARANCE / SUNZI_NETWORK 声明。

LLM 治理（可选层，REQ-038~040）

  • 脱敏闸门：core/llm/redact.py，PII 正则顺序敏感（身份证先于银行卡，否则 18 位身份证会被 16-19 位银行卡规则吃掉）。
  • 提示注入防护（REQ-039）：scan_text / wrap_untrusted / sanitize_candidate / assert_no_status_change，提案不得含状态变更。
  • 定性词黑名单：explain.py 的 _QUALITATIVE_WORDS，LLM 解释中出现的定性词会被拦截。
  • 一键降级 + 影子模式（REQ-040）：LLM 不可用时核心链路照跑；LLM_OWNED_TABLES 隔离 LLM 可写范围。
  • confidence 只排序不定性（REQ-033 AC7）：七项强类型硬校验，confidence 只能影响排序，不能变成结论依据。

接入一类全新数据源要做什么

  1. profile_table.py 做列画像，自动识别值类型（否定式 phone/id_card/date_str/amount/account/number + 肯定式 person/org）；
  2. DraftAssembler 生成 objects / links / bindings 三份草案（只写 output/drafts/，绝不写 ontology）；
  3. 分析师审阅后把草案落到 ontology/<pack>/；
  4. 若需新检测能力：在 functions.json 声明（py 实现需在 FUNCTION_IMPLS 注册），在 rules.json 写 rule_text 判据 + params；
  5. 在 policies.json 补策略——漏了会在运行时被 fail-closed 拒绝；
  6. validate_ontology.py --strict 校验后 build_ontology.py 编译。

全程不改检测器 Python 代码——这是"声明是数据"原则的直接兑现。

13业务价值

① 把经验手艺变成可复现的计算
同一份数据跑两次，结果逐字节一致。判据写在 rules.json 的 rule_text 里，机器可解释、人可审计，不再依赖"某位老侦查员脑子里的那套"。
② 结论可追溯到原始行
每条 finding 都背溯源 ID（dataset@version#partition/rowid）。要复核时按 URI 回捞原始行，而不是重新跑一遍 hoping 结果一样。这是调查工作能进法庭的前提。
③ 分清"没查"和"查了没中"
零命中四分类 + 维度覆盖缺口独立报警。调查系统最危险的失败是把"数据没接进来"静默呈现为"没有异常"，这套机制把这个坑堵上了。
④ 人机边界由代码强制，不由自觉
"已立案"是 human 专属终态、LLM 不能定性、Agent 只能提 draft 提案、confidence 只排序不定性。这些不是提示词里的软约束，是代码里的硬拦截。
⑤ 换数据源不改代码
类型层与管道层分离，新数据源只加 binding 声明。对调查场景尤其关键——每个案子的数据源都不一样，接入成本必须趋近于零。
⑥ 全程留痕，可自证清白
哈希链审计 + 17 类事件 + 内容寻址归档。任何一步"你当时为什么这么判"都能回放，且能自证记录未被篡改。
⑦ 密级与脱敏内建
对象/链接/属性三级鉴权 + 五间密级。举报线索（内间，clearance 3）天然对见习、正兵不可见；导出、MCP、Web 三条出口共用同一套策略。
⑧ 纯离线可部署
内核零 LLM 依赖、零 API Key。可完整部署在物理隔离网络中（network="isolated" 时 LLM 调用被强制关闭）。

14工程治理与质量现状

测试体系

  • run_tests.py 注册 121 个测试组，tests/ 下 98 个测试文件。
  • 每个测试组绑定需求编号（REQ-001~046、REQ-G-001~024、REQ-D-001~022、REQ-P M1~M6、Web M1~M6）。需求 → 测试 → 代码三者可互查，这是极好的可追溯性。
  • 两条静态红线进 CI：audit 组（直查扫描）与 guard 组（直查拦截）。
  • MCP 端到端：scripts/mcp_client_test.py，69 项断言覆盖 13 工具并含三条红线用例。
  • e2e 组跑全链路；--fast 跳过，--only <组> 单跑。

降级协议（REQ-G 系列）是一大亮点

项目用整整三波需求（约 20 个测试组）专门处理"系统自己出问题时该怎么办"：脏日期、缺列、实体解析跳过、函数空转、事件发布失败、唤醒条件不可解析、版本锚点缺失、派发失败…… 统一协议是：降级但不静默，留痕但不污染。降级结果进 run_diagnostic，绝不进 findings，绝不参与交叉升格。这一点比绝大多数同类系统想得深。

技术栈

Python 3.12+ DuckDB LadybugDB（可选） FastAPI Vue 3 + TypeScript JSON Schema —— 内核部分无重量级框架，无 ORM，SQL 手写并严格白名单化。

15核对发现：风险与改进建议

以下为逐行核对代码后发现的事实性偏差与能力边界，供参考。

① 文档与代码已漂移（建议优先修）
AGENTS.md 写"70 组测试"、后又写"73 组全绿"，但 run_tests.py 的 GROUPS 注册表实际有 121 组（Web M1–M6、REQ-D、REQ-P、六项解耦等大批测试组未同步进文档）。 AGENTS.md 是 agent 的第一入口，数字错误会导致新人/AI 误判"跑完就是全绿"。建议改为"以 run_tests.py 的 GROUPS 注册表为准"并删除硬编码数字。
② 图算法能力偏薄
全仓检索确认：仅实现两跳定长路径、变长跳邻居（[:*1..N]）、度（degree）统计。 未实现社区发现（Louvain/LPA）、PageRank、中介/接近中心性、最短路径、k-core。 对"资金网络团伙识别"这类需求，目前只能人工看两跳。建议优先补 Louvain 与最短路径。
③ Windows 原生无法使用图库
LadybugDB 官方 CI 不构建 Windows 版扩展，core/graph.py 走 CSV 中转，ATTACH DuckDB 在 Windows 上不可用（WSL/Linux 可用，需手工把 libduckdb.so 放到 ~/.lbdb/extension/<版本>/<平台>/common/）。 意味着 Windows 环境下图能力实质是残缺的，交付前需明确标注环境要求。
④ 规则数量偏少，且集中在资金维度
R1–R6 中资金维度占 3 条（R1/R2/R6），通讯/行为/关系各 1 条，时间维度仅 R6 一条且依附于资金判据。 作为演示骨架合格，作为生产系统需扩充。不过架构上扩展成本很低——加规则只写 rules.json。
⑤ 两把角色尺子存在认知负担
ROLE_RANK 与 ROLE_CLEARANCE 数值不一致（如偏将 rank=2 但 clearance=3，human rank=4 但 clearance=3）。 虽有注释禁止互比，但这是典型的易错点，建议在 AccessContext 层提供语义化方法而非暴露裸数值。
⑥ 启发式扫描是告警而非判定
sensitive_scan.py（列名 hints + 值模式，hit_ratio 默认 0.3）、unit_scan.py（中位数差 ≥10000 倍）都是启发式， 设计上"只告警不阻断"是对的，但需防止使用者误当作权威结论。建议在产物中显式标注 method=heuristic。
⑦ 代码规模与二元结构
core/ontology.py 单文件 1380 行，是编译器 + 类型模型 + 增量逻辑的聚合体，是全仓最难维护的模块。 同时 core/（离线内核）与 server/（Web 后端）存在一定职责重叠（server 侧有独立的 disposal_board.py、graph_view.py）， 需警惕逻辑双写导致的行为不一致。

总体判断

这是一个架构设计明显强于功能覆盖度的项目。它的真正资产不是那 6 条规则，而是那套"声明式语义层 + 确定性规则引擎 + 失败留痕 + 哈希链审计 + 人机边界硬拦截"的骨架。 规则可以补、图算法可以加，但这套骨架一旦缺失，任何"AI 侦查系统"都只是一次性的、不可复现的、无法追责的玩具。

最值得肯定的三处设计：零命中四分类（堵住"把没查当成查清"这个最危险的坑）、诊断与 findings 物理分离（系统故障不会被误当侦查发现）、 Agent 唯一写通道只产 draft 提案（人机边界由代码而非提示词保证）。
