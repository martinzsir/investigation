# 线索研判画布 PRD（落地版）

## 一、概述

**文档信息**

| 版本号 | 日期 | 作者 |
|--------|------|------|
| V1.0.0 | 2026-09-13 | 用户（需求）/ Trae（整理） |

### 1. 需求背景

- **目标用户现状**：研判岗分析师（经侦/职务犯罪侦查）在线索详情页中，已经可以查看三栏证据（事实/推断/待核实）、处置核查项（verify-items）、挂接书证、一键复跑。但"这条线索按什么规则命中 → 涉及哪些事实 → 事实从哪几行数据来 → 推断出什么假设 → 要核实什么 → 核实结论如何反证假设"这条研判链路分散在多个 Tab 和人工脑图中。
- **核心痛点**：研判过程不可视、不可保存、不可审计；事实到数据源行的反向追溯要点开多个面板手工拼；推理结论缺乏与证据/核实项的显式连线；换人或事后复查时无法还原当时的研判思路；向领导汇报需另写文档且报告与证据脱节。
- **当前问题汇总**：

| 问题点 | 问题描述 | 当前影响 |
|--------|----------|----------|
| 研判链路碎片化 | 规则、事实、推断、核实项、书证、数据源分布在不同组件 | 分析师脑内拼图，无法交接、无法复盘 |
| 反向追溯成本高 | 事实→语义对象→数据行→数据源文件需跨面板手工操作 | 溯源耗时长，汇报时被追问依据无法即时应答 |
| 规则不可见 | 命中判据 rule_text/阈值埋在线索 detail 与 rules.json | 业务专家说不清"系统凭什么报这条线索" |
| 推断无落点 | 人工假设记录在纸面/聊天里，与核实项、书证无结构关联 | 假设被证实/查否后无法回溯，重复劳动 |
| 报告与证据脱节 | 研判报告另行撰写，事实陈述无锚点 | 报告可能出现无据陈述，复核成本高 |

### 2. 需求目标

- **业务目标**（可验证）：
  1. 单条线索的研判全链路（规则→事实→推断→待核实→证据→数据源）在一张画布上完整呈现，关键节点 100% 可点击溯源到数据行/数据源文件。
  2. 研判过程可保存、可快照回滚、可交接；他人打开画布看到的布局与内容与保存时一致。
  3. 一键生成多版本研判报告，报告中每条事实陈述均带可点击溯源引用；无据内容必须标注"待核实"，不得伪装成事实。
- **成功标准**：

| 指标 | 当前状态 | 目标状态 |
|------|----------|----------|
| 事实节点可溯源到数据行的比例 | 需手工跨面板拼 | 种子事实节点 100% 带溯源入口（URI 形态或字段行形态） |
| 画布刷新后布局一致率 | 无画布 | 自动保存后坐标一致率 100%（防抖落库） |
| 报告事实句带引用率 | 不适用 | ≥95%；无引用句必须落入"待核实"段，由单测强制 |
| LLM 无据回答 | 不适用 | 0 条（引用校验不通过的句子不输出为事实，单测可造 fixture 验证） |
| 核心需求自动化测试覆盖 | 不适用 | 每条 RC 需求至少 1 个后端或前端单测用例 |

### 3. 需求范围

- **包含**（范围冻结版）：
  - 线索详情页新增「研判画布」Tab，每线索单画布，惰性初始化、自动保存
  - 规则显形（业务视图 rule_text/依据；审计视图 rule_id/function/params/阈值）
  - 反向逐层下钻：规则→事实→语义对象/链接→数据行(row_uri)→数据源文件；字段级遮蔽
  - 正向推断链与 playbook/LLM 待核实条目生成（复用 verify-items + proposals 审批）
  - G6 v5 画布：dagre 分层布局、节点拖拽/钉住/重排、连接桩连线、4 类人工关系、合法性矩阵
  - 人工节点（假设/备注）与白名单只读 Function 查询结果节点
  - 手动快照、快照回滚（坐标与内容一起冻结）
  - LLM 只读问答（强制引用、无引用不输出为事实、建议走 proposals）
  - 多版本不可变研判报告（冻结当刻画布快照、逐句引用可点回、Markdown 复制、Word 导出）
  - 业务视图/审计视图切换；G6 加载失败降级节点-关系列表
  - 全链路写操作审计与 AccessContext/PolicyEngine 权限治理
- **不包含**：多画布/多分支版本；LLM 直接写画布；画布上编辑/新建规则（仍归规则手册/rule_workshop）；自由 SQL；跨线索合并画布；PDF 导出；数据源重新上传（复用现有 ingest 登记链路，仅展示）。

## 四、功能说明

> 通用约定：
> - 画布节点分两类：**系统节点**（`system=true`，存在性由数据决定，仅可移动、不可删改）与**人工节点**（可增删改）。

> - 所有写接口经 AccessContext 校验并写审计链；LLM 会话 `network=isolated`，`llm_enabled=false` 时智能入口不可用并显示治理文案。
> - 节点/边数据契约见「五、数据结构」；端点前缀 `/api/v1`。
>
> **通用文案规范（适用于全部功能，各功能表只写差异化文案）**
>
> | 场景 | 文案内容 |
> |------|----------|
> | 操作成功（轻量） | 已保存 / 操作成功（toast，2s 自动消失） |
> | 权限不足 | 当前角色无此操作权限；如需开通请联系案件管理员 |
> | 网络异常 | 网络异常，操作未完成，请检查连接后重试 |

### 功能 RC-101：画布初始化与种子成图

**功能描述**

用户首次进入线索详情页「研判画布」Tab 时，系统惰性为该线索创建唯一画布，依据线索详情（`assemble_detail` 产物：`detail.rules`、三栏 evidence、`source_rows`）生成初始节点与系统边；再次进入直接读取已保存画布。

**种子映射规则（后端纯函数，可单测）**

| 种子来源 | 节点 kind | 业务名 | ref 取值 |
|----------|-----------|--------|----------|
| detail.rules[]（或单规则 detail.rule_id） | `rule` | 规则 | rule_id |
| evidence.fact 栏每条事实 | `fact` | 事实 | fact 稳定键（clue_id+序号哈希） |
| source_rows 每行 | `source_row` | 数据行 | row_uri（无 URI 时用 local URI，同 source_row_dto 口径） |
| source_row 反查 bindings 命中的对象 | `object` | 实体（人员/账户/公司…） | `<object>:<pk>` |
| 数据源登记（ingest register_source） | `source_file` | 数据源 | upload_id/source_id |
| evidence.pending 中 playbook 建议项 | `verify_item` | 待核实 | item_id（已存在）或 playbook_id（未采纳） |
| 已挂接 clue_evidence | `evidence` | 书证 | material_id |

系统边：`rule -[命中]-> fact`、`fact -[涉及]-> object`、`object -[来源行]-> source_row`、`source_row -[所属文件]-> source_file`、`rule -[手册建议]-> verify_item`、`verify_item -[挂接]-> evidence`。

**用户流程**

```text
点击「研判画布」Tab
  ↓
GET /clues/{clue_id}/canvas
  ├─ 画布已存在 → 返回已保存 doc（含坐标）→ 渲染
  ├─ 不存在 → 后端 seed_canvas(clue_detail) 生成 doc 并落库 → 渲染
  ├─ 线索无 source_rows → 仅规则/待核实节点 + 空态引导"暂无可溯源事实"
  ├─ 语义层未 BUILD → 对象层节点跳过，事实/数据行仍生成，顶部横幅"语义层未构建，实体关联暂不可用"
  └─ 失败（500/网络）→ 画布错误态："画布加载失败" + 重试按钮，不空白
```

**状态机**（画布生命周期）

| 状态 | 进入条件 | 退出条件 | 用户可见表现 |
|------|----------|----------|--------------|
| 未创建 | 从未进入 Tab | 首次 GET 触发 seed | Tab 显示骨架 |
| 加载中 | 发起 GET | 返回/失败 | 骨架屏 |
| 可用 | 成功返回 doc | — | 正常画布 |
| 降级 | G6 动态 import/渲染异常 | 重试成功 | 节点-关系列表 |
| 错误 | GET 失败 | 点击重试 | 错误页+重试 |

**字段规范**：本功能无用户输入字段。

**文案规范**

| 场景 | 文案 |
|------|------|
| 空状态 | 暂无可溯源事实，请先在「核查工作区」补充或运行检测 |
| 加载中 | 正在根据线索事实初始化画布… |
| 语义层未构建 | 语义层未构建，实体关联暂不可用；数据行溯源仍可使用 |
| 操作失败 | 画布加载失败，请重试 |
| 网络异常 | 网络异常，画布未加载，请检查连接后重试 |

**异常处理**

| 异常 | 触发 | 处理 | 反馈 |
|------|------|------|------|
| seed 缺规则 | detail 无 rule_id/rules | rule 节点缺省生成"未关联规则（历史产物）"占位节点，不报错 | 节点标注"历史线索" |
| 行无 URI | 纯数据 dict source_row | 按 source_row_dto 现有 local URI 口径生成 | 正常展示 |
| 数据源未登记 | row_uri dataset 匹配不到 upload | source_file 节点降级为 dataset 名文本节点（不可展开） | 节点标注"未登记数据源" |

**验收标准 AC-101**

1. 首次 GET 返回的节点数量与给定 fixture 线索 detail 的 rules/facts/source_rows 映射数量完全一致（单测断言）。
2. 第二次 GET 不重新 seed，返回首次保存的 doc（幂等，单测两次调用比较）。
3. 每个 fact 节点可达至少一个 source_row 节点（系统路径连通性单测）。
4. 无 source_rows 的线索 seed 不抛异常。
5. 前端首次进入显示骨架，成功后渲染；失败显示重试。

**单测点**

- 后端 `tests/test_canvas_seed.py`：`test_seed_node_mapping`、`test_seed_idempotent`、`test_fact_connects_to_row`、`test_seed_without_source_rows`、`test_unregistered_source_fallback`。
- 前端 `tests/research-canvas.spec.ts`：`shows skeleton then graph`、`error state retry`。

### 功能 RC-102：规则节点双视图

**功能描述**

| 场景 | 文案 |

### 功能 RC-103：反向逐层溯源下钻

**功能描述**

用户在节点上点击「展开来源/关联」，系统懒加载下一层：fact→关联 object、object→lnk 邻居对象（复用 graph_view 语义读路径，**只读消费 obj_*/lnk_*，不直读 Parquet、不生成自由 SQL**）、object→source_row（经 row_uri resolve）、source_row→source_file（经 ingest 登记元数据）。已展开节点再次点击折叠。

**用户流程**

```text
单击事实节点 → 抽屉显示事实文本 + 命中字段
  ↓ 点「查看来源行」
POST /canvas/expand {node_id, direction:"source"}
  ├─ 成功 → 画布新增 source_row 节点与系统边（已存在则不重复），抽屉显示字段表
  ├─ URI 归档缺失 → 返回 row_uri 原文 + 缺失标记，抽屉显示"归档行缺失"
  └─ 语义表缺失 → 返回降级提示，引导运行构建，不 500
对象节点「展开关联」→ 调语义邻居只读查询，返回一跳对象+关系边
数据源行 →「所属文件」→ 文件卡（文件名/格式/行数/上传人/上传时间）
```

**状态机**（节点展开态，前端内存态）

| 状态 | 进入 | 退出 | 表现 |
|------|------|------|------|
| collapsed | 初始 | 点击展开 | 节点无下游 |
| expanding | 发起 expand | 返回 | 节点转圈 |
| expanded | 成功 | 点击折叠 | 下游节点/边可见 |
| expand_failed | 失败 | 重试 | 节点红角标+重试 |

**字段规范**：本功能无用户输入字段。

**文案规范**

| 场景 | 文案 |
|------|------|
| 展开中 | 正在追溯来源… |
| 归档缺失 | 归档行缺失（URI：…），可能数据版本已更新 |
| 语义层未构建 | 实体关联不可用，请先在数据治理中构建语义层 |
| 叶子节点 | 已到达数据源文件，溯源结束 |

**验收标准 AC-103**

1. 逐层展开返回的节点均带 `ref` 与 `kind`，且新增边为系统边（`system=true`）。
2. 重复展开幂等：同一节点展开两次不产生重复节点/边（以 ref 去重单测）。
3. source_row 展开到文件的元数据字段与 ingest 登记记录一致。
4. 任一层失败不破坏已渲染图层，错误只作用于当前节点。
5. 字段表命中字段（hit_fields）琥珀高亮，与 TraceabilityPanel 既有口径一致。

**单测点**：`test_expand_dedup_by_ref`、`test_row_to_source_file_metadata`、`test_expand_missing_archive_row`、`test_neighbor_readonly_no_parquet`（静态/契约测试保证 expand 服务只依赖 obj_*/lnk_* 与 row_uri）；前端折叠/展开/失败重试组件测试。

### 功能 RC-105：正向推断与待核实生成

**功能描述**

规则节点提供「按核查手册生成建议」：后端复用 `verify_provision` 的 playbook 匹配（`verify_playbooks.json` 按 rule_id + assumptions），建议项以 `verify_item`（未采纳态）节点出现；用户决定采纳时走**既有 202 TASK_VERIFY 流程**（add_manual/建议采纳），画布轮询任务终态后刷新节点。LLM 生成的核实建议一律走 proposals 审批（见 RC-303），批准后才生成节点。

**用户流程**

```text
规则节点 →「生成手册核实建议」
  ↓ 后端匹配 playbook（纯只读）
画布出现虚线"建议"节点（kind=verify_item, ref=playbook_id, system=true, adopted=false）
  ↓ 点「采纳为核查项」
POST 既有 verify-items → 202 task → waitForTerminal → 刷新：节点变为已采纳（ref=item_id）
  ├─ 任务失败 → 节点标红，展示任务错误，可重试
  └─ 无匹配 playbook → 提示"手册暂无该规则的核实建议，可手工添加假设"
人工假设节点 →「转为待核实」→ 弹确认（文本默认带入假设内容）→ 同样走 202 流程
```

**验收标准 AC-105**

1. playbook 匹配结果与 verify_provision 既有单测口径一致（同一 fixture 输入，建议文本/channel 相同）。
2. 未采纳建议节点不会出现在核查工作台（仅画布存在）；采纳后两边一致。
3. 采纳走 202，终态失败时画布节点状态可回退/重试，无假成功。
4. LLM 建议不经审批不能生成 verify_item 节点（权限单测）。

**单测点**：`test_playbook_suggestion_seed_nodes`、`test_adopt_via_202_terminal_refresh`、`test_suggestion_not_in_workbench_before_adopt`、`test_llm_suggestion_requires_proposal_approval`。

| 场景 | 文案 |
|------|------|
| 非法拖入 | 该两类节点不能建立该关系 |

| 系统边操作 | 系统推断关系不可修改或删除 |

**验收标准 AC-203**

### 功能 RC-204：白名单 Function 查询节点

**功能描述**

工具箱「扩展查询」列出对画布开放的只读 Function 白名单（由后端配置，如资金追踪类）；每个函数根据 functions.json 声明的 parameters 自动生成**业务化参数表单**（不暴露 SQL/函数技术细节，标签取业务名）。提交后经 `function_invoke` 同一路径只读执行，结果以 `function_result` 节点落画布，边连接到发起查询的节点，记录查询参数、执行时间、操作人。

**用户流程**

```text
工具箱 →「扩展查询」→ 选择业务化查询项 → 填参数表单（含枚举下拉/数值校验）
  ├─ 提交 → 执行（同步短任务；超时走 202 任务，完成后补节点）
  │    ├─ 成功 → 结果节点（可继续溯源）+「查询条件」审计边
  │    ├─ 参数非法 → 表单字段级报错（与 {{param}} 白名单同口径，拒绝自由文本）
  │    └─ 语义表缺失/降级 → 提示"数据源未接入"，不产生空节点
  └─ LLM 网络隔离不受影响（Function 是本地只读计算，不走外网）
```

**字段规范**：参数表单由 functions.json 动态生成；integer/decimal 按类型校验，string 仅枚举白名单（沿用 Function 模板安全机制）。

**验收标准 AC-204**

1. 非白名单 function 名调用画布查询接口返回 4xx（单测）。
2. string 参数传枚举外值被拒（复用现有 Function 注入测试夹具）。
3. 查询节点记录入参快照，审计链可查；只读校验：执行前后数据库无写（事务/只读连接断言）。
4. 结果节点可继续 RC-103 溯源。

**单测点**：`test_canvas_function_whitelist_enforced`、`test_enum_param_rejected`、`test_function_result_node_audit`、`test_readonly_no_side_effect`。

### 功能 RC-205：防抖自动保存

**功能描述**

所有布局变动（坐标/pinned）与人工编辑在操作停止 500ms 后批量 PUT 保存；保存期间继续操作则重新计时。服务端整文档更新带 `updated_at` 版本戳，前端提交带本地基准版本，冲突（他人已更新）时提示合并策略（本版策略：**后写覆盖并提示，冲突计入审计**，不做三方合并）。

**状态机**（保存状态，前端）

| 状态 | 进入 | 退出 | 表现 |
|------|------|------|------|
| idle | 无改动 | 编辑 | — |
| pending | 改动后计时中 | 500ms 到/新改动重置 | "编辑中…" |
| saving | 请求中 | 返回 | "保存中…" |
| saved | 成功 | 新改动 | "已保存" |
| error | 失败 | 自动重试/手动重试 | "保存失败，重试" |

**验收标准 AC-205**

1. 用 fake timer 单测：连续 10 次改动只发起 1 次保存。
2. 保存失败时本地改动不丢失，重试成功后一致。
3. 刷新后坐标/内容与最后一次 saved 完全一致。
4. 系统节点位置可保存，但任何人工内容篡改系统节点 ref 的请求被拒。

**单测点**：`tests/canvas-autosave.spec.ts`（debounce 次数、失败保留、重试）；后端 `test_canvas_version_stamp_conflict`。

### 功能 RC-206：快照与回滚

**功能描述**

用户可手动打快照；每次生成报告自动创建隐藏关联快照。

**字段规范**

| 字段 | 类型 | 必填 | 长度 | 校验 | 错误提示 |
|------|------|------|------|------|----------|
| 快照备注 | 文本 | 是（手动快照） | 1–100 | 去空格后非空 | 请填写快照备注（不超过 100 字） |

快照为**不可变**完整文档（节点+边+坐标+人工内容版本）。支持列表查看、预览、回滚（回滚=把当前文档整体替换为快照内容，生成一条新版本，不删除当前状态，可再滚回）。

**用户流程**

```text
工具栏「快照」→ 填备注 → 创建（立即，非防抖）
快照条 → 选版本 →「预览」（只读高亮差异摘要）→「回滚到此版本」二次确认
  ├─ 确认 → 当前状态先自动存为恢复点 → 文档替换 → 画布重渲染 + 审计
  └─ 快照引用的系统数据后续变化（如核实项裁决）不回滚业务事实，仅回滚画布表达层；
     回滚后被引用对象若已不存在，节点显示"引用已失效"灰态
```

**验收标准 AC-206**

1. 快照创建后内容不可变（更新接口对快照表返回 4xx，单测）。
2. 回滚产生新文档版本且原状态可恢复（连续回滚 A→B→A 单测）。
3. 报告与快照一一关联，报告页可跳到快照预览。
4. 失效引用节点灰态展示不导致整图报错。

**单测点**：`test_snapshot_immutable`、`test_rollback_creates_recovery_point`、`test_stale_ref_renders_grey`。

### 功能 RC-301：画布只读问答

**功能描述**

用户就当刻画布提问，后端把画布文档（业务视图文本：规则判据、事实、假设、核实项状态、书证、溯源行摘要）组装为上下文调用 LLMClient；回答中事实性陈述必须带引用标记（节点 ID/row_uri）。同步接口（fake/短文本），超时 30s 返回超时提示。`llm_enabled=false` 或 `network` 档不允许时入口显示治理文案且后端拒绝。

**用户流程**

```text
打开问答侧栏 → 输入问题（≤500 字）/点推荐问题
  ├─ 成功 → 答案流式/整段渲染，引用为可点角标（点击高亮并定位画布节点/开抽屉）
  ├─ 含核实建议 → 答案下方「提交为核实建议」（RC-303）
  ├─ 超时/失败 → "回答生成失败，可重试"，不给出无据答案
  └─ LLM 关闭 → "当前案件未启用智能问答"，输入框禁用
```

**字段规范**

| 字段 | 类型 | 必填 | 长度 | 校验 | 错误提示 |
|------|------|------|------|------|----------|
| 问题 | 文本 | 是 | 1–500 | 非空 | 请输入问题 |

**文案规范**

| 场景 | 文案 |
|------|------|
| LLM 关闭 | 当前案件未启用智能问答（离线/治理策略） |
| 推荐问题 | 这条线索最关键的待核实点是什么？/ 哪些事实已有数据行支撑？/ 现有证据能否证实假设？ |
| 超时 | 回答超时，请重试或缩小问题范围 |

**验收标准 AC-301**

1. fake_invoke 模式下离线返回结构化答案（单测，不依赖网络）。
2. 发送给模型的上下文不含 denied 字段明文（脱敏单测，复用 redact 夹具）。
3. 回答引用角标全部能在当刻文档中解析到节点/行；解析不到的引用被后端剔除（单测）。
4. 问答不产生任何画布写入（只读断言）。

**单测点**：`test_canvas_chat_fake_mode`、`test_chat_context_redaction`、`test_dead_citations_removed`、`test_chat_readonly`。

### 功能 RC-302：引用强制校验（防幻觉硬门槛）

**功能描述**

问答与报告共用同一套"引用校验"服务：LLM 输出按句切分，事实句必须挂有效引用（节点 ref 或 row_uri 且存在于当刻文档/语义层）；无法挂引用的句子不得进入事实段落，问答中聚合到"待核实/模型推测"分区并显式标注，报告中进入"待核实事项"段。校验不过做**软提示 warning**（沿用"软校验→warning→不中断"模式：报告仍生成，但无据内容位置被强制归位）。

**验收标准 AC-302**

1. 构造 LLM 输出 fixture（含 3 条有据句、2 条无据句、1 条假引用），断言：有据句保留在事实段；无据句进待核实时段；假引用被剔除并记 warning（单测）。
2. 事实段引用覆盖率：报告 `事实与依据` 段落引用覆盖率 100%（本版以句子为粒度，单测断言零裸句）。
3. warning 列表随响应返回，前端可见"N 条表述因缺乏依据已转入待核实"。
4. 校验服务为纯函数，无 LLM 也可全部离线测试。

**单测点**：`tests/test_canvas_citation_guard.py`：覆盖有句/无句/假引用/空输出/全待核实五种 fixture。

### 功能 RC-303：问答建议转审批

**功能描述**

问答返回的核实建议经用户确认后，**不直接落画布/核查项**，而是提交到既有 proposals（`pp-` 前缀、draft 态）；审批走既有 `/proposals/{id}/decide`；approve 后由既有桥接生成 TASK_VERIFY，终态后画布出现 verify_item 节点（人工假设转待核实的人工直连路径除外——那是用户自己的操作，不经 LLM）。

**验收标准 AC-303**

1. 提交建议生成 proposal，类型/载荷与 proposals.py 现有 verify_item 提案契约一致（单测）。
2. reject 不产生任何画布变化；approve 后任务终态成功才出现节点（轮询刷新单测）。
3. operator 以 `agent:` 开头被拒（沿用既有硬约束单测）。

**单测点**：`test_chat_suggestion_creates_proposal`、`test_reject_no_change`、`test_agent_operator_rejected`。

### 功能 RC-304：报告生成与多版本

**功能描述**

用户点「生成研判报告」，系统先创建不可变画布快照（RC-206），以快照内容组装上下文调用 LLM 生成结构化报告；202 异步任务（沿用任务池/终态轮询）。每次点击产生新 `version_no` 递增的不可变版本，历史版本永久保留、可对比。

**报告结构（业务语言，禁止技术术语）**：一、线索概况；二、命中规则与判据（业务表述）；三、事实与依据（**逐句引用**）；四、研判推断（区分"已有证据支持"与"分析推测"）；五、待核实事项（关联 verify-item 状态）；六、书证清单；七、数据源清单（文件名/行数/上传时间）；附录：引用索引。

**用户流程**

```text
报告面板 →「生成新版本」→ 202 task → 面板显示"生成中 vN…"
  ├─ 成功 → 列表新增 vN（含生成时间/模型/耗时/warning 数）→ 可阅读
  ├─ 失败 → 任务 FAILED，显示原因 +「重新生成」；已建快照保留
  └─ LLM 关闭 → 按钮禁用 + 治理文案
```

**状态机**（报告版本）

| 状态 | 进入 | 退出 | 表现 |
|------|------|------|------|
| generating | 任务 PENDING/RUNNING | 终态 | 进度条 |
| ready | 成功 | — | 可阅读/导出 |
| failed | 任务 FAILED/重试上限 | 重新生成 | 错误+重试 |

**字段规范**：生成入口无输入字段（可选"补充要求"≤300 字，透传 prompt，仅做长度校验）。

**验收标准 AC-304**

1. 每次生成 version_no 严格递增且内容不可变（更新接口 4xx，单测）。
2. 报告记录关联 snapshot_id；事后修改画布不影响历史报告（修改后读旧报告断言文本不变）。
3. 报告结构化字段齐全（8 个章节键存在，空章节有固定兜底文案而非缺段）。
4. 任务失败不产生 ready 版本，快照可独立查看。
5. fake_invoke 下端到端可生成（单测/集成测试）。

**单测点**：`test_report_version_monotonic_immutable`、`test_report_pins_snapshot`、`test_report_sections_complete`、`test_failed_task_no_ready_version`。

### 功能 RC-305：报告阅读与溯源跳转

**功能描述**

### 功能 RC-306：Markdown 复制与 Word 导出

**功能描述**

报告面板提供「复制 Markdown」（含附录引用索引）与「导出 Word」。Word 由后端用 python-docx 生成（标题层级、事实句脚注式引用编号、附录表格），同步下载端点；导出行为写审计（操作人/用途/版本）。

**用户流程**

```text
「复制 Markdown」→ 剪贴板成功 toast
「导出 Word」→ GET 报告 docx 端点
  ├─ 成功 → 浏览器下载 《研判报告_线索标题_vN_日期.docx》
  └─ 失败 → toast 报错并提示改用 Markdown 复制
```

**验收标准 AC-306**

1. docx 可被 python-docx 重新打开，章节标题数 ≥8，事实段落含引用编号（单测校验生成产物，不依赖 Word）。
2. 文件名规则固定且含版本号（单测断言响应头/命名函数）。
3. 导出写审计记录；无权限角色下载被拒。
4. Markdown 复制内容与 ready 报告存储一致。

**单测点**：`test_docx_structure`、`test_export_filename`、`test_export_audit_and_permission`；前端剪贴板与下载失败兜底测试。

### 功能 RC-402：权限与会话治理

**功能描述**

全部端点经 AccessContext（operator 必填，system 旁路仅限本机既有约定）；对象/行读经 PolicyEngine；LLM 端点受 `llm_enabled` + llm_policy（network/档位/allowed_models）约束，fail-closed；画布编辑权限按案件角色（本版建议默认值：正兵及以上可编辑；只读角色仅查看——具体角色名以系统现有角色枚举实现，接口契约固定为"无编辑权限返回 403"）。

**验收标准 AC-402**

1. 无 operator 会话调用写端点 401/403（单测）。
2. llm_enabled=false 时问答与报告生成端点返回明确业务错误码而非 500。
3. policy 缺失时 fail-closed 拒绝（复用 redact/guard 默认策略夹具）。
4. 只读角色所有写端点 403，读端点 masked 口径正确。

**单测点**：`test_canvas_write_requires_operator`、`test_llm_disabled_business_error`、`test_fail_closed_without_policy`、`test_readonly_role_403_matrix`。
