## 1. 现状技术定性

### 1.1 布局实现位置

| 层 | 文件 | 职责 |
|---|---|---|
| Server | `server/app/canvas_seed.py::_apply_positions` | 种子图初始坐标（按 kind 分列，列内按出现顺序） |

| 前端 | `frontend/src/domain/canvas-layout-tier.ts` | 证据强度三带（`layoutByTier`、`tierOf`） |

### 1.2 分层规则（两处需保持同口径）

```ts
export const RANK_X: Record<NodeKind, number> = {
  rule: 0,
  fact: 260, verify_item: 260,
  object: 480, evidence: 480, hypothesis: 480, note: 480, function_result: 480,
  source_row: 720,
  source_file: 960,
}
```

**列内排序规则**（`canvas-layout.ts`）：

```ts
.sort((a, b) =>
  a.y - b.y ||
  (degrees.get(b.id) ?? 0) - (degrees.get(a.id) ?? 0) ||
  (a.id < b.id ? -1 : a.id > b.id ? 1 : 0))
```

### 1.3 对照 Sugiyama 三步

| 步骤 | 标准做法 | 本项目 | 评价 |
|---|---|---|---|
| ① 层级分配 | 按拓扑最长路径分层 | **按 `kind` 硬编码** | 🟡 见 §1.4 |
| ② **交叉最小化** | barycenter / median 迭代 | ❌ **无** | 🔴 主要缺陷 |
| ③ 坐标分配 | priority method / Brandes-Köpf | 简单落槽 `idx * GAP` | 🟡 可接受 |

### 1.4 层级分配的两个问题

**问题 A：层级不由拓扑决定**

`object`(480) 与 `evidence`(480) 被强行同列，但 evidence 在语义上可能是 object 的下游。按 `kind` 分列会把真实的语义层级拉平。

**问题 B：列内排序是启发式而非算法**

`(y, 度数, id)` 只保证「不重叠 + 可复现」，**没有做任何交叉优化**。跨列长边（`rule → source_row`、`fact → source_file`）必然大量交叉。

### 1.5 🔴 G6 v5 布局能力未使用

```
package.json: "@antv/g6": "^5.1.1"
```

G6 v5 内置：`dagre` / `antv-dagre` / `force` / `d3-force` / `radial` / `concentric` / `circular` / `comboCombined` / `mds` / `fruchterman` / `grid` / `fishbone`。

**项目全部手工实现**——动机正确（确定性、纯函数、可单测、与 server 同口径），但**代价是没有交叉最小化**。

> 📌 这是本项目第 N 次出现「有能力未使用」：列画像（`samples`/`null_rate`）、`geo.py`、`china.json`、G6 布局——同一个模式。

## 2. 实测：barycenter 的收益

### 2.1 实测方法

纯 Python 复刻 `canvas-layout.ts` 分层规则，构造典型种子图（`rule → N fact → M source_row → source_file`，fact 与 source_row 之间随机命中边），统计跨列长边交叉数。

运行：

```bash
python3 barycenter_poc.py
```

### 2.2 结果

| 场景 | 现状 | barycenter | 下降 |
|---|---|---|---|
| 小图 4事实/5行 | 12 | 2 | **-83%** |
| 中图 8事实/10行 | 52 | 15 | **-71%** |
| 中图 8事实/12行 | 46 | 11 | **-76%** |
| 大图 12事实/16行 | 165 | 33 | **-80%** |
| 大图 15事实/20行 | 198 | 46 | **-77%** |
| **合计** | **473** | **107** | **-77%** |

### 2.3 收敛性与确定性

```
确定性校验（同输入两次一致）：True

迭代  1 轮 → 交叉 16
迭代  2 轮 → 交叉 15   ← 已收敛
迭代  4 轮 → 交叉 15
迭代  8 轮 → 交叉 15
迭代 16 轮 → 交叉 15
```

**关键结论**：

- **2 轮即收敛** → 实装时 `iterations=4` 足够（留安全余量）
- **同输入必同输出** → 确定性成立，可进快照测试
- **1 轮就拿到 15/16 的收益** → 即便性能敏感也能降级到 1 轮

## 3. P0 实施方案：barycenter 交叉最小化

### 3.1 算法

对每一列，按「相邻列中邻居节点的位序中位数」重排本列，双向扫描若干轮。

```
输入：nodes, edges, 初始位序（沿用现有 (y, 度数, id) 规则，保证同起点）
重复 iterations 轮：
    交替方向（奇数轮正向、偶数轮反向）扫描各列：
        对列内每个节点 n：
            neigh = 邻居中「不在本列」者的当前位序集合
            key   = median(neigh) 若非空，否则取 n 当前位序
            按 (key, 当前位序, id) 升序重排本列
        更新 rank_of
输出：(x, 槽位 * GAP)
```

### 3.2 为什么用中位数而非均值

| | 均值 barycenter | 中位数 median |
|---|---|---|
| 离群邻居 | 被拉偏 | 稳健 |
| 实测 | — | 收敛更快 |

本项目实测采用**中位数**，与 Geng & Wismath 的 median heuristic 一致。

### 3.3 TypeScript 参考实现（拟新增 `canvas-layout-cross.ts`）

```ts
// 画布分层布局交叉最小化（Sugiyama 第②步）。
// 纯函数、确定性：同输入必同输出，可进快照测试。
import type { CanvasEdge, CanvasNode } from './canvas'
import { RANK_X, RANK_Y_GAP } from './canvas-layout'

const DEFAULT_ITERATIONS = 4

function median(values: number[]): number | null {
  if (values.length === 0) return null
  const s = [...values].sort((a, b) => a - b)
  const mid = s.length >> 1
  return s.length % 2 ? s[mid] : (s[mid - 1] + s[mid]) / 2
}

/**
 * 最小化跨列长边交叉：按邻居位序中位数双向迭代重排各列。
 *
 * @returns 节点 id → 列内位序（0 基）
 */
export function minimizeCrossings(
  nodes: readonly CanvasNode[],
  edges: readonly CanvasEdge[],
  iterations = DEFAULT_ITERATIONS,
): Map<string, number> {
  const kind = new Map(nodes.map((n) => [n.id, n.kind]))
  const adj = new Map<string, Set<string>>()
  for (const e of edges) {
    if (!adj.has(e.source)) adj.set(e.source, new Set())
    if (!adj.has(e.target)) adj.set(e.target, new Set())
    adj.get(e.source)!.add(e.target)
    adj.get(e.target)!.add(e.source)
  }

  const columns = new Map<number, string[]>()
  for (const n of nodes) {
    const x = RANK_X[n.kind]
    if (!columns.has(x)) columns.set(x, [])
    columns.get(x)!.push(n.id)
  }
  const xs = [...columns.keys()].sort((a, b) => a - b)

  // 初始位序沿用现有确定性规则，保证与现状同起点
  const deg = new Map<string, number>()
  for (const e of edges) {
    deg.set(e.source, (deg.get(e.source) ?? 0) + 1)
    deg.set(e.target, (deg.get(e.target) ?? 0) + 1)
  }
  const yOf = new Map(nodes.map((n) => [n.id, n.y]))
  const rank = new Map<string, number>()
  for (const x of xs) {
    columns.get(x)!
      .slice()
      .sort((a, b) =>
        (yOf.get(a)! - yOf.get(b)!) ||
        ((deg.get(b) ?? 0) - (deg.get(a) ?? 0)) ||
        (a < b ? -1 : a > b ? 1 : 0))
      .forEach((id, i) => rank.set(id, i))
    columns.set(x, [...columns.get(x)!]
      .sort((a, b) => rank.get(a)! - rank.get(b)!))
  }

  for (let it = 0; it < iterations; it++) {
    const dir = it % 2 === 0 ? xs : [...xs].reverse()
    for (const x of dir) {
      const ids = columns.get(x)!
      const scored = ids.map((id, i) => {
        const neigh: number[] = []
        for (const m of adj.get(id) ?? []) {
          if (RANK_X[kind.get(m)!] !== x && rank.has(m)) neigh.push(rank.get(m)!)
        }
        const m = median(neigh)
        return { id, key: m ?? i, i }
      })
      scored.sort((a, b) => a.key - b.key || a.i - b.i || (a.id < b.id ? -1 : 1))
      const next = scored.map((s) => s.id)
      next.forEach((id, i) => rank.set(id, i))
      columns.set(x, next)
    }
  }
  return rank
}
```

修改 `canvas-layout.ts::layoutNodes`，把列内排序替换为：

const rank = minimizeCrossings(nodes, edges)

## 4. 架构边界：重排 vs 重投影

这是回答「还能加什么视图」的关键区分。

| | 重排（Reorder） | 重投影（Reproject） |
|---|---|---|
| 定义 | 同一数据、同一投影，**只改 y** | 不同聚合方式、不同边语义 |
| 现有 | `process` / `tier` | 无 |
| 能否用 `perspective` 实现 | ✅ | ❌ |
| 例子 | 证据强度三带 | Sankey（边=金额流量）、时序（轴=时间）、关系网络（节点=实体） |

### 4.1 「换轴不换位」是好设计，别丢

`canvas-layout-tier.ts` 注释明写：

> 横向仍按 RANK_X 分列（与流程视角同口径，便于在两种视角间「换轴不换位」）

`tier` 只改 y、不改 x——用户切换时节点仍在同一列，**不会迷失**。这个纪律必须保住。

### 4.2 所以：别再加 perspective

process 覆盖「结构」，tier 覆盖「置信」。**再加第三种重排收益递减**，还会加重「我该看哪个」的负担（与三组件职责重叠同源）。

**要补的是重投影——它们是数据的不同视图，不是同一张图的重排。**

## 5. 布局适用性矩阵（技术维度）

| 布局 | 图类 | 适配 | 判断 | 成本 |
|---|---|---|---|---|
| **分层 DAG** | 流程图 | ✅ 主视图 | 需补 §3 交叉最小化 | 0.3 |
| **同心圆 concentric** | 知识图谱 | ✅ | **expand 反向四层溯源天然径向**（以我为中心逐层外扩） | 0.5 |
| **时序泳道** | 时序图 | ✅ | 横轴时间、每主体一条泳道 | 1–2 |
| **Sankey** | 流量图 | 🟡 | 资金流专用，需金额字段 | 1–2 |
| **Combo 分组** | 架构图 | 🟡 | 按数据源归组，节点多时必卡 | 0.5 |
| **力导向 force** | 知识图谱 | ❌ | **破坏确定性，否决** | — |
| **矩阵 / 热力图** | 关系图 | ❌ | 丢失拓扑，不适合因果链 | — |

### 5.1 力导向为何否决

画布是**取证/研判**场景，用户需要「上次看到的位置这次还在」。力导向每次打开位置可能不同，且 `n-body` 计算在节点多时不可控。这与 `canvas_seed.py` 「排序方便单测/快照比对」的确定性纪律直接冲突。

### 5.2 同心圆为何适配 expand

`canvas_expand.py`（782 行）实现的是**反向四层溯源**：`fact → object → source_row → source_file`。这在语义上就是「以我为中心，逐层向外」——**正是同心圆的语义**。

当前用同一套分层布局表达，导致展开后节点散在五列里，看不出「层级外扩」的关系。

## 6. 业务维度：七类认知任务覆盖

| 侦查员的疑问 | 应有视图 | 现状 |
|---|---|---|
| 这条线索凭什么成立 | 证据链 DAG | ✅ `process` |
| 我信几分 | tier 三带 | ✅ `tier` |
| **钱怎么流的** | Sankey | ❌ |
| **谁和谁有关系** | 关系网络 | ❌ |
| **什么时候发生的** | 时序泳道 | ❌ |
| 还缺什么证据 | 清单（非图） | ❌ |
| **多条线索怎么碰撞** | 跨线索视图 | ❌ |

### 6.1 最值得注意的空白：多线索碰撞

当前画布是**单线索证据链**。而研判真正的难点是**多线索交叉碰撞**——比如：

- 线索 A 和线索 B 指向同一个中间人
- 两条线索的资金流在同一时间点交汇

这是**知识图谱的强项**，也是目前完全空白的。

> 📌 但这也是最大的架构决策——跨线索视图要重新定义「种子」和「溯源」，成本远超其他项。建议单独立项，不并入本方案。

### 6.2 数据基础已具备

时序泳道所需字段已存在：`transaction.date`、`call.date`、`case_ledger.case_date`，且 `resolve_source_row` 能取到行内容（已过遮蔽）。
