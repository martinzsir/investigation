## 一、需求背景

M1~M4 交付了案件生命周期、治理仪表盘、研判主流程闭环、配置与人审四块能力后，平台仍缺三项**高级能力**：
- **跨案件查询**：多案件串并分析只能手工逐库查，无统一 ATTACH 通道，且需严格控制权限与审计；
- **案件包导入导出**：案件移交无标准化打包格式，缺 SHA-256 完整性校验与审计链冻结；
- **代码逃生舱**：四类本体扩展（Function/值类型/清洗规则/副作用）无代码桩生成器，开发者需手工查阅注册点。

M5 目标：以 **core 零改动**落地五项需求——跨案件 ATTACH READ_ONLY + 全有或全无鉴权（W-026/027）、案件包导出导入（W-028/029）、四类代码桩生成（W-031）。核心约束：全部实现集中在 `server/` 目录，复用 `PackManager.init_pack`、`AuditChain`、`FUNCTION_IMPLS`/`TYPE_SQL`/`ALLOWED_SIDE_EFFECTS` 既有接口；不引入新依赖（hashlib/json/shutil/zipfile 均标准库）。

## 二、方案设计（七个决策点）

| 决策 | 推荐项 | 落地位置 |
|---|---|---|
| D-M5-1 CrossCaseStore 实现位置 | 独立 `backend_cross.py`（backend_api.md 目录结构明示） | `server/app/store/backend_cross.py` |
| D-M5-2 ATTACH 连接缓存键 | 按 `frozenset(case_ids)`（无序集合，同组不同序复用） | `backend_cross.py` `_conn_cache` OrderedDict LRU |
| D-M5-3 禁 DDL/DML 实现 | SQL 首词白名单 + READ_ONLY 双保险 | `backend_cross.py` `_assert_readonly_sql` |
| D-M5-4 导出压实策略 | 导出前内联压实副本（不碰原文件，不改案件状态） | `worker/package.py` `handle_export` |
| D-M5-5 导入后 pack_id | `pack_id = new_cid`（案件级隔离，与 M3/M4 快照一致） | `worker/package.py` `handle_import_package` |
| D-M5-6 逃生舱产物形态 | 返回代码桩文本 `{files, registration_points}`，不写文件 | `worker/escape_hatch.py` `generate_stub` |
| D-M5-7 跨案件 PolicyEngine | 跨案件 SQL 通道不做行级遮蔽，依赖全有或全无授权 + 审计 | `routers/cross_case.py` `_authorize_all` |

### 关键调用链

```

POST /cross-case/query
  → _authorize_all(case_ids, principal, ctx)  # 全有或全无，ATTACH 前
      → 逐案 ctx.cases.get_case(cid) 校验 tenant_id

      → PRAGMA timeout
      → SELECT * FROM ({sql}) LIMIT {max_rows}
  → record_ops("cross_case_query", {case_ids, sql, reason, result_rows})
  → store.close()  # 归还缓存，不关闭

案件包导出（Worker）：

  → 导出 audit/chain.csv
  → 逐文件 SHA-256 → manifest.json（case_knowledge 标 sensitive）
  → README.md（验证命令 + 复现命令）
  → zip 打包 → 清理工作目录

案件包导入（Worker）：

  → 解压 zip 到临时目录
  → verify_package(work)  # 7 步校验
      → format → SHA-256 逐文件比对 → 13 声明齐全
      → schema_version=2 一致 → root_hash 校验 → DuckDB 只读打开

  → PackManager.init_pack(new_cid, from_pack=new_cid)  # 复用

代码逃生舱：

  → generate_stub(ext_type, name, description)
      → 四类模板分派：function/value_type/clean_rule/side_effect

      → 不写文件、不注册、不执行
```

## 四、关键实现要点

### 1. CrossCaseStore ATTACH READ_ONLY（W-026，D-M5-1/2/3）

ATTACH 逻辑独立到 [backend_cross.py](file:///d:/dev/inves_duckdb/server/app/store/backend_cross.py)，与单案件 CaseStore 分离（门禁更清晰）。连接按 `frozenset(authorized_cases)` 缓存复用（AC-7），LRU 上限 16 防组合爆炸耗尽资源。禁 DDL/DML 采用双保险：ATTACH 的库均 `READ_ONLY`（DuckDB 层面禁写）+ SQL 首词白名单（`SELECT`/`WITH`/`PRAGMA`，防对主内存连接写临时表）。`max_rows` 通过子查询包裹强制 `LIMIT`（DuckDB 多个 LIMIT 取最后一个，子查询包裹更安全）。

### 2. 全有或全无鉴权（W-027，D-M5-7）

`_authorize_all` 遍历 `case_ids` 逐一校验 `tenant_id` 归属，任一失败即整体 403。**拒绝发生在 ATTACH 之前**——不调用 `factory.for_cross_case`（测试用 mock spy 验证 `for_cross_case` 未被调用）。拒绝事件落 `ops_events`（`cross_case_denied` kind，含被拒案件列表）。

跨案件 SQL 通道不做行级/字段级遮蔽（PolicyEngine 在跨库 JOIN 场景下难以统一应用），依赖全有或全无授权 + 审计控制。单案件查询仍走 PolicyEngine，跨案件通道是特权操作。

### 3. 案件包导出（W-028，D-M5-4）

版本压实仅作用于导出副本——先 `shutil.copytree` 复制到 `exports/{task_id}/` 临时目录，再在副本中只复制 `v{cur}.duckdb`（旧版本文件不进入导出包）。**不碰原案件文件**，导出失败不丢失旧版本。审计链冻结校验调 `AuditChain.readonly(st.conn, case_id, backend="sqlite").chain_integrity()`，`chain_ok=false` 时标记告警但继续导出（AC-6 橙色告警放行）。`case_knowledge.json` 在 manifest 中标 `sensitive: true`（AC-5）。README 含验证命令与复现命令（AC-7）。

### 4. 案件包校验（W-029，7 步）

`verify_package` 七步校验：①目录结构与 manifest.json 存在 → ②逐文件 SHA-256 比对 manifest → ③13 声明文件齐全 → ④`schema_version=2` 一致 → ⑤审计链 `root_hash` 校验 → ⑥DuckDB 只读打开。篡改一字节即 SHA-256 不匹配；缺声明文件即失败；schema_version 不一致即失败。DuckDB 只读连接收敛到 `store.backend.open_readonly_conn`（避免 worker 层直连 DuckDB 触发门禁）。

### 5. 案件包导入（W-029，D-M5-5/6）

导入流程：解压 → `verify_package` → 复制 ontology 快照 + DuckDB 到新案件目录 → `PackManager.init_pack(new_cid, from_pack=new_cid)` 复用（AC-6）→ `repo.create_case` + `repo.set_version` 登记新案件。导入后可通过 `StoreFactory.for_case(new_cid, mode="read")` 查询数据（AC-7 导入后可查询）。`pack_id = new_cid`（案件级隔离，与 M3/M4 快照一致）。

### 6. 代码逃生舱（W-031，D-M5-6）

`generate_stub(ext_type, name, description)` 四类模板：
- **function**：生成 `core/functions/{name}.py` 桩（`@register_function` + 签名 + TODO + 输入输出契约）+ 测试骨架（`self.fail("TODO: implement")`）+ 注册点说明（`FUNCTION_IMPLS` + `functions.json` 声明）；
- **value_type**：生成 `TYPE_SQL` 追加示例 + loader 校验点 + 测试骨架；
- **clean_rule**：生成 `core/functions/{name}_clean.py` 桩 + 注册点（`bindings.json` clean 字段）；
- **side_effect**：生成 `ALLOWED_SIDE_EFFECTS` 追加说明 + `actions.json` 声明模板 + `action_executor.py` 分支处理。

**不写文件、不注册 core**（测试断言 `FUNCTION_IMPLS.keys()` 在生成前后不变）。仅返回 `{files: [{path, content}], registration_points: [...]}`，由开发者手动合入（req.md 明确"不做租户沙箱在线执行"）。

## 六、踩坑记录

1. **Pydantic `min_length=2` 约束**：`CrossCaseQueryIn.case_ids` 设 `min_length=2`（跨案件至少两案），单案件查询测试用 `["c1"]` 会 422。修复：测试改用 `["c1", "c2"]`。
2. **CaseRecord 字段名**：M3/M4 后 `CaseRecord` 用 `pack_snapshot_at` 非 `snapshot_version`。导入 handler 初始用了旧字段名。修复：改为 `pack_snapshot_at`。
3. **篡改测试目标文件选择**：篡改 `manifest.json` 会触发 JSON 解析错误而非 SHA-256 不匹配（manifest 自身的 SHA-256 不在 manifest 内）。修复：篡改 `objects.json`（声明文件），触发 SHA-256 比对失败 + JSON 格式错误双重报错。
4. **store 门禁捕获 worker 层直连 DuckDB**：`package.py` 的 `duckdb.connect(str(db), read_only=True)` 触发 `tests/test_store_backend.py` 门禁（非 store 模块不得直连 DuckDB）。修复：在 `store/backend.py` 新增 `open_readonly_conn` 辅助函数，package.py 改用它。
5. **M1 骨架测试过时**：`test_store_backend.py` 的 `TestCrossCaseSkeleton` 断言 CrossCaseStore 全方法抛 `UnsupportedOperation`（M1 骨架行为）。M5 实现后需更新为 ATTACH READ_ONLY + 只读查询 + 禁 DDL/DML 行为。
6. **AuditChain.readonly 需 StateStore**：导出/校验中读审计链需先构造 `StateStore` 获取连接，再传给 `AuditChain.readonly(st.conn, case_id, backend="sqlite")`。
7. **导出工作目录清理时机**：`handle_export` 在 zip 打包后清理工作目录，但若 zip 打包失败工作目录残留。用 `ignore_errors=True` 确保不阻塞。

## 八、遗留与后续

- **W-026 GB 级大规模未验证**：req.md 标记为未验证项，M5 仅做小规模 AC 覆盖（spike H5-H7 的 50 库×1000 行）。GB 级性能留后续专项验证。
- **跨案件 PolicyEngine 行级遮蔽**：跨案件 SQL 通道不做行级/字段级遮蔽（D-M5-7）。若后续要求字段级遮蔽，需在 query 结果后追加 PolicyEngine 逐行处理（性能代价大）。
- **ATTACH 连接缓存内存压力**：最坏情况组合数爆炸。M5 MVP 缓存上限 16（LRU 淘汰），超限时关闭最久未用连接。后续可引入 TTL 过期策略。
- **案件包导出的版本压实副作用**：当前采用"先复制到临时导出目录再压实"策略（不碰原案件文件）。若后续要求导出前清理原案件旧版本，需单独的封存流程触发。
- **W-031 代码桩模板时效性**：模板基于 M4 交付时的 core 现状。若 `FUNCTION_IMPLS` 注册方式或 `TYPE_SQL` 字典变更，需同步更新模板。
- **前端页面**：M5 仅交付后端端点，前端跨案件查询界面、案件包上传/下载 UI、逃生舱生成器 UI 待后续。
- **Postgres 元数据后端**：M5 跨案件审计事件仍落 SQLite `ops_events`，生产环境切换 Postgres 后需适配。
