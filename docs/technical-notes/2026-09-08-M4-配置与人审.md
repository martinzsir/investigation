## 一、需求背景

M3 交付了研判主流程闭环（数据接入→语义构建→线索检测→线索读面→处置→审计→规则迭代）后，平台仍缺**配置与人审**两块能力：
- 模型/权限/知识/视图只能手改 `ontology/<pack>/*.json`，无 Web 写面；
- 脏数据诊断（缺列/脏值降级）无聚合入口，异常线索无独立通道；
- 组织实体对齐中 `needs_review` 弱证据候选（前缀包含等）无人工裁决通道，只能等下次 BUILD 重算。

M4 目标：以**案件快照级配置写**（复用 M3 rule_workshop 临时副本 + load_pack 校验 + os.replace 范式）补齐四类配置端点，以**只读聚合**补齐异常通道与数据治理，以**最小 core 触点**（仅 W-021 追加实体合并/驳回纯函数）落地人审裁决。核心约束：**server 外最小影响**——七项中六项 core 能力已就绪可纯 Web 实现；写操作唯一入口经 Worker + StateSink，不产 DuckDB 版本。

## 二、方案设计（四个决策点）

| 决策 | 推荐项 | 落地位置 |
|---|---|---|
| D-M4-1 配置写粒度 | 案件快照级 `cases/{cid}/ontology/default/*.json`（非共享包级） | `snapshot_config.py` `save_config_json` |
| D-M4-2 W-021 裁决通道 | 单独 `TASK_REVIEW` 任务落 `state.review_decision`（非复用 DISPOSE 线索板） | `worker/review.py` `handle_review` |
| D-M4-3 合并语义 | 软合并：`merge_entities` 仅改内存 resolver 状态（标 `needs_review=False`、`confidence=1.0`），裁决落 state | `core/entity.py` `merge_entities` |
| D-M4-4 W-011 治理页 | 新建轻量只读聚合端点（从 `run_diagnostic` detail 提取 object/property） | `routers/data_governance.py` |

核心约束：core/ 仅 W-021 追加纯函数（不改解析逻辑）；配置写一律「临时副本 → load_pack 校验 → os.replace 原子落盘」；实体裁决经 Worker 走 `state.review_decision` + 审计链，不产版本；AC-5 红线：系统任何模式下不自动合并 `needs_review` 候选。

### 关键调用链

```
配置写（以 objects 为例）：
PUT /cases/{cid}/objects
  → snapshot_config.save_config_json
      → shutil.copytree(snap_dir, tmp_root/default)
      → atomic_write_json(tmp/objects.json, data)
      → load_pack("default", base_dir=tmp_root) 全量校验
      → 校验通过 → atomic_write_json(real_path, data) 原子落盘
      → 校验失败 → 400（临时副本丢弃，不污染快照）

异常通道：
GET /cases/{cid}/anomalies
  → _AllRowsHealth(伪 health，直接 SELECT run_diagnostic 全表)
      （避开 RunHealth.__init__ 的 DDL——只读版本库不可 CREATE）
  → emit_anomaly_clues(health, record=False)
  → 表不存在返回空列表

数据治理：
GET /cases/{cid}/governance/missing-columns
  → dashboard.list_diagnostics(kind in {source_column_missing, source_value_cast_failed})
  → 从 detail JSON 提取 object/property 聚合

实体裁决：
GET  /cases/{cid}/review/queue
  → build_org_table_from_duckdb(obj_org) → OrganizationResolver
  → review_candidates() 过滤已裁决（state.review_decision target_id）
POST /cases/{cid}/review/{rid}/decision 🔒
  → enqueue TASK_REVIEW(action=review_merge|review_reject, candidate_id, reason, operator)
  → worker/review.handle_review
      → 构建 resolver → merge_entities|reject_review（纯函数）
      → state.review_decision INSERT + audit_append（不产版本）
```

## 四、关键实现要点

### 1. 配置写范式复用（D-M4-1）
`snapshot_config.save_config_json` 统一封装 M3 rule_workshop 验证过的写盘范式：`shutil.copytree` 快照到临时目录 → 写目标 JSON → `load_pack` 全量 loader 校验（值类型/kind/pk/name_property/链接端点引用/动作副作用）→ 校验通过 `os.replace` 原子落盘，失败抛 400 不污染。`require_analyst` 要求偏将及以上（role in {human, system} 或 clearance>=2）。

### 2. 模型设计器（W-013）
值类型白名单用 `set(TYPE_NAMES)`（9 种，与 core TYPE_SQL REQ-041 口径一致，非 AC 描述的 5 种）；kind 仅 entity/event；间类五间（生间/反间/因间/死间/内间）；链接端点引用已声明对象。新对象/链接需同步补 binding（loader 硬失败）。

### 3. 权限与字段遮蔽（W-015）
`mask` 白名单 {partial, full, none}。**偏差**：`load_pack` 不校验 object_policies 覆盖率——fail-closed 是运行时 `PolicyEngine.check_object` 行为（漏策略运行时拒），非装载期。测试以 `PolicyEngine(path=...).check_object(ctx,"person")` 断言 raise 验证。

### 4. 角色视图（W-017）
Object Views 按角色投影（flat 视图声明 + 装载校验），查询时派生不物化。引用列校验含 `pk`（代理键也是视图可引用列）。

### 5. 异常通道（W-022）
`RunHealth` 实例化会执行 DDL（CREATE TABLE run_diagnostic），在只读版本库连接上失败。采用 `_AllRowsHealth` 伪 health 直接 `SELECT * FROM run_diagnostic`，表不存在时捕获异常返回空。调 `emit_anomaly_clues(health, record=False)` 不写诊断。

### 6. 数据治理（W-011）
`run_diagnostic.detail` 是 JSON 列，`object`/`property` 在 detail 内（非顶层列）。聚合从 `it["detail"].get("object")` 提取。

### 7. 实体裁决（W-021，D-M4-2/3）
- **不走 DisposalBoard**：实体裁决与线索状态机无关，单独 `TASK_REVIEW`，落 `state.review_decision`（kind=`entity_review`）。actions.json 的 `review_merge`/`review_reject` 为声明式文档（`target_status=待查` 占位，不实际迁移线索状态）。
- **纯函数**：`merge_entities`/`reject_review` 只修改内存 resolver 的 `needs_review`/`confidence`/`merge_reason`，返回裁决记录供 Worker 持久化；不修改 `obj_*` 语义表。
- **AC-5 红线**：`review_candidates()` 只在 BUILD 时由 resolver 产出前缀包含弱证据候选；系统永不自动合并——只有人审触发的 `TASK_REVIEW` 才调 `merge_entities`。
- **AC-4 驳回不重复**：`reject_review` 标 `needs_review=False`，队列端点过滤已裁决 `target_id`，驳回/合并后候选不再出现。

## 六、踩坑记录

1. **loader 要求非 runtime 对象/链接有 binding**：PUT 新对象时 400「缺少 binding 声明」。测试用 `_add_object_binding`/`_add_link_binding` 补最小 binding 后再 PUT。
2. **视图引用 pk 列**：`person_directory` 视图引用 `person_id`(pk) 但校验只查 properties → 400。修复：`obj_props[base].add(o.get("pk"))`。
3. **import 返回 200 非 202**：import 端点同步返回 200（带 task 行），测试断言 202 失败，改为 200。
4. **RunHealth DDL 在只读连接失败**：`Cannot execute CREATE on read-only database`。anomaly 端点改用 `_AllRowsHealth` 直接 SELECT（record=False）。
5. **`record(detail={...})` 嵌套错误**：`record` 的 `**detail` 把 `detail={"subject":..}` 存成 `{"detail":{"subject":..}}`。修复：直接传 `subject="张三"` 等 kwargs。
6. **run_diagnostic 表不存在**：BUILD 未产诊断时表未建。`_AllRowsHealth.__init__` 捕获异常返回空列表。
7. **诊断 object/property 在 detail 内**：data_governance 从 `it.get("object")` 取不到。修复：从 `detail` dict 提取。
8. **accessconfig fail-closed 非装载期**：删 person 策略后 load_pack 不拒绝。测试改为保存缺策略后 `PolicyEngine.check_object` 断言 raise。
9. **views.py TYPE_NAMES 9 种非 5 种**：REQ-W-013 AC-2 说 5 种但 core TYPE_SQL 已扩展 9 种。用 `set(TYPE_NAMES)` 与 loader 口径一致。
10. **actions.json 要求 target_status + ALLOWED_SIDE_EFFECTS**：新增 review 动作缺 `target_status` 且 `merge_entity`/`dismiss_review` 未在白名单 → loader 硬失败。修复：`target_status=待查` 占位 + ALLOWED_SIDE_EFFECTS 追加两项。
11. **import column_map 方向**：`column_map` 是「CSV 列 → 声明表列」，当 CSV 列名已匹配声明列时不传（否则 400「映射目标不在声明列内」）。
12. **实体候选触发 needs_review 的数据构造**：共享法人会被强合并（`_share_strong_org`）；"第一项目部""有限公司"等是可剥后缀会归一到同一 core。需用「法人不同 + 核心字号前缀关系且非可剥后缀」（如 `宏业建设` / `宏业建设集团`）触发 needs_review。
