# 数据接入与治理需求清单

**编号**：`REQ-D-XXX`（D = Data）。与 REQ-001\~027（功能）、REQ-G-001\~025（治理）、REQ-W-001\~031（Web 平台）编号空间独立。编号一经分配即固定。

**独立性定义**：每条满足三点——① 可独立交付，单独完成即产生价值；② 可独立测试，不依赖其他需求产物即可验证；③ 可独立验收，通过与否是可执行断言而非主观判断。

**贯穿约束**：**映射层严格 1:1**（一源列 → 一属性）。任何形式的列拆分不在 ETL 声明层实现。

# A. 数据元标准层

## REQ-D-001　数据元标准注册

**优先级** P0 ｜ **硬依赖** REQ-D-004（clean_rule 交叉引用需 op 注册表先行）

**业务目标**：项目现在只有"类型"一个维度（`{"raw_name": "string"}`），无法回答"这个值该长什么样"。电诈的假身份证、空号、异常金额在统计上完全正常，统计型检查全看不出来。建立规范层是补这个缺口的唯一途径。

**方案**：新增第 14 个声明文件 `data_elements.json`，注册数据元（类型、长度、格式、值域、敏感度、推荐清洗规则）。

```json
{
  "schema_version": 2,
  "elements": {
    "DE_IDCARD": {
      "name": "公民身份号码", "type": "string", "length": 18,
      "format": "^[1-9]\\d{5}(19|20)\\d{2}(0[1-9]|1[0-2])(0[1-9]|[12]\\d|3[01])\\d{3}[\\dXx]$",
      "checksum": "idcard_mod11",
      "sensitive": true, "mask": "partial",
      "clean_rule": "normalize_idcard"
    }
  }
}
```

**验收标准**：

- AC-1 断言 `data_elements.json` 通过 loader 强校验，字段缺失硬失败
- AC-2 断言未知 `checksum` 算法名硬失败（fail-closed 不放宽）
- AC-3 断言 `schema_version` 与其余 13 个声明文件一致
- AC-4 断言数据元可被引用来定义属性，且属性继承类型与格式
- AC-5 断言数据元 ID 唯一，重复注册硬失败

**测试方式**：独立测试——写一个含 3 个数据元的 JSON，断言 loader 接受；删掉必填字段，断言拒绝。

**业务价值**：这是"值域合规检查"（REQ-D-016）和"自动推荐"（REQ-D-021）的共同前提。

## REQ-D-002　属性引用数据元

**优先级** P0 ｜ **硬依赖** REQ-D-001

**业务目标**：避免同一约束在多处重复声明（类型、格式、清洗、遮蔽各写一遍），一处定义多处生效。

**方案**：`objects.json` 属性从 `"id_card": "string"` 扩展为可引用：

```json
"id_card": {"data_element": "DE_IDCARD"}
```

loader 自动继承：类型、格式、清洗规则、遮蔽策略。

**验收标准**：

- AC-1 断言属性引用数据元后，类型自动继承（无需重复声明）
- AC-2 断言属性本地声明与数据元冲突时硬失败（不静默覆盖）
- AC-3 断言清洗规则自动挂接，无需在 binding 中重复
- AC-4 断言敏感标记自动进入 `property_policies` 候选
- AC-5 断言未引用数据元的属性行为与现状完全一致（向后兼容）
- AC-6 断言引用不存在的数据元 ID 硬失败

**测试方式**：独立测试——同一属性分别用"直接声明"和"引用数据元"两种方式定义，断言编译产物等价。

**业务价值**：AC-2 很关键——本地与标准冲突时必须是硬失败，不能让本地悄悄覆盖标准，否则标准形同虚设。

## REQ-D-003　代码表接入

**优先级** P1 ｜ **硬依赖** REQ-D-001

**业务目标**：现有一处矛盾——`enum_space.json` 的 `_note` 写"主体名随案件包走"，但实际硬编码了 `["张卫国","李志强","A建材"]`。原因是**缺合法值域来源**，只好写 demo 数据。

**方案**：数据元承载代码表（性别、案件类别、行政区划、币种、证件类型），`enum_space` 从数据元的值域派生，不再手写具体人名。

**验收标准**：

- AC-1 断言代码表可从数据元值域派生
- AC-2 断言 `enum_space` 中不含任何具体人名/地名（可通过 `scan_hardcoded_names` 验证）
- AC-3 断言维度值为非法枚举时硬失败
- AC-4 断言案件级可追加自定义枚举值，但不覆盖标准值
- AC-5 断言代码表变更不影响已锁定 pack 快照的案件

**测试方式**：独立测试——接入含代码表的数据元，断言 enum\_space 派生结果不含硬编码人名。

**业务价值**：AC-2 可直接复用现有的 REQ-024 扫描脚本验证，不需要新工具。

# B. 清洗配置化

## REQ-D-004　清洗规则注册表

**优先级** P0 ｜ **硬依赖** 无

**业务目标**：`CLEAN_RULE_NAMES = {"strip","exclude_org_tokens"}` 是硬编码 set，加规则必须改 Python。电诈需要的规则（手机号/身份证/卡号归一化）远超两条。

**方案**：改为注册表模式，声明式规则与代码规则统一注册。`CLEAN_RULE_NAMES` 保留为**动态集合**（现有两处引用不用改），但内容来自注册表而非硬编码。

**验收标准**：

- AC-1 断言新规则注册后，`CLEAN_RULE_NAMES` 自动包含它
- AC-2 断言重复注册同名规则硬失败
- AC-3 断言 loader 校验未知清洗规则仍硬失败（fail-closed 不放宽）
- AC-4 断言现有 `strip` 与 `exclude_org_tokens` 行为不变（回归）
- AC-5 断言 `draft_assembler` 的 `clean_available` 自动列出全部规则

**测试方式**：独立测试——注册一条新规则，断言出现在 `CLEAN_RULE_NAMES` 且可被 binding 引用。

**业务价值**：这是把清洗从"改代码"变成"改配置"的开关。

***

## REQ-D-005　属性级清洗作用域

**优先级** P0 ｜ **硬依赖** REQ-D-004

**业务目标**：现有两处硬限制——`if otype.name != "person": return rows`（只对 person 生效）、`r[0]`（只处理名称列）。**结果是卡号、手机号、身份证的脏数据原样入库**，而这三类恰恰是电诈最关键的关联键。

**方案**：binding 的 `clean` 从数组扩展为属性级映射，`_name` 作为名称列的约定别名。

```json
"clean": {
  "_name":     ["strip", "strip_alias"],
  "phone_raw": ["normalize_phone"],
  "id_card":   ["normalize_idcard"]
}
```

数组形式保持兼容（等价于 `{"_name": [...]}`）。

**验收标准**：

- AC-1 断言非 person 对象（如 transaction）的属性可被清洗
- AC-2 断言非名称列（如 phone\_raw）可被清洗
- AC-3 断言数组形式 binding 行为与现状一致（向后兼容）
- AC-4 断言属性级规则按声明顺序执行（顺序敏感）
- AC-5 断言清洗只作用于已声明的属性，未声明属性不被改动

**测试方式**：独立测试——给 transaction 的 card\_no 挂清洗规则，断言生效；此前它会被跳过。

**业务价值**：解除这两条限制，卡号/手机号/身份证的归一才有可能。

***

## REQ-D-006　声明式清洗规则

**优先级** P1 ｜ **硬依赖** REQ-D-004、REQ-D-005

**业务目标**：实测 17 类电诈脏格式中 15 类可用正则/有序步骤解决，不需要写代码。

**方案**：内置四种原子 op——`regex`（替换）、`strip_cc`（剥国家码）、`pad_date`（补零）、`reject_if`（条件拒绝）。

与 REQ-D-011 的原子 op 注册进**同一 op 注册表**（REQ-D-004），clean/transform 两层只是注入点不同。

**验收标准**（基于实跑数据）：

- AC-1 `138 0013 8000`、`+86 138-0013-8000` → `13800138000`
- AC-2 `6222-0212-3456-7890` → `6222021234567890`
- AC-3 `2024年3月15日`、`2024/3/15`、`2024.03.15` → `2024-03-15`
- AC-4 `李强（绰号小强）` → `李强`
- AC-5 `6222********7890` 触发 `reject_if` **而非静默通过**
- AC-6 断言规则按数组顺序执行（国家码需先剥前缀再去非数字）

**测试方式**：独立测试——17 条样例跑一遍，断言 15 条成功、2 条按预期失败。

**业务价值**：AC-5 特别重要——星号遮蔽的卡号通过任何规则都无法还原，必须显式拒绝而不是假装清洗成功。

**已知边界**：`0086` 国家码需有序多规则（单条正则不够）；科学计数法 `1.28e3` 需 L4 代码规则。

## REQ-D-007　词表参数外置

**优先级** P1 ｜ **硬依赖** REQ-D-004

**业务目标**：`ORG_KEYWORDS` 是硬编码 tuple，且是**贪腐词表**（公司/局/厂/中心）。换电诈场景要改代码。

**方案**：词表等参数外置到 `clean_rules.json`，案件级可覆盖。

**验收标准**：

- AC-1 断言词表修改后行为立即变化，无需改 Python
- AC-2 断言案件级词表可追加，不覆盖平台级（合并语义）
- AC-3 断言词表为空时该规则退化为 no-op 且不报错
- AC-4 断言词表非字符串数组时硬失败
- AC-5 断言电诈词表（科技公司/商贸/跑分）可替换贪腐词表

**测试方式**：独立测试——换一份词表，断言同一批数据的过滤结果不同。

**业务价值**：这是"换业务领域只改 JSON"的具体兑现。

## REQ-D-008　清洗留痕

**优先级** P0 ｜ **硬依赖** REQ-D-005

**业务目标**：现有 `exclude_org_tokens` 把行**静默丢弃**——用户看到的 `obj_person` 里" A建材"不存在，以为数据本来就这样。这与 R5 静默失效、审计链空链假通过是**同一病根**：系统做了事但不告诉你。

**方案**：清洗统计进 `stats["clean_stats"]`，含对象、属性、规则、剔除行数、脱敏样本；进健康度小节与数据画像页。

**验收标准**：

- AC-1 断言过滤规则执行后，剔除行数被准确记录
- AC-2 断言记录含规则名与作用属性（可定位）
- AC-3 断言样本经过脱敏，不含完整敏感值
- AC-4 断言剔除量超过阈值（如 30%）时升级为 warning
- AC-5 断言清洗统计进入健康度小节并可检索
- AC-6 断言数据画像页可展示每属性的清洗前后行数

**测试方式**：独立测试——构造 100 行数据让规则剔除 40 行，断言统计准确且触发阈值告警。

**业务价值**：清洗决定"哪些数据进了分析"。这一步不可见，后面所有结论的可信度都建立在黑箱上。

# C. ETL 转换（1:1 约束下）

## REQ-D-009　transform 层（脏值可用性抢救）

**优先级** P1 ｜ **硬依赖** 无

**业务目标**：实测 4 行电诈真实脏数据（VARCHAR 源列）→ B2-08 前 **3 行导致整批中断**；B2-08 已将 `ontology_loader.py` 的编译期硬编码 `CAST` 改为 `TRY_CAST` + 脏值计数（`core/run_health.py` record_build_dirty），**整批中断已消除**。遗留问题是脏值**静默降级 NULL、不可用**（实测 TRY_CAST 下 4 行里 2 行静默丢失）。本条重述为**脏值可用性抢救**：`48,000.00` → 可用的 `48000.00`，而非降级 NULL。

**方案**：在 SQL 投影内、`TRY_CAST` 之前注入 transform 层（声明式 op 编译为 `regexp_replace` 等表达式）。实际执行顺序是 **SQL 投影内 transform → TRY_CAST 先执行，Python 侧 clean 后执行**（`core/ontology.py` `_compute_object_rows`：先 fetch 已 CAST 行，再 `_apply_clean`，clean 仅作用于字符串列）：

```
SQL 投影内：源列 → transform（归一格式，新增）→ TRY_CAST（进列，B2-08 起）
Python 侧（SQL 之后）：fetch 已 CAST 行 → clean（仅字符串列：去空格/剥绰号）
```

**验收标准**：

- AC-1 断言 `48,000.00` 经 transform 后可 CAST 为 DOUBLE（此前 Conversion Error）
- AC-2 断言 `2024年3月15日` 经 transform 后可 CAST 为 DATE
- AC-3 断言 `￥1,280.50` 可 CAST 为 DOUBLE
- AC-4 断言 transform 与 clean 作用域分离，互不干扰
- AC-5 断言未声明 transform 的属性行为与现状一致（向后兼容）
- AC-6 断言 transform 规则为未知 op 时硬失败

**测试方式**：独立测试——用上述 3 条脏数据跑装载，断言不再中断。

**业务价值**：装载中断已被 B2-08 消除，但"脏值=NULL 不可用"仍在；transform 让脏值抢救为可用，是金额/日期类关联与聚合分析的前提。

## REQ-D-010　on\_cast\_error 三态

**优先级** P0 ｜ **硬依赖** REQ-D-009

**业务目标**：CAST 失败的历史结局是整批崩溃（B2-08 前硬 `CAST`）；现状 `TRY_CAST` 下**静默变 NULL**——实测 4 行里 2 行静默丢失，系统报告"一切正常"。静默同样不可接受。

**方案**：属性级声明 `on_cast_error`，三态：`null`（**默认**，保持 B2-08 已验收行为）/`quarantine`（属性级显式声明：脏行进隔离表 + 进健康度，其余正常装载）/`fail`（可回退的历史语义，非现状）。

**验收标准**：

- AC-1 断言 `quarantine` 模式下，脏行不阻断其余行装载
- AC-2 断言被隔离的行进入隔离表且**记录失败原因与样本值**
- AC-3 断言隔离数量进入健康度小节
- AC-4 断言 `fail` 模式行为与历史硬 CAST 一致（可回退的历史语义，而非现状默认）
- AC-5 断言 `null` 模式产生的 NULL 数量被统计（**不静默**）
- AC-6 断言未声明 `on_cast_error` 时默认 `null`（B2-08 已验收行为），`quarantine` 为属性级显式声明

**测试方式**：独立测试——4 行数据含 2 行脏值，断言 2 行正常装载、2 行被隔离且有记录。

**业务价值**：AC-5 是关键——即使选择静默模式，NULL 数量也必须被统计，不能真的无声无息。

**建议**：默认保持 `null`（不改动 B2-08 已验收语义），需要隔离留痕的属性显式声明 `quarantine`——隔离+留痕能让用户看到"这 200 行卡在金额列，样本是 `48,000.00`"，而不是无声无息。

## REQ-D-011　内置原子 op

**优先级** P1 ｜ **硬依赖** REQ-D-009

**业务目标**：覆盖常见格式归一，让绝大多数 1:1 转换零代码实现。

**方案**：内置 `regex`（字符替换）、`pad_date`（日期补零）、`to_upper`/`to_lower`、`reject_if`（条件拒绝）、`default`（空值默认值）。

与 REQ-D-006 的原子 op 注册进**同一 op 注册表**（REQ-D-004），clean/transform 两层只是注入点不同。

**验收标准**：

- AC-1 断言 6 类日期格式归一为 `YYYY-MM-DD`（实测 4/4 通过）
- AC-2 断言千分位与货币符号可被清除（实测 2/2 通过）
- AC-3 断言 `pad_date` 处理 `2024-3-5` → `2024-03-05`
- AC-4 断言 `default` 可为 NULL 提供兜底值
- AC-5 断言 `reject_if` 命中时按 `on_cast_error` 策略处置

**测试方式**：独立测试——每种 op 一组样例，断言输出。

**已知边界**：科学计数法 `1.28e3` 需代码规则（走逃生舱）。

## REQ-D-012　1:1 约束守护

**优先级** P0 ｜ **硬依赖** 无

**业务目标**：保证可追溯性——**一个属性必须能明确回答"它来自哪一列"**。若允许一列拆多列，映射关系变成 1:N，审计链无法说清属性来源，REQ-D-002 的"依据什么数据"就断了。

**方案**：loader 强制校验——**同一 binding 内**同一源列不得映射多个别名（一源列一属性）；禁止任何形式的列拆分声明（含 transform 的 split 类 op）。豁免边界：`source_sql` 绑定即派生属性，属合法（person/account 现有 UNION 绑定不违规）；跨对象共用同一源列合法（如通话记录.主体 同时喂 person/call）。

**验收标准**：

- AC-1 断言**同一 binding 内**两个属性映射同一源列时硬失败，错误信息指明冲突双方（跨对象共用源列合法，不在此列）
- AC-2 断言声明 `split` 类 op 时硬失败（**本约束明确禁止**）
- AC-3 断言一属性映射多列（N:1 合并）时也硬失败，除非显式声明为派生属性
- AC-4 断言错误信息给出可行出路（提示用 source\_sql 在上游处理）
- AC-5 断言现有 13 个声明文件全部通过此校验（无既存违规）

**测试方式**：独立测试——构造两个属性指向同一源列，断言被拒绝且错误信息可读。

**业务价值**：这条是**防御性需求**。它不增加功能，但保护了可追溯性这条底线——而可追溯性是整个审计链的地基。

**关联**：此约束直接导致 REQ-D-013 成为必需。

***

## REQ-D-013　复合列处置

**优先级** P0 ｜ **硬依赖** REQ-D-012

**业务目标**：禁止拆分后，电诈常见的复合列（`张三|330108...`、`USD 1,280.50`、`浙江省杭州市滨江区...`）必须有明确出路，否则接入即失败。

**方案**：复合列只能在**数据源侧**处理，两条路径：

| 路径          | 做法                                          | 适用        |
| ----------- | ------------------------------------------- | --------- |
| **A. 上游拆分** | `source_sql` 中拆开，声明层仍是 1:1                  | 推荐，保持可追溯  |
| **B. 整列降级** | 显式声明 `composite: true`，整列按 string 接入并标记不可关联 | 无法改上游时的兜底 |

**验收标准**：

- AC-1 断言 `source_sql` 预处理的复合列，声明层仍满足 1:1
- AC-2 断言未声明 `composite` 却含复合值时，由物化后值扫描检出 + 画像告警（loader 编译期无法静态判定复合列）
- AC-3 断言 `composite: true` 的属性被标记为**不可参与实体关联**
- AC-4 断言复合列属性在数据画像中显示为"未拆分"状态
- AC-5 断言复合列不参与主键与去重判定
- AC-6 断言数据元标准提供的原子字段不触发此检查

**测试方式**：独立测试——构造 `张三|330108199001011234`，分别用两条路径接入，断言结果符合预期。

**业务价值**：AC-3 最关键——复合列若被误当作可关联键，实体对齐会全线出错，而这种错误极难发现。

**根本解法**：数据元标准要求上游提供原子字段，从源头消灭复合列。这是 REQ-D-001 的又一价值。

## REQ-D-014　空值策略

**优先级** P1 ｜ **硬依赖** REQ-D-009

**业务目标**：现在无任何空值处理。电诈场景里"金额为空"与"备注为空"的严重性完全不同，需要区分对待。

**方案**：属性级声明 `null_policy`：`allow` / `reject` / `quarantine`。

**验收标准**：

- AC-1 断言 `reject` 属性的空值行被拒绝且记录原因
- AC-2 断言 `allow` 属性行为与现状一致
- AC-3 断言空值率进入数据画像（现有已有此能力，需确保 transform 后仍准确）
- AC-4 断言空值策略与 `on_cast_error` 可组合且优先级明确
- AC-5 断言空值统计进入健康度

**测试方式**：独立测试——同一列分别声明三种策略，断言行为差异。

## REQ-D-015　业务键去重

**优先级** P2 ｜ **硬依赖** 无

**业务目标**：现在去重是全行比对（`IS NOT DISTINCT FROM` 所有列）。电诈需要**按流水号去重**——同一笔交易重复导入应按业务键识别，而非全行比对。

**方案**：`key: {"columns": ["serial_no"], "on_conflict": "keep_latest"}`。

**验收标准**：

- AC-1 断言按业务键去重生效，非全行比对
- AC-2 断言 `keep_latest` / `keep_first` / `fail` 三态行为正确
- AC-3 断言未声明 key 时行为与现状一致
- AC-4 断言业务键冲突数量被统计
- AC-5 断言业务键含空值时行为明确（拒绝或跳过，不静默）

**测试方式**：独立测试——同一流水号两行内容略异，断言按 key 去重。

# D. 质量检查

## REQ-D-016　值域与格式合规检查

**优先级** P0 ｜ **硬依赖** REQ-D-001

**业务目标**：**这是当前最大的缺口**（已用 grep 确认：`value_range`/`format_check`/`regexp_matches`/`checksum` 全部无命中）。现有画像只有统计特征，无法判断身份证是否 18 位、卡号校验位对不对、金额是否为负、日期是否为未来时间——**而这些恰恰是电诈数据最容易出问题的地方，因为它们在统计上完全正常**。

**方案**：基于数据元的格式与值域定义，对已物化属性执行合规扫描。

**验收标准**：

- AC-1 断言身份证格式非法、校验位错误的行被检出
- AC-2 断言手机号号段非法被检出
- AC-3 断言金额为负或超阈值被检出
- AC-4 断言未来日期被检出
- AC-5 断言枚举值不在代码表内被检出
- AC-6 断言检查项可单独启用/停用
- AC-7 断言违规行进入隔离或标记，**不静默通过**
- AC-8 断言未引用数据元的属性不执行合规检查（不误报）

**测试方式**：独立测试——构造含各类非法值的样例，断言逐项检出。

**业务价值**：统计型检查（空值率、基数）与规范型检查（格式、校验位）是互补的两半。现在只有前一半。

***

## REQ-D-017　合规结果纳入画像

**优先级** P1 ｜ **硬依赖** REQ-D-016

**业务目标**：现有画像扣分基于统计（实测：`org.raw_name` 混装 -25 block、`org.relation` 空值 67% -20 block）。合规违规应该同等参与评分，否则"格式全错但空值率低"的属性会拿到高分。

**方案**：合规违规率作为新扣分项，复用现有 block/warn 两级与五要素（scope/ref/code/reason/severity）。

**验收标准**：

- AC-1 断言合规违规率超阈值触发扣分
- AC-2 断言扣分条目含完整五要素
- AC-3 断言合规扣分与统计扣分可区分（不同 code 前缀）
- AC-4 断言报告顶部"全部结论均为待核实候选"的声明仍然保留
- AC-5 断言现有画像分数在无非合规属性时不变（回归）

**测试方式**：独立测试——构造合规违规率 40% 的属性，断言扣分且 code 可区分。

**业务价值**：AC-4 不能丢——画像全部是"待核实候选"，加新扣分项不能改变这个定性。

## REQ-D-018　敏感字段主动扫描

**优先级** P1 ｜ **硬依赖** 无

**业务目标**：现有遮蔽是声明式的（`property_policies` 仅 3 条）。若某个敏感列未声明，它会**以明文暴露**。需要主动发现未声明的敏感列。

**方案**：基于列名启发式 + 值模式识别（身份证/卡号/手机号形态），扫描未声明遮蔽但疑似敏感的字段。

**验收标准**：

- AC-1 断言未声明遮蔽的身份证列被识别并告警
- AC-2 断言已声明遮蔽的列不重复告警
- AC-3 断言普通文本列不误报（误报率需可测）
- AC-4 断言扫描结果给出"建议补充遮蔽声明"的可操作建议
- AC-5 断言扫描为**告警**而非阻断（不阻止装载）

**测试方式**：独立测试——构造含未声明敏感列的表，断言被识别。

**业务价值**：这是唯一一条"防御遗漏"的需求。声明式遮蔽的弱点就是怕漏声明。

## REQ-D-019　数据时间新鲜度

**优先级** P2 ｜ **硬依赖** 无

**业务目标**：现有新鲜度检查是**本体版本**的（`FRESH`/`STALE`/`UNBUILT`），不是数据时间的。用户无法回答"我看到的流水是多久以前的"。

**方案**：按时间属性统计最新数据时间，与当前日期比对，超期告警。

**验收标准**：

- AC-1 断言可显示每个含时间属性对象的最新数据时间
- AC-2 断言超期（可配阈值）触发告警
- AC-3 断言时间属性为空时行为明确（不误报为"很旧"）
- AC-4 断言与本体版本新鲜度**分开显示**，不混淆
- AC-5 断言进入健康度小节

**测试方式**：独立测试——构造半年前的数据，断言超期告警。

## REQ-D-020　单位与口径一致性

**优先级** P2 ｜ **硬依赖** REQ-D-001

**业务目标**：元/万元混用、百分比与小数混用——这类问题统计特征完全看不出来，但会让所有金额类结论错误。

**方案**：数据元声明单位，装载时校验；跨表金额聚合前校验单位一致。

**验收标准**：

- AC-1 断言同一数据元在不同表中单位不一致被检出
- AC-2 断言金额分布异常（如突增 10000 倍）触发提示
- AC-3 断言单位声明缺失时给出提示而非硬失败
- AC-4 断言检出结果为告警，不阻断装载

**测试方式**：独立测试——两张金额表分别用元和万元，断言被检出。

**说明**：AC-2 只能给提示不能确证，因为"金额突增"本身可能是真实业务。这条需求的价值是**让人注意到**，不是自动判定。

## REQ-D-021　数据元驱动自动推荐

**优先级** P1 ｜ **硬依赖** REQ-D-001、REQ-D-002

**业务目标**：接入向导（REQ-W-010）目前需人工映射。有了数据元标准，可按列名与值模式推荐映射与规则。

**方案**：基于数据元的名称、别名、格式特征，为源列推荐目标属性与清洗/转换规则。

**验收标准**：

- AC-1 断言列名含"身份证"的列被推荐 id\_card 数据元
- AC-2 断言推荐同时给出清洗规则（normalize\_idcard）
- AC-3 断言推荐为**建议**而非自动生效（红线：提案永不自动生效）
- AC-4 断言低置信度推荐被标记为"需人工确认"
- AC-5 断言用户可覆盖推荐，且覆盖行为被记录
- AC-6 断言复合列被识别并提示需上游拆分（联动 REQ-D-013）

**测试方式**：独立测试——准备含 10 个典型列名的表，断言推荐准确率与召回率可统计。

**业务价值**：AC-3 是红线。自动映射只能是推荐——这符合项目"提案永不自动生效"的既定原则，**不是缺陷，是设计**。

## REQ-D-022　质量结果进健康度

**优先级** P1 ｜ **硬依赖** REQ-D-008、REQ-D-016、REQ-D-017

**业务目标**：数据质量的各类结果分散在不同模块，用户看不到全貌。治理仪表盘（REQ-W-018）应汇总呈现。

**方案**：清洗留痕、CAST 隔离、合规违规、敏感字段告警统一进健康度小节，并在仪表盘展示。

**验收标准**：

- AC-1 断言清洗剔除数进入健康度且可检索
- AC-2 断言 CAST 隔离行数进入健康度
- AC-3 断言合规违规数进入健康度
- AC-4 断言敏感字段告警进入健康度
- AC-5 断言每类结果有独立 `source` 标识，可区分来源
- AC-6 断言健康度状态因数据质量问题而降级（不只是规则问题）
- AC-7 断言所有条目可下钻到具体行样本

**测试方式**：独立测试——构造含四类问题的装载，断言健康度全部呈现且可下钻。

**业务价值**：AC-6 很关键——现在健康度主要反映规则运行状态，数据本身的问题没有充分体现。

# 三条不可突破的边界

1. **映射层严格 1:1**（REQ-D-012）。任何形式的列拆分不在 ETL 声明层实现——这是可追溯性的底线。复合列只能在上游 `source_sql` 处理，或显式声明为不可关联的降级属性。
2. **未知规则硬失败不放宽**（REQ-D-004 AC-3、REQ-D-011 AC-6）。配置化的目的是降低扩展成本，不是降低校验强度。
3. **任何数据丢弃必须留痕**（REQ-D-008、REQ-D-010 AC-5、REQ-D-016 AC-7）。静默过滤、静默 NULL、静默通过——三种形态都要消灭。
