## 1. 背景与问题定位（代码事实）

**现状能力：**

- 证据三栏 [ThreeColumnEvidence.vue](../../../frontend/src/components/research/ThreeColumnEvidence.vue) **纯只读**：渲染 `partitionEvidence` 三栏（事实/推断/待核实），卡片上无任何操作。
- 待核实项来源 [evidence_builder.py](../../../server/app/evidence_builder.py)：动态生成、非持久对象——降级标记 `d{clue_id}`、待验证假设 `h{clue_id}`、规则判据 `r{clue_id}`；事实 `f{clue_id}-{idx}`、推断 `i{clue_id}`。
- 唯一"动手"入口是**整条线索**状态机 [ClueStatusMachine.vue](../../../frontend/src/components/research/ClueStatusMachine.vue) → `POST /cases/{cid}/clues/{clue_id}/actions`（[clues.py](../../../server/app/routers/clues.py) L61-106）→ `TASK_DISPOSE`（[worker/dispose.py](../../../server/app/worker/dispose.py)）→ `DisposalBoard`/`ActionExecutor` → `state.sqlite clue_disposal_status` + `audit_chain`。
- 处置结论只有**一段自由文本 note**。

**核心缺口：** 待核实栏每一条本质是可执行的核查任务（现金存款人是谁、合同付款节点、配偶账户去向…），但系统没有对象承接"谁查了什么、结论是什么、依据哪份材料"。核查过程不可累积、不可逐项追溯、挂不上书证，最后只能往一个文本框里塞结论。

## 2. 架构决策（ADR）

### ADR-V-1 数据承载：per-case state.sqlite 新增 3 表

核查项/书证/调取清单是**业务态**不是数据态——落 [state_store.py](../../../server/app/store/state_store.py) `_SCHEMA`（与 `clue_disposal_status`/`de_recommendation` 同层），不进 DuckDB 语义层。`CREATE TABLE IF NOT EXISTS` 随打开幂等建表，**旧案件零迁移脚本**。不随 BUILD 重建丢失（D1 决策延续）。

### ADR-V-2 写路径：Worker 任务 + StateStore 方法 + audit_append（W-021 先例）

核查项**不是线索状态迁移**，不走 `ActionExecutor.execute()`（其四步校验绑定 `ClueStatusMachine.validate(clue.status, target_status)`）。写路径复用既有同族先例：

- W-021 实体裁决（[worker/review.py](../../../server/app/worker/review.py)）：专用 Worker handler → 直接写 state 表 → `StateSink.audit_append()` 落审计链；
- W-P-007 数据元裁决（`decide_de_reco`）、W-P-008 质量检查（`save_quality_check`）同通道。

不改 `actions.json`/loader（[ontology_loader.py](../../../core/ontology_loader.py) L1133 强制 `target_status`，改造属 core 风险面，73 测试组牵连）。备选方案（扩展 ActionSpec 支持 item-level 动作，optional target_status）记入 P3 评估。**线索级处置门禁联动**（REQ-V-008）在 worker/dispose.py 处置路径上加前置校验，复用既有 `TASK_DISPOSE`。

### ADR-V-3 定性权与主体一致性

- 内核复跑结论、Agent 建议**一律标注"AI辅助推演·需人确认"，永不自动定性**；
- 已证实/已查否/固证/立案均是人写动作；`operator` 一律取**会话快照**（随任务行，不信请求体——REQ-009 同款）；`operator` 以 `agent:` 开头直接拒绝；
- 每次核查写操作经 `StateSink.audit_append()` 落 `audit_chain` 哈希链（`chain_verify` 可验）。

### ADR-V-4 稳定键：核查项跨 BUILD 幂等

待核实文本是 BUILD 动态产出，重建后同内容应映射同一核查项（结论不丢）：

```
item_key = sha1(f"{clue_id}|{kind}|{text}").hexdigest()[:16]
item_id  = f"vi_{item_key}"
UNIQUE(clue_id, item_key)
```

产物重建后惰性供给按 `item_key` UPSERT（`origin='auto'` 项只补缺不覆盖结论；人工项永不触碰）。

### ADR-V-5 三栏纪律与产物不可变

- 事实栏**永不改写**（事实是数据，FE-T-005 延续）；
- 核查结论是"人对推断/待核实项的裁决"，只落 state.sqlite 工作区，**不回写 artifact**（产物随版本不可变）；
- 核查工作区在"三栏证据"之下独立成区，不混栏。

## 3. 数据模型（state.sqlite 新增表 DDL）

追加进 `_SCHEMA`（[state_store.py](../../../server/app/store/state_store.py) L29-101）：

```sql
-- 核查项：每条待核实/推断的可操作裁决对象
CREATE TABLE IF NOT EXISTS clue_verify_item (
    item_id     TEXT PRIMARY KEY,            -- vi_{item_key}
    case_id     TEXT NOT NULL,
    clue_id     TEXT NOT NULL,
    item_key    TEXT NOT NULL,               -- sha1(clue_id|kind|text)[:16]
    kind        TEXT NOT NULL,               -- pending_degrade|pending_hypothesis|pending_rule|inference|manual
    text        TEXT NOT NULL,
    origin      TEXT NOT NULL DEFAULT 'auto',-- auto=供给生成 / manual=人工添加
    status      TEXT NOT NULL DEFAULT '待核查',
                -- 待核查 → 核查中 → 已证实 | 已查否 | 无法核实
    conclusion  TEXT NOT NULL DEFAULT '',
    operator    TEXT NOT NULL DEFAULT '',
    updated_at  TEXT NOT NULL DEFAULT '',
    UNIQUE(clue_id, item_key)
);
CREATE INDEX IF NOT EXISTS idx_vi_clue ON clue_verify_item(clue_id);

-- 证据材料：人工调取的书证（区别于 uploads/ 数据源，不参与自动检测）
CREATE TABLE IF NOT EXISTS clue_evidence (
    material_id   TEXT PRIMARY KEY,          -- ev_{uuid12}
    case_id       TEXT NOT NULL,
    clue_id       TEXT NOT NULL,
    item_id       TEXT,                      -- 可空=线索级材料
    material_type TEXT NOT NULL,             -- 缴款单|监控截图|合同|付款凭证|审批文件|其他
    filename      TEXT NOT NULL,             -- 消毒后存储名
    orig_name     TEXT NOT NULL,
    sha256        TEXT NOT NULL,
    size          INTEGER NOT NULL,
    note          TEXT NOT NULL DEFAULT '',
    uploaded_by   TEXT NOT NULL,
    uploaded_at   TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_ev_clue ON clue_evidence(clue_id);

-- 调取清单：外部取证的台账（超期可跟踪）
CREATE TABLE IF NOT EXISTS verify_request (
    request_id       TEXT PRIMARY KEY,       -- vr_{uuid12}
    case_id          TEXT NOT NULL,
    clue_id          TEXT NOT NULL,
    item_id          TEXT,                   -- 关联核查项（可空）
    target           TEXT NOT NULL,          -- 调取单位/对象
    material         TEXT NOT NULL,          -- 调取材料
    legal_instrument TEXT NOT NULL DEFAULT '',-- 法律手续（调取函/审批文号）
    handler          TEXT NOT NULL DEFAULT '',-- 经办人
    due_date         TEXT NOT NULL DEFAULT '',-- 期限 YYYY-MM-DD
    status           TEXT NOT NULL DEFAULT '待发起',
                     -- 待发起 → 已发起 → 材料已回 | 超期 → 关闭
    note             TEXT NOT NULL DEFAULT '',
    created_by       TEXT NOT NULL,
    created_at       TEXT NOT NULL,
    updated_at       TEXT NOT NULL DEFAULT ''
);
CREATE INDEX IF NOT EXISTS idx_vr_clue ON verify_request(clue_id);
```

文件存储（P2）：`cases/<cid>/evidence/{material_id}/{filename}`，与 `uploads/`（数据源）物理分离。

#### REQ-V-001 StateStore 核查项 CRUD + 稳定键

**目标**：`clue_verify_item` 表的持久化方法层，供惰性供给与 Worker 复用。

**改动点**：[state_store.py](../../../server/app/store/state_store.py)——`_SCHEMA` 追加 DDL；新增方法：

```python
@staticmethod
def verify_item_key(clue_id: str, kind: str, text: str) -> str: ...

def upsert_verify_items(self, case_id: str, clue_id: str,
                        items: list[dict]) -> dict
# items=[{kind,text}]；按 item_key INSERT OR IGNORE（只补缺不覆盖既有结论/状态）；
# 返回 {added:int, total:int}

def add_manual_verify_item(self, case_id, clue_id, text) -> dict   # origin='manual'
def list_verify_items(self, clue_id: str) -> list[dict]            # 按 status+created 排序
def get_verify_item(self, item_id: str) -> dict | None
def transition_verify_item(self, item_id, *, status, conclusion,
                           operator, updated_at) -> dict | None    # rowcount=0 → None
def verify_progress(self, clue_id: str) -> dict
# {total, concluded, pending, by_status:{...}}
```

**细节**：
- 键算法 ADR-V-4；`conclusion` 必须随终态转移写入（见 REQ-V-003 校验，此处方法层不重复校验）；
- `upsert_verify_items` 用 `INSERT OR IGNORE`——天然幂等，重跑行数不变（对齐 `import_from_duckdb` 幂等纪律）。

**验收标准**（可独立断言）：
1. 同一批 items 两次 upsert，第二次 `added=0`，`total` 不变；
2. 已有结论的项重新 upsert 后 `conclusion/status/operator` 不被覆盖；
3. `verify_item_key` 对相同 (clue_id,kind,text) 稳定、不同 text 不同键；
4. `verify_progress` 对 3 项（1 已证实/1 已查否/1 待核查）返回 `{total:3, concluded:2, pending:1}`；
5. 打开**旧案件**（无新表）的 state.sqlite，方法可用（幂等建表生效）。

**测试落点**：`tests/test_verify_item.py`（新）→ 注册测试组 `verifyitem`。

#### REQ-V-002 核查项惰性供给（读面组装）

**目标**：线索详情读面把"待核实/推断"证据项自动映射为核查项清单（只补缺，不改状态）。

**改动点**：
- 新文件 `server/app/verify_provision.py`：`provision_for_clue(raw_clue: dict) -> list[dict]`——纯函数，从 artifact raw 产出 `[{kind,text}]`：
  - `detail.待核实` 列表项 → `kind='pending_rule'`（沿用 detail 中文键，需对照 registry_bootstrap 各适配器实际写入的键名，编码期逐一核对）；
  - 降级标记 → `kind='pending_degrade'`；假设 → `kind='pending_hypothesis'`（与 evidence_builder L78-106 同源逻辑，但**直接从 raw_clue 取**，不依赖 access）；
  - `detail.依据` 非空 → `kind='inference'`（推断也可被核查裁决）；
- [clues_view.py](../../../server/app/clues_view.py) `assemble_detail`：`state` 非 None 时调用 `upsert_verify_items` 并在返回项中附加 `verify = {items, progress}`（读面顺带供给，无需显式初始化步骤）。

**细节**：
- 读面写库需注意 WAL 并发——`upsert_verify_items` 单事务、busy_timeout=5000 已有；
- 已立案（终态）线索：供给仍执行（补清单），但转移类操作被 REQ-V-004 拒绝。

**验收标准**：
1. 构造含 `detail.依据` + 待核实项的 raw_clue，首次 `assemble_detail` 后 state 表出现对应行，`origin='auto'`；
2. 修改某项 status='已证实' 后再调 `assemble_detail`，该项状态/结论不变、不新增行；
3. 无 state.sqlite（未处置过）的案件：`_read_state` 返回 None，供给跳过，详情接口不报错、响应无 `verify` 键；
4. 供给产出与 evidence_builder 三栏 pending 文本一致（同源）。

**测试落点**：`tests/test_verify_item.py`（与 001 同组）。

#### REQ-V-003 核查项状态机与转移校验

**目标**：核查项自身的确定性状态机，前后端同构（对齐 domain/clue.ts 模式）。

**状态机**（单一事实源写在 `core` 侧纯函数，server/frontend 同构引用）：

```
待核查 → 核查中 | 已证实 | 已查否 | 无法核实
核查中 → 已证实 | 已查否 | 无法核实 | 待核查（退回）
已证实/已查否/无法核实 → 核查中（重开，需 operator 具名，覆盖结论前旧值留审计）
```

**改动点**：新文件 `core/verify_machine.py`：

```python
VERIFY_STATUSES = ("待核查", "核查中", "已证实", "已查否", "无法核实")
VERIFY_TRANSITIONS: dict[str, tuple[str, ...]] = {...}
CONCLUSION_REQUIRED = {"已证实", "已查否"}   # 无法核实可不填但建议
def validate_verify_transition(cur: str, nxt: str) -> None  # 非法迁移 raise ValueError
```

**细节**：
- 终态重开是合法路径（侦查实务允许翻案），但必须留审计（REQ-V-004 落链含 before/after）；
- 纯函数无 I/O，前端 vitest 直接测同构表。

**验收标准**：
1. 非法迁移（待核查→待核查、已证实→已查否）抛 `ValueError`；
2. `CONCLUSION_REQUIRED` 终态缺结论时上层任务报 `CONCLUSION_REQUIRED`；
3. 合法迁移全表遍历通过。

**测试落点**：`tests/test_verify_item.py`。

#### REQ-V-004 TASK_VERIFY Worker 任务（核查写通道）

**目标**：核查项写操作唯一执行体：校验 → state 写 → 审计链。

**改动点**：
- [worker/tasks.py](../../../server/app/worker/tasks.py)：`TASK_VERIFY = "VERIFY"` + handler 注册（对齐 `TASK_REVIEW: _review_handler` L299 模式）；
- 新文件 `server/app/worker/verify.py`：`handle_verify(task, *, repo, factory, **_) -> dict`。

**行为**（对齐 worker/dispose.py 与 worker/review.py 纪律）：

```
入参 params = {
  op:        "transition" | "add_manual",
  clue_id, item_id?, text?,
  next_status?, conclusion?,
  operator, role, clearance            # 入队时会话快照，Worker 不信任请求体 operator
}
校验：
  op=transition → item 存在（ITEM_NOT_FOUND）；core/verify_machine.validate；
  终态缺结论 → CONCLUSION_REQUIRED；
  operator 以 agent: 开头 → AGENT_FORBIDDEN（对齐 clue_transition 红线）
写：transition_verify_item(...)；StateSink.audit_append({
      event:"verify_item_transition", clue_id, item_id,
      before:{status,conclusion}, after:{...}, operator, ontology_version:f"v{ver}"})
错误映射：ValueError→VERIFY_REJECTED；PermissionError→VERIFY_FORBIDDEN；
          KeyError→ITEM_NOT_FOUND（TaskExecError 三态，不崩 Worker）
```

**验收标准**：
1. 合法转移后 state 行更新 + audit_chain 追加 1 条且 `chain_verify()` 通过；
2. `agent:xxx` operator → 任务 FAILED，error=`VERIFY_FORBIDDEN`；
3. 非法迁移 → `VERIFY_REJECTED`；不存在 item → `ITEM_NOT_FOUND`；
4. 同 item 并发两个转移任务，FIFO 串行执行均成功（WAL busy_timeout）；
5. 任务不产 DuckDB 版本文件（`current_version` 不变）。

**测试落点**：`tests/test_verify_item.py`（Worker 层用例）。

#### REQ-V-005 核查项 API

**目标**：前端可用的读写端点（读同步、写 202 入队——对齐 backend_api.md 2.4 处置模式）。

**改动点**：[routers/clues.py](../../../server/app/routers/clues.py) 追加：

```
GET  /cases/{cid}/clues/{clue_id}/verify-items
     → {items:[{item_id,kind,text,origin,status,conclusion,operator,updated_at}],
        progress:{total,concluded,pending,by_status}}
     （state 不存在 → {items:[],progress:{total:0,...},available:false}）

POST /cases/{cid}/clues/{clue_id}/verify-items            # 人工添加
     body {text} → 202 + task_dto（TASK_VERIFY op=add_manual；idem_key=verify-add:{clue_id}:{sha1(text)}）

POST /cases/{cid}/clues/{clue_id}/verify-items/{item_id}/transitions   # 202
     body {next_status, conclusion?} → 202 + task_dto
     （idem_key=verify:{item_id}:{next_status}；API 侧快速失败仅做参数形状校验，
       状态机/红线在 Worker 兜底——与 clues.py 注释同款纵深防御）
```

**细节**：跨租户 404 走 `_get_owned_case`；operator 取 `p.operator` 会话快照入任务行（与 clue_action L93-100 同款）。

**验收标准**：
1. GET 返回供给后的清单与 progress；无 state 时 `available:false`；
2. POST transitions 返回 202+task_id，Worker 消费后 GET 可见新状态；
3. 缺 `next_status` / 非法值 → 400（ERR_VALIDATION）；
4. 跨租户访问他人案件 → 404；未登录 → 401；
5. 相同 idem_key 重复提交不产生重复任务行。

**测试落点**：`tests/test_verify_api.py`（新，参考 test_dispose_api.py 的 TestClient 造案模式）→ 注册测试组 `verifyapi`。

#### REQ-V-007 三栏待核实卡片联动

**目标**：待核实卡片从"只能看"变成"可跳转核查"，但保持组件向后兼容。

#### REQ-V-008 固证/排除核查门禁

**目标**：把"填一段 note 就能固证"改为"核查项全结才能固证/排除"——闭环的强制点。

**改动点**：[worker/dispose.py](../../../server/app/worker/dispose.py) `handle_dispose`：
- `_apply_action` 之前：action ∈ {confirm, exclude} 时读 `state.verify_progress(clue_id)`；
- `pending > 0` → `TaskExecError("VERIFY_PENDING", f"尚有 {pending} 项核查未结：{前三项 text}…（先逐项得出结论，或标记无法核实）")`；
- 无核查项（total=0）或已全结 → 放行（行为向后兼容）；
- file/verify/reset 不受门禁影响；
- **前端提示**（非拦截）：[ClueStatusMachine.vue](../../../frontend/src/components/research/ClueStatusMachine.vue) 新增可选 prop `verifyPending?: number`，>0 且 action=confirm/exclude 的确认弹窗顶部显示琥珀警示"尚有 N 项核查未结（服务端将拒绝）"。

**细节**：
- 门禁在 Worker（core 真值）而非 API——API 侧仅前端提示，纵深防御与 file 校验同款；
- "无法核实"算已结——外部调取走 verify_request 台账，不阻塞固证。

**验收标准**：
1. 3 项中 1 项待核查时 confirm → FAILED error=`VERIFY_PENDING`，状态仍"查证中"，audit_chain 无迁移事件；
2. 全结后 confirm 成功；
3. total=0 的线索 confirm 行为与现状完全一致（回归）；
4. exclude 同样被拦截；verify/reset/file 不受影响；
5. 前端：`verifyPending=2` 时 confirm 弹窗出现警示文案；=0 不出现。

**测试落点**：`tests/test_verify_api.py`（门禁用例）+ `frontend ClueStatusMachine.spec.ts` 扩充 → 后端注册进 `verifyapi`。

#### REQ-V-017 一键复跑回填

**目标**：核查项旁"运行内核核查"按钮 → 调只读 Function → 结果回填为该项"内核复跑结论 + 溯源行"，标注 **AI辅助推演·需人确认**，不自动改状态。
