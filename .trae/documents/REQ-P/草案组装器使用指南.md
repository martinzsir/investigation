# 草案组装器使用指南（REQ-P M6）

> 一句话：**新表接入前先画像，画像自动产出「objects/links/bindings 三件草案 + ETL 步骤清单」，
> 人工审核后复制进 `ontology/<pack>/`，经 `build_ontology` 校验才生效。**
> 全程只读、只写 `output/`，**绝不写 `ontology/`**；草案恒为【待核实】候选。

- 核心模块：[core/draft_assembler.py](../../../core/draft_assembler.py)
- 画像契约：[core/ontology_profile.py](../../../core/ontology_profile.py)（`TableProfile` / `build_table_profile`）
- CLI：[scripts/profile_table.py](../../../scripts/profile_table.py)
- 依赖：M3 值类型识别（`core/value_type.py`）、M4 六层画像、REQ-P-034 metadata_props

---

## 一、它解决什么问题

接入一张新外部表（Excel/CSV/SQLite/Parquet/JSON）时，过去要手工回答：

1. 这张表值不值得接？（空值率、混装、基数）
2. 每列该建什么属性类型？（string/decimal/date…）
3. 哪列是主键、哪列是名称、哪列是备注？
4. 哪些列能连到已有对象？（候选归一关联）
5. 接入要按什么顺序做？（先拆混装还是先建表？）

草案组装器把 2~5 自动生成成**带证据的草案**，1 由画像报告给出。
**生成 ≠ 生效**：草案落在 `output/drafts/`，人工确认 + loader 校验两道闸后才进入本体。

---

## 二、最快上手（CLI）

```bash
# 读外部表 → 画像报告 + 三件草案（语义层存在时额外算候选关联）
python -m scripts.profile_table --input data/samples/工商信息.xlsx

# 指定 Excel sheet / SQLite 表名
python -m scripts.profile_table --input data/samples/xxx.xlsx --sheet Sheet1
python -m scripts.profile_table --input data/xxx.sqlite --sheet 表名

# 指定案件包 / 语义层库
python -m scripts.profile_table --input xxx.csv --pack default --db investigation.duckdb

# 只画像、不生成草案
python -m scripts.profile_table --input xxx.csv --no-drafts
```

**产物**：

| 产物 | 路径 | 内容 |
|---|---|---|
| 画像报告 | `output/profiles/<表名>_profile.md` | 列画像表、候选关联、建议 ETL 步骤 |
| 画像数据 | `output/profiles/<表名>_profile.json` | 完整 TableProfile + steps + 草案路径 |
| 对象草案 | `output/drafts/<表名>/objects.draft.json` | 对象声明草案（属性类型/pk/名称/metadata） |
| 链接草案 | `output/drafts/<表名>/links.draft.json` | 候选关联 → 链接 + 端点 ref 提示 |
| 绑定草案 | `output/drafts/<表名>/bindings.draft.json` | object_binding + link_bindings SQL 草案 |

> CLI 以 **raw 模式**读表（`dtype=str`、不映射列名、不做类型转换）——
> 金额/日期必须保持原始字符串，值类型识别才有效（风险 7：适配器隐式 coerce 会把
> `100000` 转成数字、把日期转成 Timestamp，导致判型失真）。

## 三、Python API

```python
from core.ontology_profile import build_table_profile
from core.draft_assembler import DraftAssembler, recommend_steps

# 1) raw 读取外部表（全字符串矩阵；空单元格传 None）
columns = ["账号", "姓名", "金额", "日期", "备注", "混装"]
rows = [
    ["6222000111110001", "张卫国", "100000", "2021-10-01", "工资发放", "张卫国"],
    ["6222000222220002", "李志强", "4600000", "2021-09-28", "备注二", "6222000111110001"],
]

# 2) 构建画像（gateway 可选：提供时算候选关联；None 时纯列画像）
profile = build_table_profile("demo_table", columns, rows,
                              gateway=gw,            # OntologyReadGateway；无库传 None
                              pack="default",
                              min_ratio=None)        # None→读 thresholds profiler.draft_overlap_min_ratio

# 3) 组装三件草案
da = DraftAssembler(profile, pack="default")
da.draft_object()     # → objects.json 草案 dict
da.draft_links()      # → links.json 草案 dict
da.draft_bindings()   # → bindings.json 草案 dict
da.write_drafts("output/drafts")   # → 落盘 3 个文件（只写 output/drafts）

# 4) 步骤序列（零 IO，纯函数）
steps = recommend_steps(profile)   # → [{"step","why","how","done_when"}, ...]
```

### TableProfile 契约

```python
TableProfile(
    table_name: str,
    row_count: int,
    columns: list[ColumnProfile],      # 每列画像
    candidates: list[CandidateAssoc],  # 候选关联（需 gateway）
)

ColumnProfile(
    name: str, null_rate: float, distinct: int,
    type_dist: dict,            # 值类型分布，如 {"account": 2}
    samples: list,              # 去重样例（前 5，敏感列勿外传）
    mixed: bool | None,         # 混装（≥2 归一落点）
    landing_suggestions: list,  # 落点建议，如 ["account","person"]
    needs_confirmation: bool,   # 含肯定式识别（人名/机构名）
)

CandidateAssoc(
    col: str, target_obj: str, target_prop: str,
    overlap_ratio: float,       # 外部列 distinct 命中身份列的比例
    direction: str = "external_to_ontology",
)
```

## 四、草案长什么样（真实示例）

对 `data/samples/工商信息.xlsx`（1 行 × 2 列：主体/关联）生成的对象草案：

```json
{
  "schema_version": 2,
  "_draft": true,
  "_status": "待核实",
  "pack": "default",
  "objects": [
    {
      "name": "ext_TODO_RENAME",
      "title": "工商信息（外部接入候选，对象名待人工命名）",
      "kind": "entity",
      "name_property": "主体",
      "properties": { "主体": "string", "关联": "string" },
      "_candidates": {
        "pk": [],
        "name_property": ["主体", "关联"],
        "metadata_props_suggested": []
      },
      "_evidence": [
        { "kind": "name_property_candidate", "column": "主体",
          "dominant_type": "person", "needs_confirmation": true }
      ]
    }
  ]
}
```

要点：

- **`name: "ext_TODO_RENAME"` 是占位符**——中文表名不能直接做语义表名，必须人工改成英文标识（如 `shareholder`）；
- **每条 `_candidates` 都有 `_evidence`**，记录判型/基数/相似度来源，可追溯；
- `_draft` / `_status` / `_note` 是草案头，复制进正式 `ontology/` 时**删除这些字段**。

## 五、判型与候选规则

### 值类型映射（`VALUE_TYPE_TO_PROP_TYPE`）

| 值类型（value_type） | 属性类型 | 说明 |
|---|---|---|
| account / phone / id_card | string | 标识类，分别归一到 account/person |
| person / org | string | 人名/机构名（**肯定式，需人工确认**） |
| number | integer | 纯整数 |
| amount | decimal | 金额串（¥/千分位/万元单位） |
| date_str | date | 日期串 |
| boolean | boolean | distinct≤2 且全集命中 是/否/true/false 等 |

- 映射输出**必须是 TYPE_SQL 认识的类型**（测试双向核对，越界即失败）。
- **列名语义启发优先于值形态**：列名含「金额/amount」→ decimal，即使裸数字 `100000`
  值形态像账号；列名含「日期/date」→ date；含「是否/is_」→ boolean。
  这是为纠偏「裸整数金额被误判账号」。

### 候选字段纪律

| 候选 | 判据 |
|---|---|
| **pk** | 否定式标识类（account/id_card/number）+ 唯一率 distinct/行 ≥0.9 + 空值率<50% + 非混装 + 列名非金额/日期/备注/名称 |
| **name_property** | 人名/机构名主导 + 非混装 + 非 metadata 列 |
| **metadata_props** | 列名命中 备注/说明/内容/title 等，或样例最大长度 >50（长文本） |

> 混装列（`mixed=true`）**既不做 pk 也不做 name_property**——必须先拆分。
> 金额/日期/备注列即使值形态像编号也不做 pk。

### 候选关联

- 外部列 distinct 值与语义层**各对象的身份列（name_property）**求交集，
  命中率 ≥ 阈值 `draft_overlap_min_ratio`（默认 0.8，`thresholds.json` profiler 段）即报候选。
- **落点只取身份列**：`relation`/`from_raw` 等可连接属性不是归一目标
  （否则单值外部列会对所有含同值的列误报 100%）。
- 链接草案给**双列方案**提示：raw 列保留 + `<col>_id` 外键，`link_binding.build_sql`
  用 `LEFT JOIN obj_<target>`（NULL 边不丢，对齐 REQ-P-031）。

## 六、建议 ETL 步骤（recommend_steps）

每步含 `why`（画像证据）/ `how`（落到既有命令或声明字段）/ `done_when`（可执行验收）。
**依赖顺序**（写死，测试固化）：

```
split_mixed → clean_rules → type_cast → cold_table → bind_object → bind_links → reprofile
```

1. **混装必先拆分**（`split_mixed`）：落点不明确时连线会同时报两个方向（G-015 教训）；
2. **清洗先于建表**（`clean_rules`）：CTAS 用源列类型；clean 名只能引用已注册规则
   （`strip` / `exclude_org_tokens`），需要新清洗时去 `core/ontology.py` 注册，**不准编造规则名**；
3. **结构化列 CAST**（`type_cast`）：amount→DOUBLE、date_str→DATE、number→BIGINT；
4. **冷层建表**（`cold_table`）：外部表入 `data/*.parquet` 后，加 object_binding 即自动建表（G-014）；
5. **绑定对象/链接**（`bind_object`/`bind_links`）：审核草案后复制进 ontology；
6. **复检**（`reprofile`）：重跑画像，验证混装已拆、空值率改善、关联已连线。

**干净表退化**：无混装、无高空值列（≥50%）、无候选关联时，序列退化为
`[cold_table, bind_object, reprofile]` 三步。

> `recommend_steps` 是**零 IO 纯函数**——只给清单，执行仍走 `data_ingest` /
> `build_ontology` 既有命令，不自动改任何东西。

## 七、从草案到生效（人工两道闸）

```
output/drafts/<表名>/*.draft.json
        │
        │ ① 人工审核：改对象名（ext_TODO_RENAME→英文标识）、确认 pk/name_property、
        │    确认 metadata_props、核对 link build_sql 列名、填 source 路径/source_sql、
        │    删除 _draft/_status/_note/_candidates/_evidence/_endpoints_hint 等草案字段
        ▼
ontology/<pack>/objects.json · links.json · bindings.json   （人工合并进去）
        │
        │ ② build_ontology loader 校验：值类型合法、clean 规则已注册、
        │    binding/link 交叉引用一致、代理键分配…… 不通过即硬失败
        ▼
obj_*/lnk_* 语义表物化（生效）
        │
        ▼
reprofile 复检（OntologyProfiler / build_table_profile）
```

- 草案字段（`_draft`/`_candidates`/`_evidence`/`_endpoints_hint`/`_note`）是**给人看的**，
  不进正式声明；正式声明只保留 loader 认识的字段。
- 草案头的 `build_sql` / `source` 是占位与建议，**必须人工核对列名与路径**后再用。

## 八、红线与常见问题

**红线**

1. 草案只写 `output/drafts/`，工具函数体不构造任何 `ontology/` 路径（测试固化）；
2. 全部只读外部表 + 只读语义层，**不写任何库表**（治理工具读原始外部表是本职，
   与「检测器/图库/MCP 不准直读 Parquet」红线不冲突——那约束的是取证取数路径）；
3. 全部结论【待核实】，启发式判型（尤其人名/机构名）可被人工推翻；
4. 不新增 MCP 工具——建模是治理面，MCP 面向办案。

**常见问题**

- **列被标 `mixed: true` 怎么办？** 先按 `landing_suggestions` 在源端拆成多列，
  再重跑 `profile_table`，直到各列落点唯一（步骤序列第一步就是 split_mixed）。
- **`pk` 候选为空？** 没有「高基数否定式标识列」。事件型表（流水/通话）本就按行发代理键，
  可不设业务 pk；实体表应人工指定编号列。
- **候选关联 0 条？** 语义层未构建（CLI 会提示跳过），或外部列值与身份列重合率低于阈值；
  用 `--db` 指向已构建的库，或检查是否该先归一。
- **人名/机构名判错（肯定式）？** 这是已知局限（技术债：肯定式识别改进）；
  metadata 列已自动排除不报警，标识列请人工确认 `name_property`。
- **样例里有敏感值？** `samples` 最多 5 条供人工核对，外传报告前注意脱敏；
  草案 JSON 不带样例值（证据只记判型/基数，测试有 PII 形态扫描）。
