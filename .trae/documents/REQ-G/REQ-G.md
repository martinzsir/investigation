## P1　失败可见性（核心缺口）

**共同症状**：某个环节失败了，系统继续往下跑，不报错、不记录、不告警，最终产物看不出任何异常。

> **一个反直觉的现状**：语义表不存在（最轻微的失败）返回 `degraded` 标记可审计；表存在但计算结果为零（最严重的失败）反而完全静默。当前降级机制覆盖「数据没接入」，没覆盖「数据接入了但没算出来」。

### REQ-G-002　规则零命中诊断与分类

**问题**：`rules.py` 中规则未命中即 `continue`，无日志、无计数、无诊断。交通违章位置碰撞失败、轨迹同框失败，在系统里表现完全一样：什么都没发生。

**后果**：（一）办案人员把「行为维度无线索」读成「这个方向没有异常」，真实情况可能是「这个方向根本没扫」。排除性结论一旦形成，极少被推翻。（二）匹配算法失效、配置缺失、数据质量缺陷、真实无异常，四种情况在产物里长得一模一样。

**方案**：为每条执行的规则输出诊断对象，至少含扫描行数、有效输入行数、匹配行数、命中与否、未命中原因分类。区分四类零：数据缺失、匹配失败、配置缺失、扫描后确认无异常。诊断对象进产物 JSON，**不进 findings 主列表**。

**验收标准**：
1. 输入 0 行 → `scan_rows=0` 且 `zero_type=data_absent`
2. 输入 100 行、有效 100 行、匹配 0 行 → `scan_rows=100`、`matched_rows=0`、`zero_type=match_failure`
3. 敏感地点集合为空 → `zero_type=config_missing`
4. 输入正常但确无匹配 → `zero_type=clean_scan`
5. 断言四种 `zero_type` 互不混淆
6. 断言诊断对象不进入 findings 主列表

**原因**：「扫描 N 行、匹配 0 行」与「扫描 0 行」含义天差地别，前者是真正需要警惕的信号，后者只是数据没到。当前产物把两者呈现得完全相同。

**价值**：让系统第一次能区分「未验证」与「无异常」。这是侦查语境下最关键的区分——前者需继续查，后者可排除。

### REQ-G-003　降级判据扩展：输入非零而输出为零

**问题**：现有降级判定 `_is_missing_semantic_table` 只识别语义表不存在（`CatalogException`）。表存在但返回零行不触发降级，走正常路径静默返回。

**后果**：最严重的失败最安静。交通违章表接入后若几百行数据一条都匹配不上，系统连「数据源未接入」那样的降级告警都不会给，没有任何迹象表明这批数据白跑了。

**方案**：降级判据增加一条——函数输入行数大于零而输出为零时标记 `degraded`，原因记为「输入非零、输出为零，疑似匹配失效」。需函数实现配合暴露输入行数，或在执行器层面统一统计。

**验收标准**：
1. obj_* 表有 500 行、函数返回 0 行 → `degraded=true` 且 reason 含匹配失效标识
2. 表不存在时仍返回原有降级标记，行为不变
3. 输入 0 行输出 0 行时**不**标记为匹配失效（属 REQ-G-002 的 data_absent）

**原因**：补齐降级机制覆盖面，让它从「只防崩溃」升级为「能识别空转」。

**价值**：匹配失效是接入新数据源后最高频的失败模式，且最易被误读为「查过了没问题」。此条直接堵住该误读路径。

### REQ-G-004　事件总线发布失败不静默丢弃

**问题**：`action_executor.py` 与 `deferred.py` 多处事件发布被 `except: pass` 包裹，失败无任何痕迹。

**后果**：事件链上挂着延迟回捞、动作派发、人审唤醒。事件丢了，依赖它的功能静默失效，而调用方以为已发出。

**方案**：发布失败不得静默。改为写入本地死信表或运行诊断列表，并在运行报告末尾汇总展示。允许不阻断主流程，但必须留痕。

**验收标准**：
1. 构造事件表不可用场景，断言失败被记录且可在诊断区检索到
2. 断言运行报告输出「事件发布失败 N 条」汇总项
3. 正常路径发布行为与审计记录不变

**原因**：`except: pass` 在这一处吞掉的不是异常本身，而是「某个功能其实没有执行」这个事实。

**价值**：恢复事件链可信度。当前无法回答「延迟回捞到底有没有被触发过」。

### REQ-G-005　延迟唤醒条件类型错误显式化

**问题**：`deferred.py` 判断唤醒条件时，`int` 转换失败即 `pass`，静默返回「条件不满足」。

**后果**：任务永远不会唤醒——不是延迟，是**永久沉睡**。正兵会一直以为条件还没到，实际该条件判断从未跑通。线索与证据都在，但系统永远不会再提起它。

**方案**：条件值类型异常不得静默。改为记录条件解析失败并标记任务状态为异常，同时在人审队列与运行报告中暴露。区分「条件未满足」与「条件无法解析」两种状态。

**验收标准**：
1. 构造 `evidence_count` 为不可转换类型的事件，断言任务状态被标记为条件解析异常而非保持沉睡
2. 断言该异常出现在运行报告诊断区
3. 正常条件匹配行为不变

**原因**：永久沉睡比漏侦更隐蔽——漏侦是没发现，沉睡是发现了却永远不会再想起。

**价值**：把「条件还没到」与「条件永远到不了」区分开，避免线索在台账上永续挂起。

### REQ-G-006　实体解析跳过与插件加载失败留痕

**问题**：`entity.py` 中表不存在或列不存在均 `continue` 跳过；自定义实体解析器插件 `exec_module` 失败后 `continue` 回退到内置规则。两处均无提示。

**后果**：（一）数据源表名写错或缺列，实体对齐直接跳过整张表，不产生任何候选也无提示。（二）用户编写了专门处理地点别名的解析器但加载失败，系统不会告知，只会用内置规则得出「无匹配」结论。

**方案**：两处跳过均写入跳过清单，记录表名、缺失列名、插件路径与失败原因，汇总至运行报告。插件加载失败额外产生告警级诊断。

**验收标准**：
1. 构造缺列的表，断言跳过记录含表名与列名
2. 构造加载失败的插件，断言产生告警级诊断且系统仍以内置规则继续运行（不阻断）
3. 正常解析行为与对齐结果不变

**原因**：「部分表对齐不阻断整条管线」的设计意图是对的，缺的是把跳过这件事表达出来。

**价值**：避免「以为对齐过了，其实压根没对齐」。实体对齐错误会沿血缘链扩散到所有下游线索。

### REQ-G-007　本体版本号缺失显式化

**问题**：`audit.py`、`case_library.py`、`derived.py` 中取不到本体版本号时静默返回 `unknown`。

**后果**：审计记录上写着 `ontology_version=unknown`，等于该记录失去版本锚定，事后无法回答「这个结论是基于哪一版规则得出的」。

**方案**：版本号缺失不得静默。改为记录版本解析失败事件并计入诊断，运行报告输出「版本锚定失败 N 条」汇总项。审计链写入时若为 unknown，需显式标记该记录的锚定状态。

**验收标准**：
1. 构造版本表不可用场景，断言审计记录被显式标记为版本锚定失败
2. 断言运行报告输出该汇总项且数值与审计记录数一致
3. 正常路径版本号写入不变

**原因**：可追溯性是审计链的核心承诺，`unknown` 使该承诺在局部失效。

**价值**：保证每条审计记录都能回答「依据哪一版规则」，这是结论进入后续程序时的基本资格。

### REQ-G-001　派生属性缓存失效令牌异常路径修正

> **核验修正（2026-09-05，基于代码逐行核对）**：本条原列 P0、定性为「缓存键塌缩导致主体串号」。经核验该后果不成立，**降级为 P1**，问题重述如下。编号 REQ-G-001 保持固定不变。

**问题（已修正）**：`core/derived.py` 的 `until_source_change` 缓存以 `params_hash` 为缓存字典键、以 `_source_version_set()` 返回的「本体版本号::对象行数」为失效令牌。取版本号失败置 `unknown`、行数查询失败置 `0`，两者同时失败时失效令牌恒为 `unknown::0`。

**对原结论的更正**：缓存字典键是 `params_hash`，而 `compute()` 在计算前把 `obj_pks` 并入 `params`（`params.setdefault("obj_pks", ...)`）。不同对象的 `obj_pks` 不同 → `params_hash` 不同 → **不可能跨对象取到对方的缓存值，原「对象 A 与 B 获得同一派生属性值 / 主体串号 / 查错人」在机制上不成立**。`unknown::0` 不是跨对象碰撞键，而是同一键的失效令牌。

**真实后果**：版本表与行数查询双双异常时，失效令牌在异常期间恒为常量 `unknown::0`，`until_source_change`「版本变化才重算」的判定永不成立——同一 `params_hash` 会持续复用**自身**陈旧缓存值、不触发重算（性质是陈旧读 / 该重算不重算，而非串号）。另需说明：截至核验时，全仓库 `until_source_change` 策略**仅 `tests/test_derived.py` 使用，无任何生产注册**，故为潜伏缺陷，当前无线上数据受影响。

**方案**：异常路径不得产生常量失效令牌。版本号缺失时改用带对象类型与随机（或单调）标识的一次性值（如 `unknown::{obj_type}::{uuid4}`），使其与任何历史令牌都不相等，强制走重算分支；异常本身计入诊断（与 REQ-G-007 的版本锚定失败留痕合并出口）。

**验收标准**：
1. 构造版本号与行数双失败场景，断言**同一对象**连续两次计算得到的失效令牌**不相等**、结果缓存标记为 miss（每次强制重算）
2. 断言该场景缓存命中率为 0
3. 断言异常被记录进诊断输出
4. 回归断言：不同对象（不同 `obj_pks`）的 `params_hash` 本就不相等，确认跨对象隔离成立
5. 正常路径缓存命中行为不变（`test_derived` 与 golden 用例全绿）

**原因**：原定性把「失效令牌恒常量」误读为「缓存键跨对象碰撞」。前者导致自身陈旧值不重算，后者才会串号；二者机制不同，处置优先级也不同。

**价值**：消除源异常期间派生属性该重算不重算的隐患；同时纠正「主体串号」误判，避免按错误定性投入处置资源。

### REQ-G-022　py 实现 Function 的结果路径导致规则静默不命中

> **补登记（2026-09-05，实施后追录）**：本条在交通违章数据源接入打磨期间发现并修复（commit `e53efad`），详见 REQ-G-REV.md 第一节。

**问题**：`core/rules.py` 执行规则时只读取 SQL 实现的 `out["rows"]`；而 py 实现的 Function 经 `invoke()` 把结果包在 `out["result"]` 里（`out["result"]["rows"]`）。挂载 py impl + `rows_nonempty` 判据的规则（R5 规则知识、R7 交通违章时空碰撞）永远读到空行。

**后果**：与 REQ-G-002 同源的沉默失败，且后果更重——两条规则在产物里**永不命中且零诊断**：没有零命中分类、没有降级标记、庙算维度覆盖仍显示通讯/行为「已覆盖」。这正是 REQ-G-002 所警告「这个方向根本没扫」与「查过了没问题」无法区分的真实实例。

**方案**：`rules.py` 兼容两条结果路径——`out["result"]` 为含 `rows` 键的 dict 时读 `result["rows"]`，否则回落 `out["rows"]`。

**验收标准**：
1. py impl + `rows_nonempty` 规则可正常命中（实跑 R5 命中 3 条、R7 命中 6 条）
2. SQL 实现路径（`out["rows"]`）行为不变，既有规则回归全绿
3. golden/baseline、rulezerodiag、r5knowledge 测试组全绿

**原因**：SQL Function 与 py Function 是同一挂钩的两种实现，结果包装形态不同却只消费一种，等于半数实现形态在规则层隐形。

**价值**：修复后 R5/R7 从「永远零命中的死规则」恢复为有效检测能力；同时印证 REQ-G-002 的零命中诊断是此类缺陷唯一的暴露口。

**状态**：**已实施**（commit `e53efad`，2026-09-05）。

### REQ-G-025　处置动作未落持久审计链，空链自检假阳性

> **登记（2026-09-05，代码逐行核对 + 真实库实测；登记当日修复）**：与 REQ-G-022 同形态——接口提供了能力，消费方没接上，而失败完全静默；且自检返回"正常"，比没有自检更危险。

**问题**：
1. **接线缺失（根因）**：`LineageClue.set_status()` / `set_filed()` 提供 `audit_chain` 形参（传入即同步落持久哈希链），但写操作唯一入口 `ActionExecutor._apply()` 的两处调用均未传——`clue.set_filed(operator, params["legal_basis"])` 漏第三参、`clue.set_status(target, operator=, note=)` 漏 `audit_chain`；`ActionExecutor` 构造签名 `(store, pack, access, health)` 根本不持有 AuditChain。处置看板五个动作（verify/exclude/confirm/file 等）全部经 `_apply()`，**全部受影响**。
2. **内存与持久链脱节**：`set_status()` 中内存 `audit_log.append()` 无条件执行，`audit_chain.append()` 在 `if audit_chain is not None` 门控内；状态赋值 `self.status = target` 也在门控外。故内存日志、看板状态、控制台「法定依据入审计链」提示一切正常，持久链为空。
3. **空链假阳性**：`chain_integrity()` 对空表计算 `expected = max(seq, default=0) = 0`、`actual = 0`，`chain_ok = (无断链) and (无缺字段) and (0 == 0) = True`，且不进入任何报警分支（run_diagnostic 零记录）。

**实测证据**（2026-09-05，可复跑）：
- 真实库 `investigation.duckdb` 的 `audit_chain` 共 50 行 = 48 条 proposal 事件 + 2 条 export 事件；**线索处置状态变更事件 0 条**（`after_state` 含 `legal_basis` 的 0 条、纯 status 事件 0 条）。
- 全新内存库经 `ActionExecutor.execute('verify', ...)` 执行成功后：线索内存 `audit_log` 有 1 条、status 已变更为「查证中」，但 **audit_chain 表从未被创建**（该路径不实例化 AuditChain）。
- 空库 `chain_integrity()` 返回 `{'chain_ok': True, 'expected_count': 0, 'actual_count': 0, ...}`，run_diagnostic 0 条。
- 测试盲区：`test_audit_chain.py` 把"不传 chain → 链 0 行"当作**向后兼容预期**固化，无任何测试断言"经 ActionExecutor 处置后链上有记录"。

**后果**：
- 所有处置状态变更——包括「已立案」这个 human 专属受控终态（需 legal_basis、占位名拦截、权限三纪律层层设防）——**没有留下任何防篡改的持久记录**。事后无法回答"这条线索是谁、依据哪一版规则、何时置为已立案"。
- 防线最严的地方恰恰没有留痕；而健康度报告显示 `chain_ok: true`，用"正常"掩盖"什么都没记下来"。
- 这直接击穿 REQ-G-018 的立项目标——该条立项时已写明"记录数期望核对（该写的事件没写进来）"是仍缺项，本缺陷正是该缺口的真实爆发。

**方案**：
1. **接线（必须）**：`ActionExecutor` 持有/惰性构造 `AuditChain(self.store.conn, health=self.health)`，在 `_apply()` 两处调用传入（无 store 的内存/兼容路径回落 None，不抛错）；`execute()` 与两阶段 `dispatch()` 共用 `_apply()`，一处修复两路径同时生效。
2. **空链/缺类不再判完整（必须）**：`chain_integrity()` 区分两种空——本次运行**存在处置动作但链上无对应事件** → warning 诊断（`audit_integrity_gap`，reason 指明"处置动作未落链，属接线缺失"）；链全空且确无处置 → 不报或 info（纯查询运行合法），避免误报。
3. **补接线测试（必须）**：新增断言"经 ActionExecutor 处置后 audit_chain 新增对应事件、chain_verify 通过、file 事件含 legal_basis"；registry 层"不传 chain 仅内存"的兼容语义保持不变。
4. **治本（可选，评估后定）**：将 `audit_chain` 改为必填位置参数，使漏传在编译/调用期暴露；代价是同步改造 `test_disposal.py` 等依赖默认 None 的脚本与兼容约定，建议接线稳定后单独评估。

**验收标准**：
1. 经 `execute()` 执行任一处置动作后，`audit_chain` 新增 1 条事件（`after_state` 含目标 status、operator 具名），`chain_verify()` 为 true
2. 经 `execute('file', ...)` 置「已立案」后，落链事件 `after_state` 含 `legal_basis`，与内存 audit_log 条目一一对应
3. 两阶段路径 `dispatch()` 同样落链（复用 `_apply()`，不重复写）
4. 无 store / 内存路径下降级为不记录、不抛错（NullRunHealth 与无 conn 均不阻断）
5. 构造"本次有处置动作但链上无处置事件"场景，`chain_integrity()` 产出 warning 诊断且 `chain_ok` 不为 true；纯查询空链运行不报警
6. `test_audit_chain` 既有"不传 chain 仅内存"兼容用例行为不变；全量回归 70 组全绿

**原因**：`audit_chain` 可选默认 None 的设计给了"只写内存"的合法退路，但唯一的生产写入口恰恰走了这条退路而无人察觉；自检又以 `0 == 0` 给空链盖章。能力接上了、校验也写了，中间的接线断了，且断点两边都显示绿色。

**价值**：让「已立案」等终态处置真正具备防篡改、可回溯的资格——这是结论进入后续程序的基本前提；同时补上 REQ-G-018"期望记录数核对"的最后半段，使审计自检不再能被空链骗过。

**状态**：**已实施**（2026-09-05）。修复落地：`ActionExecutor._chain()` 惰性构造 AuditChain 并在 `_apply()` 两处状态变更传入（即时执行与两阶段 dispatch 共用，一处接线两路径生效；无 store 回落 None 不抛错）；`chain_integrity()` 新增处置事件识别与 `clue_disposal_status`/`action_request` 双证据源交叉核对，有处置痕迹而链上零事件判 chain_ok=false 并落 warning，纯查询空链不报警；新增 6 项 AC 测试（execute/file/dispatch 落链、无 store 降级、脱链告警、接线后无告警），test_dispatch_failclosed 精确计数断言改为按 kind 过滤（落链后无锚点库按 REQ-G-007 记 version_anchor_missing 属预期）。方案 4（audit_chain 改必填）按条目约定留待接线稳定后单独评估。

## P2　覆盖度实证化

> 当前覆盖度指标衡量的是「假设声称要覆盖什么」，不是「数据实际支撑了什么」。

### REQ-G-008　维度覆盖度改为实证口径

**问题**：维度覆盖度仅统计假设声明的维度，不校验该维度是否真产出证据。本案中 H3 声明覆盖「通讯+行为」，行为维度即被计为已覆盖，而 R4（唯一的行为维度规则）实际零命中。

**后果**：覆盖度报告显示 80%、无报警，而行为维度实际是空白。指标与实情脱节，制造虚假的完整感。

**方案**：维度覆盖度改为双轨并列——**声明覆盖**（现状口径，衡量假设设计完整性）与**实证覆盖**（该维度下确有 finding 产出才计入）。两轨同时呈现，不得相互替代。

**验收标准**：
1. 构造假设声明某维度但规则零命中，断言声明覆盖含该维度而实证覆盖不含
2. 断言两轨数值独立计算互不污染
3. 构造规则命中的场景，断言两轨均含该维度

**原因**：声称与实证是两个不同的问题。前者问「我们想到了吗」，后者问「我们看到了吗」，混淆二者会让前一个答案冒充后一个。

**价值**：让覆盖度指标从「衡量设计完整性」升级为同时能回答「实际证据版图有多大」。

### REQ-G-009　报警阈值边界修正与缺口明细

**问题**：报警判据为 `score < 0.8`（严格小于）。本案恰好等于 0.8，不触发报警。报警文案为通用的「假设覆盖不完整，建议补充数据或人工注入」，不指出缺哪个维度。

**后果**：边界值恰好逃过报警；即便报警，也无法从文案得知缺口所在，需人工反查。

**方案**：阈值判据改为小于或等于（`score <= 0.8` 即报警）。报警文案改为枚举具体缺口维度名称与对应规则命中情况。

**验收标准**：
1. 构造 score 恰为 0.8，断言 alarm 为 true
2. 断言 alarm_text 含缺失维度名称
3. 断言 score 为 1.0 时不报警（避免误报）

**原因**：边界值恰等于阈值是极常见情形，严格小于会让这一类全部漏报。

**价值**：堵住边界漏报，并把笼统提示变成可执行的具体指向。

### REQ-G-010　运行健康度报告

**问题**：运行产物缺少汇总视角——本次运行有几处降级、几条规则零命中、几个数据源被跳过、几条审计记录失去版本锚定。这些信息分散在代码各处，从未汇总。

**后果**：使用者拿到一份结构完整的报告，无从判断它缩水了多少。报告的完整性不会因底层缺失而少一个字。

**方案**：运行产物中新增健康度小节，汇总各类降级与跳过事件的计数与明细。**该小节位于报告首部，位于所有结论之前。**

**验收标准**：
1. 断言产物 JSON 含健康度小节且字段完整
2. 构造含 N 处降级的运行，断言健康度计数与实际降级数一致
3. 断言健康度小节在产物中位于结论字段之前

**原因**：使用者在读结论之前，需要先知道该用什么态度读。这是 REQ-G-002 至 REQ-G-007 的价值出口——没有汇总，前面的留痕就散落在日志里。

**价值**：把散落的降级信号收敛成一眼可扫完的健康声明，直接对抗虚假确定感。

### REQ-G-023　规则强度分级与 rule_text 名实相符

> **补登记（2026-09-05，实施后追录）**：本条在 R7 交通违章规则打磨期间发现并修复（commit `e53efad`），详见 REQ-G-REV.md 第二、三节。

**问题**：R7 规则文本（rule_text）声明了「强度分级（strong/weak）」判据，第一版实现未写任何分级逻辑——规则承诺分级、输出无分级，属规则手册化要根治的「名实不符」。且初版把窗口外对照组到访计入窗口判据，导致 1 条 weak 被虚报为 strong。

**后果**：判据与文本脱节使规则文本失去审计意义（AGENTS.md 原则：rule_text 随线索落产物、可审计）；窗口外计数虚增强度，直接违背「宁可低估、不可高估」的侦查口径——高估会把待核实材料包装成强信号误导判断。

**方案**：强度分级常量落地 `core/functions.py`（高频通行路段 / 非公开通行区两组正则，与 R7 rule_text 的 strong/weak 判据一一对应）；拆分 `visit_count_at_site`（窗口内，作判据）与 `visit_count_all_time`（全量，作背景）双口径，窗口外记录不进入判据；weak 信号不丢弃、只标注理由，保留作资金/通讯类线索的时空印证。

**验收标准**：
1. 分级判据与 rule_text 逐条对应，规则零命中诊断（REQ-G-002）可对该规则挂钩
2. 窗口外记录不计入窗口判据（演示数据 6 条命中全部回归 weak，无 strong 虚报）
3. weak 信号仍产出并携带标注理由，不被丢弃

**原因**：规则文本是写给人看的审计承诺，实现是机器执行的判据，二者不一致时系统对外呈现的推理过程即不可信。

**价值**：守住「名实相符」与「宁低估不高估」两条口径；weak 保留机制使弱信号不丢失、可作交叉印证材料。

**状态**：**已实施**（commit `e53efad`，2026-09-05）。

### REQ-G-024　实证覆盖缺口独立报警

> **补登记（2026-09-05，实施后追录）**：本条为 REQ-G-008/009 落地后的补强，需求全文见 REQ-G-fix.md，实施 commit `00fd2ac`。

**问题**：REQ-G-008 实现了声明/实证双轨输出，但报警只由声明轨决定——`alarm = (score <= 0.8)` 仅看声明覆盖；`empirical_missing`（实证缺口）算出后既无报警键、也不写诊断。本案声明覆盖 5/5（score=1.0）时，实证缺口（行为、时间两维零产出）不产生任何诊断，健康度仍报 healthy。

**后果**：双轨制只完成了一半——实证轨能看不能警。声明完整而实证空白的假设（最危险的「设计完美、实扫空白」情形）在报告里完全无标记，REQ-G-008「让指标回答实际证据版图」的承诺在报警层落空。

**方案**：

2. 新增 `record_dimension_gaps(dc, health)`：双轨缺口各自独立留痕，声明轨 source 为 `miaosuan:dimension`、实证轨为 `miaosuan:dimension:empirical`，互不门控；
3. `run_all.py` 接线：两轨缺口均写运行诊断，实证缺口经 REQ-G-019 异常通道转为待核实线索（级别恒待核实、needs_human_review 恒真、不参与升格）。

**验收标准**：
1. 声明 5/5、实证 3/5 时 `alarm=False` 而 `empirical_alarm=True`，报警文案枚举实证缺口维度
2. 实证覆盖率恰为 0.8 时报警（边界值），1.0 时不报
3. 两轨留痕互不门控：声明轨不报警时实证缺口仍写诊断
4. NullRunHealth（health=None）下降级为不记录、不抛错
5. 实证缺口异常线索不参与五间交叉升格
6. 全量回归 70 组全绿；真实管线现场健康度 healthy → degraded，实证缺口诊断落库

**原因**：声明轨回答「假设设计是否完整」，实证轨回答「数据实际支撑了什么」——后者才是侦查判断依据，用前者的报警门控后者，等于让「我们想到了」掩盖「我们没看到」。

**价值**：双轨制在报警层闭合；实证空白从「报告无痕迹」变为「健康度降级 + 待核实线索」，直接堵塞「声明完整即无遗漏」的误读路径。

**状态**：**已实施**（commit `00fd2ac`，2026-09-05）。同批随附修复 `core/rebuild_planner.py` f-string 反斜杠问题（Python 3.11 语法错误、CI 阻断，属缺陷修复非需求条目）。
**遗留**：`qi_zheng` 阶段 findings 未并入实证口径（「时间」维低估来源），方向安全但不准确，后续按阶段统计改进。

## P3　声明化配置

> 项目在语义层做到了「声明是数据、实现是代码」，但这一原则没贯彻到元数据层。

### REQ-G-011　侦查维度声明化

**问题**：五个维度（资金、通讯、行为、关系、时间）硬编码为 Python 类常量，且只是字符串标签，不是一等公民。系统里没有维度对象，没有维度与数据源的映射，维度不参与优先级排序、血缘去重或线索合并。

**后果**：加维度要改代码。更要紧的是，维度不承担任何计算职责——可任意增删改而不破坏功能，反过来说明它目前只是给人看的标签。

**方案**：新建 `dimensions.json`，由 `ontology_loader` 装载校验，与 objects.json 等并列。维度定义至少含名称、说明、关联数据源类型。装载器对未知维度沿用既有的未知名硬失败原则。

**验收标准**：
1. 断言 `dimensions.json` 存在且通过 loader 强校验
2. 断言引用未声明维度的规则被硬失败拒绝
3. 断言新增一个维度无需修改任何 Python 文件即可被规则引用并参与覆盖度计算

**原因**：与语义层设计原则保持一致。当前元数据层是明显的双标。

**价值**：消除一处双标，使维度体系可随案件包演进，并为 REQ-G-008 的实证口径提供结构基础。

### REQ-G-012　枚举空间配置化

**问题**：枚举空间的五个维度及其取值硬编码在 Python 中，主体维度直接写死了本案的四个人名与机构名。

**后果**：换个案子必须改代码。更关键的是，枚举空间是系统**唯一主动面向未知的机制**，其边界由硬编码决定——黑天鹅若发生在枚举维度之外，连「待补」的空格都不会出现。

**方案**：枚举空间定义移出代码，改为案件包内的声明文件，支持正兵运行时扩展维度与取值。保留传参覆盖能力。

**验收标准**：
1. 断言枚举空间定义来自声明文件而非代码常量
2. 断言新增一个维度取值无需改代码即出现在候补池
3. 断言自定义 space 传参仍可覆盖声明值

**原因**：系统所有的反遗漏机制都反映设计者的经验边界。把边界写死在代码里，等于让经验边界不可扩展。

**价值**：把「未知的未知」降级为「已知的未知」。范围扩大了，盲区落在圈外的概率就小了。

### REQ-G-013　五间映射声明化

**问题**：`_JIAN_MAP` 硬编码在 `functions.py`，新对象不会自动纳入五间交叉计算。

**后果**：新数据源接入后，即便语义表已建立、行数非零，也不参与交叉等级计算，需人工改代码加一行映射。

**方案**：在 objects.json 与 links.json 增加可选的间类声明字段，由 loader 做枚举校验，交叉等级函数改为遍历案件包而非读硬编码字典。

**验收标准**：
1. 断言新增对象并声明间类后，无需改代码即纳入交叉等级计算
2. 断言声明非法间类值被 loader 硬失败拒绝
3. 断言间类展示顺序与等级规则仍保持硬编码、不可配置

> **重要边界（红线）**：间类展示顺序与交叉等级规则（单源=观察、双源=线索、三源及以上=可立案依据候选）**必须保持硬编码，不可配置**。等级规则一旦可配置，整套防误判设计即形同虚设。

**原因**：新数据源接入的最后一处代码依赖。完成后，接入交通违章类数据源的代码改动数从三处降为零。

**价值**：兑现「换案件改 JSON 不动代码」的承诺。

### REQ-G-014　冷层建表按需声明推导

**问题**：`init_duckdb.py` 的建表清单与回退 schema 均为硬编码，且与 objects.json 的属性声明、bindings.json 的源列名存在重复——同一件事写了两遍。

**后果**：新数据源不在清单内即扫不到。且两处定义可能漂移，没有任何机制校验二者一致。

**方案**：改为从案件包推导建表语句——物理表名取 bindings 的源表名，列名取源列名，列类型由 objects 的属性值类型映射。预聚合表依赖具体业务表列，属温层优化，保持手工。

**验收标准**：
1. 断言新增数据源仅在 bindings 中声明即可生成对应空表
2. 断言推导出的列类型与语义层物化列类型一致
3. 断言预聚合表行为不受影响
4. 断言 `init_duckdb` 不引入对 core 的导入依赖（避免循环依赖）

**原因**：消除一处真实的重复定义。这与规则手册化要根治的「名实不符」是同一类病。

**价值**：新数据源接入的代码改动数降为零，且杜绝定义漂移。

### REQ-G-015　链接端点列名形式化

**问题**：`links.json` 只声明 `from_obj` 与 `to_obj`，未声明端点输出列名。实际各链接端点列名各异（`from_account`、`from_person`、`person_1`），导致图导出器无法通用化，每条边都是定制 SQL。

**后果**：新增链接必须同步改导出脚本，是三处硬编码中改动量最大的一处。

**方案**：`links.json` 增加端点列名声明，迁移现有链接的类型定义，导出器改为按声明通用生成。

**验收标准**：
1. 断言全部现有链接完成端点列名声明
2. 断言新增链接无需修改导出脚本即可导出
3. 断言导出结果与迁移前逐条一致（golden 比对）

**原因**：配置化的真正障碍不是硬编码本身，而是端点列名未形式化导致通用 SQL 无从推导。

**价值**：完成三处硬编码改造的最后一处，使图库能力自动跟随语义层演进。

### REQ-G-016　策略文件版本收口

**问题**：`policies.json` 的 schema_version 为 1，`case_knowledge.json` 无版本字段，其余声明文件为 2。根因是这两个文件由各自模块独立装载，不走 `ontology_loader` 的统一版本校验。

**后果**：当前不报错，但一旦后续把策略收口进统一 loader，会直接硬失败。属技术债。

**方案**：`policies.json` 版本号提至 2，`case_knowledge.json` 补充版本字段，二者纳入统一版本校验。

**验收标准**：
1. 断言全部声明文件版本号一致
2. 断言二者纳入 loader 校验后现有测试用例全绿
3. 断言版本不符时硬失败

**原因**：当前的不一致只是「尚未被校验」，不是「没有不一致」。

**价值**：消除一处会在未来某个时点突然爆发的隐患，成本极低。

## P4　可信度元能力

> 本组不直接产出线索，而是回答「这份报告能不能信」。

### REQ-G-017　人工推翻率告警

**问题**：规则运行时度量记录了人工推翻率，但该指标只被记录，未被监控，无告警机制。

**后果**：这是全系统唯一能间接暴露「规则系统性失效」的指标，目前处于闲置状态。

**方案**：为推翻率设定阈值，超过即产生告警级诊断并进入健康度报告。按规则粒度输出，便于定位是哪条规则跑偏。

**验收标准**：
1. 构造某规则推翻率超阈值场景，断言产生告警级诊断
2. 断言告警含规则标识
3. 断言未超阈值时不告警

**原因**：该指标不能告诉你黑天鹅是什么，但能告诉你「现在的规则可能整体跑偏了」。这是目前唯一具备此能力的通道。

**价值**：把闲置指标激活为主动防线。这是对抗「经验不足导致系统性误判」最实际的手段。

### REQ-G-018　审计链完整性自检（在既有 chain_verify 上扩展）

> **核验修正（2026-09-05，基于代码逐行核对）**：本条原述「当前无机制校验审计链」。经核验 `core/audit.py` 已存在 `AuditChain.chain_verify()`，故本条是**扩展既有能力**而非从无到有，验收标准相应区分「既有回归」与「新增」。

**现状（已有，勿重复建设）**：`chain_verify()` 已按 seq 顺序逐条重算 signature 并校验 `prev_hash` 衔接（`core/audit.py`），即哈希链连续性与篡改检出（原验收 1）**已实现**，由 audit / spec 测试组覆盖。

**仍缺（本项真实范围）**：
1. **记录数核对**：`chain_verify` 只校验链内自洽，回答不了「是否有该写的事件根本没写进来」。需引入期望记录数（各写路径应产生的审计事件）比对，差异可检出。
2. **必填字段完备性**：`operator` / `ontology_version` / `after_state` 等必填项缺失或为空时计数报告——尤其 `ontology_version=unknown`（见 REQ-G-007）应作为锚定缺失计入，而非签名通过即视为完好。
3. **结论出口**：完整性结论（记录数、断链数、字段缺失数）结构化输出至健康度报告（依赖 REQ-G-010），而非仅返回单一 bool。

**后果**：系统实际执行路径与它声称的执行路径可能不一致，而使用者无法验证。现有 `chain_verify` 能证明「写进来的记录没被篡改」，证明不了「所有该写的都写进来了、且字段完备」。这动摇了「可审计」这一核心承诺的后半段。

**方案**：把 `chain_verify()` 从单一 bool 扩展为结构化完整性自检——在既有签名 / 衔接校验之外，增加记录数期望核对与必填字段完备性扫描，返回 `{chain_ok, expected_count, actual_count, broken_links, missing_fields}` 之类的结论对象，并输出至健康度报告。保留原 bool 返回形态以兼容现有调用。

**验收标准**：
1. （既有，回归）哈希链连续性 / 签名校验可检出篡改——`chain_verify()` 现有行为不变
2. （新增）必填字段缺失或为空（含 `ontology_version=unknown`）被检出并计数
3. （新增）实际记录数与期望不符时给出差异
4. （新增）完整性结论进入健康度报告

**原因**：审计链是系统对外的核心承诺。承诺本身若有洞，其他能力再强都少了底气；但已实现的部分（防篡改）应如实承认，补的是「完备性」这半段。

**价值**：让「每步可溯源、可被质疑、可被推翻」这一主张可验证，而非仅有形式。

### REQ-G-019　异常线索通道

**问题**：系统擅长表达「我们发现了什么」，不会表达「我们没能看什么」。缺失没有被当成一种结论。

**后果**：正向异常可被刻意规避，而规避行为留下的空白更难抹掉——但系统看不到空白，因此无从提示。

**方案**：建立平行于正常线索的异常通道——把零命中、匹配失败、覆盖缺口、健康度异常转化为待核实条目，与正常线索**同构**（同样携带溯源、同样进审计、同样进人审队列），但带两个强制标记：**级别恒为待核实、needs_human_review 恒为真**。

**验收标准**：
1. 断言异常条目与正常线索数据结构同构且携带 `source_rows`
2. 断言异常条目级别恒为待核实、`needs_human_review` 恒为真
3. **断言异常条目不参与五间交叉等级计算**（构造异常条目后等级不变）
4. 断言异常条目按主体聚合输出

> **关键约束（红线）**：异常线索**绝不能**参与五间交叉等级计算。交叉等级逻辑为「非空即命中」，若异常也能贡献命中，则「缺的东西越多，等级越高」——会让数据最不完整的报告看起来最像可立案。异常通道应标注健康度，不参与升格。

**原因**：让系统具备回答「我们还有什么没看到」的能力，这是庙算的本意。

**价值**：本清单中业务价值最高的一条。它把修复后的异常从噪音转化为矿。

### REQ-G-020　动作派发失败遵循 fail-closed

**问题**：`action_executor.py` 中捕获 `ImportError` 后，将动作状态设为 `dispatching`（派发中），而实际写入发件箱失败、什么都没发出去。

**后果**：从台账看程序在流转，实际卡住。业务上称**程序空转**，比程序停摆更难发现。同时违反项目自己确立的 fail-closed 原则（缺失即拒绝）。

**方案**：改为显式标记派发失败状态，并产生告警级诊断。不得用进行中状态掩盖失败。

**验收标准**：
1. 构造发件箱模块不可用场景，断言状态被标记为派发失败而非派发中
2. 断言产生告警级诊断
3. 断言正常路径状态流转不变

**原因**：与设计原则自相矛盾。项目在权限层严格执行 fail-closed，此处却用乐观状态掩盖失败。

**价值**：消除一处原则性不一致，避免程序空转被误认为正常流转。

## P5　新能力

### REQ-G-021　地点标准化与空间匹配能力

**问题**：现有同框匹配采用字符串精确相等（`t1.location = t2.location`）。无模糊匹配、无地名标准化、无地理编码能力。

**后果**：交通违章记录中的地点为交警系统录入的文字描述（如「某路与某路交叉口东侧 50 米」「某高速下行 K12+300」），项目地点来自招投标档案。用精确相等匹配二者，**碰撞失败不是可能，是必然**。这不是数据缺失问题，是匹配能力根本不存在。

**方案**：引入地点标准化层——地址解析与别名归一，或引入地理编码把文字地址转为坐标后按距离阈值判定。在此之前，任何基于「地点重合」的规则都是空转。

**验收标准**：
1. 断言「滨江路中段 K3+200」与「滨江路」可判定为同一地点或距离小于设定阈值
2. 断言完全无关的两个地点不误判为重合
3. 断言该能力可被规则通过 function 挂钩调用
4. 断言无坐标数据时不报错而是降级标注

**原因**：这是 REQ-G-002 与 REQ-G-003 能真正发挥作用的前提——没有匹配能力，诊断只会持续报告「匹配失败」，无法转为有效线索。

**价值**：解锁整个行为维度。当前该维度唯一的规则从设计上即不可能命中，补上此能力才谈得上行为证据分析。

# 实施建议

## 优先级划分依据

优先级按「后果的不可逆性」而非「修复难度」排序。一个会导致查错人的缺陷，即使触发条件苛刻，优先级也高于一个每天都在发生但只影响可读性的问题。

> **核验修正（2026-09-05，基于代码逐行核对）**：原列 P0 的 REQ-G-001「缓存键塌缩导致主体串号」经核验不成立——缓存字典键 `params_hash` 已含 `obj_pks`，不同对象键本就不同、不跨对象碰撞；真实缺陷是失效令牌在异常路径恒为常量导致自身陈旧值不重算，且该策略当前无生产注册。REQ-G-001 已**降级 P1**。**本清单当前无 P0 项**；P0 档位定义保留，供后续若发现真正「错误数据不可逆扩散」类缺陷时归位。

| 优先级 | 主题 | 判定依据 |
|---|---|---|
| P0 | 数据正确性 | 会造成错误的业务数据扩散，且错误不可自查（**当前无归属项**；原 REQ-G-001 经核验降 P1） |
| P1 | 失败可见性 | 系统当前最大的能力缺口，直接导致「沉默的失败」 |
| P2 | 覆盖度实证化 | 当前指标衡量「声称」而非「实证」，会制造虚假确定感 |
| P3 | 声明化配置 | 决定新数据源接入成本，影响长期可维护性 |
| P4 | 可信度元能力 | 不直接产出线索，但决定报告能否被信任 |
| P5 | 新能力 | 无此能力则部分业务规则从设计上即不可能命中 |

## 推荐实施顺序

| 批次 | 需求 | 依赖 | 完成标志 |
|---|---|---|---|
| 第一批 | REQ-G-002 至 REQ-G-007、REQ-G-010、REQ-G-001 | 无 | 运行报告出现健康度小节，六类静默点全部留痕；派生缓存异常失效令牌非常量、强制重算（test_derived/golden 全绿） |
| 第二批 | REQ-G-008、REQ-G-009、REQ-G-016、REQ-G-017、REQ-G-018、REQ-G-020 | 第一批（留痕是实证口径的数据来源） | 覆盖度双轨输出，边界值可报警，审计链完备性自检（在既有 chain_verify 上扩展记录数/字段完备性） |
| 第三批 | REQ-G-011 至 REQ-G-015、REQ-G-019、REQ-G-021 | 第二批（异常通道依赖健康度数据） | 新数据源接入零代码改动，异常可转为待核实条目 |

## 三条不可突破的边界

1. **交叉等级规则**（单源=观察、双源=线索、三源及以上=可立案依据候选）与间类展示顺序必须硬编码，不可配置。等级规则一旦可配置，整套防误判设计即失效。

2. **异常线索不得参与五间交叉等级计算**，不得自动升格为已核实。只有人能区分「数据缺失」与「刻意规避」，这个区分错了，代价是查错人或漏掉线索。

3. **未知名硬失败原则不得放宽**。本清单要求的是「失败可见」，不是「失败容错」——把静默改为留痕，不是把硬失败改为放行。

## 一句话总结

这 25 项需求动机高度一致：项目为保证管线不中断，在多处使用了 try/except 或 continue，但处理方式只有「吞掉」，没有「降级标记」。（原列 21 项；REQ-G-022 至 024 为实施阶段补登记、025 为核查发现待实施——G-022 与 G-025 同为「吞掉」型沉默失败的真实实例：前者是 py Function 结果路径未读致规则永不命中，后者是 audit_chain 漏传致处置动作永不落链。）

真正要补的不是异常处理语句，而是**一套统一的降级协议**——失败必须留下可查的痕迹，而不只是让程序继续往下跑。

项目里已有三处做对了：语义表缺失返回 `degraded`、血缘合并写 `merged_from`、双轨比对不一致打印告警。共同点是**失败被表达成了数据**。

建议以这三处为样板固化成协议，再逐点改造。这样 25 项需求就不是 25 个补丁，而是一次统一的能力升级。
