## 一、现状核查（事实基线）

```
对象类型 14（ontology/default/objects.json）
  person / org / account / person_identity / transaction / call
  trackpoint / location / bid_project / clue / decision
  tipoff / osint_article / image_evidence          ← 无 item

链接 14（links.json）　无一条涉物品
  transfers(account→account, amount/date)、co_located(person→person, location/date)
  trackpoint_at(trackpoint→location, date)、time_window(bid_project→transaction) …

维度 6（dimensions.json，code 为机器标识）
  fund(transaction) / comm(call) / behavior(trackpoint)
  space(trackpoint, location) / relation(person, org) / time(transaction, call, trackpoint)

间类 5（packs/wujian/jians.json）source_object_types 涉
  org / bid_project / tipoff / call / trackpoint / transaction     ← 无物品

包 5：geo / relation / timeline / vlm / wujian                     ← 无 item 包
```

**结论**：物品缺失不是画布接线问题，是**本体层结构性空白**——与"组织没上画布"（本体有、三处断链）性质不同，物品是本体层就没有。

### 关键可复用资产（降低工作量）

- `location` 已有 `lat/lng/coord_sys/geocode_source/geocode_confidence` → **地点精度档现成**，物品落图直接复用，不另造口径
- `trackpoint` 为 `kind=event`、`person_raw/location/date/timestamp` → 物品轨迹可复用同一对象，无需新建轨迹类型
- `person_identity` 已声明 `identity_key=["raw_name","id_card"]` → 复合身份键机制已跑通，物品照做
- 空间研判能力（轨迹分段/时空伴随/异常检测/活动范围）只耦合 `trackpoint→location`，**未限定必须关联 person** → 有一半潜力未被对象模型释放

## 三、需求（R1–R14，逐条可跟踪、可单测）

### 建模层

**R1 `item` 对象类型入本体**
新增 `objects.json: item`，`kind=entity`，属性：`item_type`、`identifiers[]`、`title`、`holder_raw`、`acquire_date`、`dispose_date`、`descriptors{}`、`location`、`lat/lng`、`coord_precision`。
验收：装载期无交叉校验失败；`item` 可被 links/jians/dimensions 引用。
测试：T1（声明合法）、T2（未声明引用硬失败）

**R2 `item_type` 枚举由行业包声明**
`item_type` 取值走 `enum_space`，default 本体给出通用枚举（vehicle/realestate/invoice/drug_batch/device/portable/goods_other），行业包（金融/医疗）可扩展。
验收：行业包可追加取值且不改 Python；未声明取值装载期硬失败。
测试：T3（扩展生效）、T4（未知取值失败）

**R3 标识符结构 `identifiers[]`**
每项 `{kind, value_digest, sensitive, issuer, verified}`。`kind` 枚举：plate / property_cert / invoice_code_no / imei / msisdn / batch_no / serial / none。
验收：同一 item 可挂多标识符；`kind=none` 仅用于 D4 类物品。
测试：T5（多标识符）、T6（none 类不参与消歧）

**R4 时态持有边**
新增链接 `holds(person→item)` 与 `item_transfer(item→item 或 person→person)`，properties 含 `start_date`、`end_date`、`basis`、`precision`。
`end_date` 空表示"当前仍持有"。
验收：同一 item 在不同时间可指向不同持有者，且查询结果**按时间过滤**（见 D8 前置验证）。
测试：T7（时间区间过滤生效）、T8（未闭合区间视为当前持有）

**R5 物品复用 `trackpoint` 与 `location`**
`trackpoint` 增加 `item_raw` + `holder_type`（person/item）；`location` 不改动，直接复用 `geocode_confidence` 作精度档。
验收：物品轨迹与人员轨迹走同一套对象；空间镜头无需区分主体类型即可跑通。
测试：T9（物品轨迹入分段）、T10（精度档随 geocode_confidence）

### 消歧层

**R6 物品身份键（复合）**
`item.identity_key = ["item_type", "identifiers.primary_digest"]`，与 `person_identity` 同机制（`core/ontology.py` 装载期）。
无凭证类（D4）不设 identity_key，只按 `descriptors` 建描述性实体。
验收：同牌号不同车（若另有判别证据）可分列；同牌号无反证则保持合并并留诊断。
测试：T11（复合键生效）、T12（无反证不静默拆分）

**R7 抗辩式冲突检测（不复用 homonym）**
新增 `core/item_conflict.py`：同一 item 在同一时刻出现在**物理不可达**的两地 → 输出**线索**（套牌/改号嫌疑），而非"消歧失败"。
判据复用空间侧既有不可达判据（距离 > 速度上限 × 时间差）。
验收：输出为待核线索，措辞不得含"可疑""涉嫌"等定性词。
测试：T13（200km/同刻 出线索）、T14（正常位移 不出）、T15（无定性措辞）

**R8 精度档贯通**
物品相关的每条证据必须带 `precision`（minute/date/none），与空间/时间侧同一套取值。
验收：缺失 precision 的证据不得进入打分。
测试：T16（缺失即降级或拒绝）

### 接入层

**R9 维度归属（不新增维度）**
`space.source_object_types` += `item`；`fund` += `invoice` 类；`comm` += 设备/号码类。维度总数保持 6。
验收：`dimensions.json` 维度数仍为 6；覆盖度统计纳入物品证据。
测试：T17（维度数仍为 6）、T18（物品证据进覆盖度）

**R10 镜头供给**
新增 `item` 包（或并入 wujian）提供镜头：物品轨迹分段、物品—人共现、持有链回溯、同号多点冲突。
镜头声明 `uses_functions`、`auto_from`（靶心自动带入）、`assumption`、`produces_dims`。
验收：镜头可在画布被调度（`canvas_enabled`）；参数类型非法不导致整包加载失败。
测试：T19（参数类型合法）、T20（非法类型不拖垮整包）

**R11 画布节点语义扩展**
`subject` 节点支持 `person / org / item` 子类型；`MANUAL_NODE_KINDS` 扩 `subject`（前后端各一份，沿用现有单测对拍）。
验收：可从 object 节点「提升为研判主体」，提升后锚定 `pk`，幂等（同一 pk 不建第二个）。
测试：T21（提升幂等）、T22（锚定 pk 而非随机 id）、T23（前后端 kind 集合对拍一致）

**R12 标签真相源 `label_of()`**
定义单一 `label_of(node)`：`label` 显式字段优先 → 按对象类型取声明的标题属性（`person.raw_name`、`bid_project.title`、`item.title`…）→ 末位兜底 `pk`。
回填期保留现有 `name or pk` 猜测作兜底（D7），**但禁止新增猜测点**。
验收：三处既有猜测点改为调用 `label_of()`；`bid_project` 能取到 `title`（当前猜测口径对其落空）。
测试：T24（bid_project 取到 title）、T25（item 取到 title）、T26（`label` 显式优先）

### 合规层

**R13 敏感标识复用既有机制**
物品标识符中属个人信息的（msisdn、imei）声明为 `sensitive=true` 的数据元，并在 `policies.json property_policies` 声明 `mask`/`default`/`allow_roles`。
**复用** `DE_*` + policies + 装载期 fail-closed 校验，不新造脱敏模块。
验收：声明 sensitive 但未在 policies 声明遮蔽 → 装载期硬失败（现有 AC-4/AD-5 自动生效）。
测试：T27（未声明遮蔽硬失败）、T28（已声明可按角色放行）

**R14 摘要口径**
缓存、日志、观察摘要一律存 `value_digest`（哈希），不落明文；明文仅在授权角色下读取。
验收：全库搜索物品模块输出，不得出现明文标识符。
测试：T29（日志/缓存无明文）

### 凭证与合规补全（v1.1 新增）

**R15 组织凭证 `credit_code`（D10）**
`org` 新增属性 `credit_code`（统一社会信用代码，18 位，GB 32100-2015），并声明 `identity_key=["raw_name","credit_code"]`。
- 公开信息，**不标 sensitive**（与 `DE_IDCARD` 区分）；校验位不合法标 `verified=false`，**不硬失败**（避免脏数据拖垮装载）
- 无 `credit_code` 的组织（未登记主体）沿用 D4 精神：**不进自动消歧**，保持合并并留诊断
- 已知边界：同码不同名（更名）、同名不同码——均靠 `credit_code` 区分，不靠名称
验收：两个同名组织若 `credit_code` 不同可分列；无 `credit_code` 者不静默拆分。
测试：T31（同码不同名不误合）、T32（无码不进消歧）、T33（校验位非法标 unverified 不硬失败）

**R16 手机号设敏感（D11）**
`DE_PHONE` 标 `sensitive=true`，并在 `policies.json property_policies` 声明 `mask`/`default`/`allow_roles`（否则装载期 fail-closed 硬失败）。
**连带口径**：遮蔽后明文不可用于关联，关系分析的 join 键改用 `digest`，不得用部分遮蔽后的明文串做匹配（会产生错配）。
**影响面**：既有通话链路的遮蔽行为随之改变，I22 必须先回归通话关系分析再继续。
验收：声明 sensitive 但未在 policies 声明遮蔽 → 装载期硬失败；遮蔽后关系分析仍可正确 join。
测试：T34（未声明遮蔽硬失败）、T35（遮蔽后按 digest join 不错配）

## 五、红线（单测守死）

1. **不新增"物品"维度** —— 维度数恒为 6（T17）
2. **物品重号是信号不是噪声** —— 物品不得调用 `homonym.py` 的 person 裁决入口（T13）
3. **无凭证物品不进自动消歧、不进交汇打分** —— 否则给伪精确（T6）
4. **系统不得定性** —— 冲突检测只说"同一标识同一时刻出现在物理不可达两地"，不说"套牌"（T15）
5. **明文标识符不落缓存/日志** —— 一律摘要（T29）
6. **不静默挑一个** —— 多候选标歧义、留候选清单（T12）
