## Implementation Steps（依赖顺序）

**第一并行波（互相无依赖）：REQ-025 / REQ-027 / REQ-028 / REQ-029 / REQ-030**

1. **REQ-025 规则互斥与重叠消解**
   - Step 1.1：`ontology_loader.py` — Rule dataclass 加 `exclusive_group: str | None` / `primary_rule: bool` / `overlap_resolution: str | None` / `excludes: list[str]`；装载期解析 rules.json 新字段；装载尾做 **excludes 双向一致性核对**（A→B 但 B→A 不写 warning log，不硬失败，AC2）；装载期校验 exclusive_group 内最多一个 `primary_rule=True`。
   - Step 1.2：`rules.json` — R1（季度末整数存现，归 primary）、R2（整数转账聚合，非 primary，排除 R1）、R6（中标时间窗整数资金，独立组）标注 exclusive_group="integer_amount" / overlap_resolution="drop_if_primary_hit"。
   - Step 1.3：`core/rules.py` — 抽取 `_evaluate_single(rule, fx, out)` 为单规则评估；线性跑后调用新函数 `_suppress_overlaps(findings, rules)`：按 group 分组，若 primary 命中则该组非 primary 全部进 `suppressed_log`，并从 findings 主列表移除；finding 结构新增 `_suppressed` / `suppressed_log`（AC3 AC5）；suppressed_log 每项 {rule_id, suppressed_by_group, suppressed_by_rule, reason, 级别, 候选虚处}。
   - Step 1.4：写 `tests/test_rule_overlap.py` — AC1 组内 primary 命中抑制；AC2 excludes 单向装载告警；AC3 suppressed_log 存在且审计完整；AC4 无 group 的 R3/R4/R5 行为不变；AC5 产物落盘字段含抑制原因。单测全绿后进入下一步。

2. **REQ-027 阈值策略对象（分位数自适应）**
   - Step 2.1：`thresholds.json` — 声明 R1（absolute round_unit 10000）、R2（absolute transfer_aggregate_min 100万）、R3（relative_median multiplier=2.0 min_samples=20 fallback=30 bounded 5~1000 per=subject）、R4（absolute co_loc_window_days=1）、R5（absolute —— 知识包，无阈值）、R6（absolute within_days=20）。
   - Step 2.2：`core/threshold.py` — `load_thresholds(pack)` 读 JSON；`ThresholdStrategy.resolve(store, rule_id, sample_rows)` 应用策略：relative_median 使用 FeatureStore 历史或 sample_rows 计算中位数×multiplier；不足 min_samples → fallback 值，标记 is_degraded=true；bounded_by clamp 上下界；per=["subject"] 按分组算。`apply_params(params, strategy)` 把自适应值写进 rule params（替换硬编码常量）。
   - Step 2.3：`core/rules.py` — run_rules 循环前，对每条 rule 调用 `ThresholdStrategy.resolve(...)` 将 params 内的阈值替换为计算值；finding 字典写入 `threshold_method` / `threshold_value` / `is_degraded`（AC5）。

## Dependencies and Considerations

- **REQ-025 不破坏既有 finding 结构**：新增字段（_suppressed / suppressed_log / threshold_method / threshold_value / is_degraded）仅 append，不改变现有关键字段（rule_id / 级别 / source_rows），下游 lineage / disposal / export 不会坏。
- **REQ-027 阈值策略**：`absolute` 声明等价于原有硬编码值，旧行为向后兼容。`relative_median` 只在 FeatureStore 已有样本的 R3 激活，其他规则全 absolute 不变。
- **REQ-028 / 029 隔离性**：新模块不改动 gateway / ontology 编译链；它们是"上层便利 API"，未被 run_all / MCP 直接接线，本批只保证单测全绿 + 接口断言通过。
- **REQ-030 写路径**：rule_run_metric 建表走 `ensure_rule_run_metric(conn)`（类似 ensure_runtime_tables，编译器不会 DROP）。record_run 是写动作但走 Store.execute，本模块不走 ActionExecutor（纯运行元数据，不是"处置写动作"）。
- **REQ-026 的 within_days 语义**：R6 命中自带 ±20 天命中窗口，`within_days` 在 DSL 里是"复合条件"额外时间窗约束（比如 finding A 的 date ≤ finding B 的 date + within_days）——走 source_rows 的日期字段 min/max 比较，不改动 rule 自身 SQL。
- **最小化侵入**：6 个 REQ 共 5 个新文件（threshold/derived/object_set/metrics/rule_dsl）+ 4 处改（loader/rules/rules.json/run_tests）+ 2 处新建 JSON（thresholds.json）。绝不乱改既有模块。
- **范围控制**：按经验 157140，**绝不顺手扩展**（例如 DS L 不做 OR-of-AND 以外语法糖、ObjectSet 不做 aggregate 复杂函数、DerivedProperty 不做 cross-object join），严格按验收标准的 AC 条实现。

## Risks

- **R1-R2 抑制导致 finding 数量下跌**：run_all 原有"9 条线索"可能变成 8 条。应对：在 tests/test_run_all.py 中先更新期望数到"8"并在交接文档明确"抑制是预期行为，不是 regression"。若 golden baseline 的 finding 数量从 4 变到 3（R2 被 R1 抑制），则需要同步刷新 tests/fixtures/golden/baseline.json expect —— 这属于 golden 基线的**有意升级**，不是 bug。
- **REQ-027 相对中位数样本不足**：FeatureStore 可能空（首次跑无历史），is_degraded=true 走 fallback 30，行为与原一致。风险低。
- **ObjectSet AST 误判 SQL 注入**：若 predicate 值里含 "SELECT" 字符串（比如人名字段），不能被误判为注入。应对：注入防护在 AST **节点类型** 检查（Eq 两边必须是 str/primitive），不是对值做 LIKE 扫描。
- **Rule DSL within_days 取日期字段**：不同 finding 的 source_rows 列名不一（R1 是 DATE(日期)、R6 是 lnk 日期）。应对：先在每个 finding 中取 source_rows 首行，寻找 `"日期"/"中标公示日"/DATE` 列，找不到就 DSL 视为"日期未知" → within_days 默认不通过，不崩。
