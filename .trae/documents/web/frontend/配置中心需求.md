## 一、先说原则：不是所有东西都该配置化

### 1.1 一条反直觉的警告

很多团队过度配置化，最后**配置比代码还难维护**。这套系统尤其危险：

> 执法场景下，配置错误不是"功能异常"，而是**证据可采性存疑**。

如果规则阈值今天一个值、明天一个值，同一批数据得出不同结论，法庭上会被质疑。所以配置化的前提是——**每次变更可追溯、可回滚**。

### 1.2 四条判断标准

一个东西该不该做成配置，问四个问题：

| 问题 | 若答"是" |
|---|---|
| 改动后会让某条红线失效吗？ | **不可配** |
| 改动后会影响结论的可采性吗？ | 可配，但需审批+审计 |
| 不同单位/案件的需求确实不同吗？ | 可配 |
| 只是个人使用习惯吗？ | 可配，用户级随便改 |

## 二、四层配置金字塔

```
        ▲
       /L0\      红线层 —— 硬编码，测试锁定
      /────\
     /  L1  \    策略层 —— 可配，需主办审批 + 审计留痕
    /────────\
   /   L2     \  运营层 —— 管理员可配，需留痕
  /────────────\
 /     L3       \ 偏好层 —— 用户自配，随便改
└───────────────┘
```

| 层 | 内容 | 存储 | 审批 | 审计 | 回滚 |
|---|---|---|---|---|---|
| **L0 红线** | 12 条不可动摇的规则 | 代码常量 | — | 测试锁定 | 需发版 |
| **L1 策略** | 升格阈值、门禁门槛、规则阈值 | 后端 pack 配置 | 主办+ | **必记** | 版本化 |
| **L2 运营** | 并发、超时、资源、功能开关 | 后端 tenant 配置 | 主办 | 记 | 版本化 |
| **L3 偏好** | 主题、密度、列显隐、排序 | **前端 localStorage** | 无 | 不记 | 重置即可 |

## 三、L0 红线层：绝对不可配置

**这 12 条如果可配，就等于没有红线。**

| # | 红线 | 为什么不可配 |
|---|---|---|
| 1 | 已立案必须 human（AI 不可触发） | 配成"AI 可立案"= 系统失去存在意义 |
| 2 | 推断必挂 `source_rows` | 配成"可不挂"= 溯源链断裂 |
| 3 | 三栏物理分隔（不可合并） | 配成"可合并"= 事实与推断混淆 |
| 4 | 单源不升格 | 配成"单源可升格"= 孤证定案 |
| 5 | 推断栏禁用绿色 | 配成"可用绿"= 候选被误读为事实 |
| 6 | 权限 fail-closed 默认值 | 配成"默认放行"= 越权可见 |
| 7 | 登录错误统一文案 | 配成"提示具体项"= 泄露账号存在性 |
| 8 | `NOT_FOUND` 统一文案 | 配成区分 403/404 = 泄露资源存在性 |
| 9 | 敏感数据不落 localStorage | 配成"可缓存"= 合规事故 |
| 10 | 遮蔽在序列化前完成 | 配成"前端遮蔽"= 明文已到浏览器 |
| 11 | 实体裁决永不自动合并 | 配成"可自动"= 同名不同人被合并 |
| 12 | 跨案件全有或全无 | 配成"部分执行"= 越权数据混入结果 |

**实现方式**：写成常量 + 单元测试锁定。

```ts
// core/redlines.ts
export const REDLINES = Object.freeze({
  FILED_REQUIRES_HUMAN: true,
  INFERENCE_REQUIRES_SOURCE_ROWS: true,
  THREE_COLUMN_SEPARATED: true,
  SINGLE_SOURCE_NO_UPGRADE: true,
  INFERENCE_NO_GREEN: true,
  // ...
} as const)
```

配 `FE-T-011`：**红线常量不可被配置覆盖的测试**（尝试注入配置修改 → 必须失败）。

## 四、L1 策略层：可配但需审批+留痕

这层是**业务策略**，改动会影响结论，所以必须审批 + 进审计链。

| 配置项 | 当前值 | 危险等级 | 说明 |
|---|---|---|---|
| **五间升格阈值** | 双源升格 / 三源成候选 | 🔴 危险 | 调低 = 孤证可立案 |
| **状态迁移角色门槛** | 已立案 ≥ 主办 | 🔴 危险 | 调低 = 见习可立案 |
| **降级判定阈值** | 健康度 < X 算降级 | 🔴 危险 | 调低 = "结果不完整"提示失效 |
| **规则阈值** | 如 R-SM-004「20天7次」 | 🟡 谨慎 | 已在 `rules.json`，本就可变 |
| **置信度色阶分界** | high/medium/low | 🟡 谨慎 | 影响视觉判断，但不影响数据 |
| **敏感地点白名单** | — | 🟡 谨慎 | 图35 已有此功能 |
| **断言有效期默认值** | — | 🟡 谨慎 | 图35 时间轴 |

**🔴 危险项的特殊约束**：

1. 改动必须走 `ConfirmDialog` 二次确认
2. 必须填写**变更理由**（进审计链）
3. 提示**影响范围**：`此改动将影响 N 个案件 / M 条已有候选`
4. 必须可回滚（配置版本化）

> **降级阈值我倾向于不给配** —— 它能让"结果不完整"的警示失效，风险太大。若一定要配，建议只允许在保守区间内调整（如 70–85），不可低于 70。

## 八、配置 UI 的呈现原则

配置多了会失控，UI 上要做约束：

### 8.1 沿用原型已有的分组

图33/46 的左侧导航分组很好，直接沿用：

```
外观偏好      → L3 主题/密度/字号
任务队列      → L2 并发/重试
资源限额      → L2 行数/CPU/内存/超时
本体与标准    → L1 数据元/ETL/规则
审计与合规    → L2 日志级别/合规开关
权限与遮蔽    → L2 矩阵/规则 ← 建议新增加入
```

### 8.2 危险等级可视化

每个配置项标一个等级徽章：

| 徽章 | 含义 | UI 表现 |
|---|---|---|
| 🟢 安全 | 随便改 | 无特殊标记 |
| 🟡 谨慎 | 影响体验 | 提示"将影响所有用户" |
| 🔴 危险 | 影响采信度 | **红色边框 + 需填变更理由** |

### 8.3 变更前的三重提示

🔴 危险项改动时，ConfirmDialog 必须显示：

```
⚠️ 此改动影响证据可采性

影响范围：12 个案件 · 340 条已有候选
变更理由：[________________]（必填，将写入审计链）

[取消]  [确认变更]
```

### 8.4 未保存提示

图33/46 已有「设置已修改，尚未保存」+ 取消/保存按钮，**这个设计很好，保留**。

## 九、配置的版本化与回滚

### 9.1 为什么必须版本化

执法场景的核心要求：**结论可复现**。

> 三个月前基于当时规则得出的候选，今天要能解释"当时为什么这么判"。
> 所以配置必须跟本体版本一样，支持 🔒 锁定与历史回溯。

### 9.2 建议方案

```
配置快照 v1 ── 配置快照 v2 ── 配置快照 v3（当前）
     ↑              ↑              ↑
   案件A引用      案件B引用      新案件引用
```

- 每次 L1/L2 配置变更生成一个快照
- 案件记录当时使用的配置版本
- 历史结论可追溯到当时的配置

**这与已有的「本体版本 🔒 锁定态」是同一套机制**（`OntologyVersionTag` 组件），建议配置复用。

### 9.3 配置的导入导出

私有化多单位部署下很有用：

```
单位 A 调好的配置 → 导出 JSON → 单位 B 导入
```

与 `案件包` 类似机制（图37/50 已有导出/导入流程），**建议复用同一套校验清单 UI**。

## 十二、风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| **配置过度导致采信度受损** | 同一数据不同时间结论不同 | L1 强制审批+留痕+版本化 |
| pack 级配置改动波及多案件 | 改一次影响全部 | 变更前提示影响范围 |
| 危险配置被误改 | 红线失效 | 🔴 徽章 + 二次确认 + 理由必填 |
| 前端偏好丢失 | 用户体验回退 | 提供"重置为默认" |
| 配置与代码不同步 | 配置项失效 | 配置 schema 版本化，启动时校验 |

## 十三、一句话总结

> **L0 焊死，L1 留痕，L2 记录，L3 随便。**

配置化的价值是灵活性，代价是可追溯性。这套系统里，**可追溯性优先于灵活性**——所以每一层配置的严格程度，取决于它离"证据采信"有多近。

**最该做的一件事**：先落地 `FE-T-011`（红线不可被配置覆盖的测试）。有了它，后面怎么加配置都安全；没有它，加得越多风险越大。
