## 一、为什么用 MVP 式

按依赖分层排期（T0–T10）逻辑正确，但有个问题：

> **第 10 周才能看到第一个真实业务页面。**

前 9 周全在打地基，期间**没有任何可向业务方演示的东西**，风险全堆在后面才暴露。

| 对比 | 分层式 | **MVP 式** |
|---|---|---|
| 首个业务闭环 | 第 10 周 | **第 5 周** |
| 风险暴露 | 集中在后期 | 每 2–4 周一次 |
| 业务方参与 | 末期验收 | 每阶段可看可评 |
| 调整成本 | 高（已铺开） | 低（范围小） |

**关键取舍**：MVP 阶段允许砍功能，**但红线相关的砍不得**。

---

## 二、剪裁原则

### 2.1 三不砍

> **红线不砍、溯源不砍、权限不砍。**

这三样是系统存在的理由。MVP 可以没有图谱、没有批量操作、没有配置页，但**不能没有三栏分隔、不能没有溯源 URI、不能没有四重门禁**。

理由：这套系统的价值不是"页面多"，而是"AI 结论可采信"。砍掉红线，做出来的就是普通后台管理系统，跟项目定位完全背离。

### 2.2 五可砍

| 可砍项 | MVP 阶段替代 | 何时补 |
|---|---|---|
| 图表交互 | 静态 SVG / 数字卡片 | MVP-2 |
| G6 图谱 | 暂不做 | MVP-5 |
| 批量操作 | 单条操作 | MVP-2 |
| 配置页 | 暂不做 | MVP-4 |
| **Electron 桌面端** | **仅 Web 形态（fetch transport）**；transport 接口批次 0 预留 | MVP 后立壳（ipc.transport + safeStorage + sse-bridge，renderer 零改动） |

> **v1.1 说明**：原「虚拟滚动」一项已从可砍清单移除——方案本身改为分页，不再是需要权衡的性能优化项。

### 2.3 Mock 的使用边界

**允许 Mock**：图表数据、列表假数据、后端尚未实现的端点（清单 v1.7 附录 F backlog：disposal/board、graph、hypotheses、profiles、quality-checks、quarantine、etl-pipeline、settings/* 等约 20 个）
**禁止 Mock**：权限判定、溯源 URI、状态机门禁、审计链

> Mock 红线 = 红线形同虚设。宁可页面少做，也不能用假数据演示真红线。
> 端点 ⛔ 待补的页面，其**红线交互不得 Mock 成"永远通过"**（如 20 页 1:1 阻断判定）；上线节奏与后端 backlog 对齐，已就绪端点（批次 1 的 01/04、批次 3 的模型/审计/权限、批次 4 的跨案件/案件包/逃生舱）一律直连真实接口。

## 三、六个 MVP

| MVP | 名称 | 周期 | 累计 | 目标 |
|---|---|---|---|---|
| **MVP-0** | 能开门 | 2 周 | 2 | 浏览器能打开、能登录 |
| **MVP-1** | 能办案 ★ | 3 周 | 5 | **打通看线索→处置→留痕闭环** |
| **MVP-2** | 能批量 | 4 周 | 9 | 从"看一条"到"处理一批" |
| **MVP-3** | 能接入 | 3 周 | 12 | 数据进来、长任务跑起来 |
| **MVP-4** | 能配置 | 4 周 | 16 | 从"用系统"到"配系统" |
| **MVP-5** | 全量 | 2 周 | 18 | 26 页交付 |

### MVP-0 · 能开门（第 1–2 周）

**目标**：建立可运行的最小外壳，**验证离线环境可行性**。

| 类别 | 内容 |
|---|---|
| **包含** | FE-I-001/002/003（离线三件套）· FE-I-004/005/008（request/错误/认证）· FE-D-001（Token）· FE-C-024/025/026/027（AppShell/Header/SideNav/Banner）· FE-P-023a（登录页）· FE-B-001/002（构建/托管） |
| **砍掉** | 所有业务页面 · 图表库 · 全部 domain 组件 |

**演示路径**：打开浏览器 → 登录页 → 输入账号密码 → 进入空骨架 → 切换案件 → 退出

**验收**：
- [x] 断网环境下 `pnpm install` + `build` 成功
- [x] 登录错误文案统一（不泄露双因子状态）
- [x] 请求头带 `X-API-Version: 1`
- [x] 全局条五元素齐全（案件/本体版本/任务/用户/设置）

> **这个阶段最重要的是验证离线可行性** —— 内网镜像、字体、图标能不能真跑起来。不验证，后面全是空中楼阁。

### MVP-1 · 能办案 ★（第 3–5 周）★ 核心

**目标**：打通"看线索 → 判断 → 处置 → 留痕"最小闭环。**这是整个项目的价值验证点。**

| 类别 | 内容 |
|---|---|
| **包含** | **四个承重墙**（FE-C-012/013/014/015）· FE-C-001/002/004（Badge/Metric/Drawer）· **FE-P-001 治理仪表盘** · **FE-P-004 线索详情** · FE-P-006 审计链（简化版）· FE-C-017 五间雷达 · 全部红线测试（FE-T-003~006/009/010） |
| **砍掉** | 图谱 · 批量操作 · 所有配置页 · 数据接入 |
| **简化** | 仪表盘只做健康度+线索统计+五间雷达+高优先级列表；审计链只做时间线+链校验 |

**演示路径（这条能走通，系统就活了）**：

```
登录 → 案件门户（简化）→ 治理仪表盘
  ↓ 看到健康度徽章（第一块）+ 线索统计 + 五间雷达
点线索 C-0231 → 线索详情
  ↓ 三栏：事实（青）/推断（琥珀）/待核实（灰虚线）
点「溯源 →」→ 抽屉打开
  ↓ 行 URI 可复制，命中字段琥珀高亮
点「查证中 → 已固证」→ ConfirmDialog → 提交
  ↓ 拿到审计回执
打开审计链 → 看到自己刚才那条记录，署名真实姓名+角色
```

**验收（7 条红线全过）**：
- [x] 推断栏无绿色
- [x] 无 `source_rows` 的推断拒绝渲染
- [x] system/ai 会话下「已立案」按钮不渲染
- [x] 单源候选交叉等级为"观察"
- [x] 降级态下导出/立案禁用且写明原因
- [x] 无权限字段渲染 `****`
- [x] 敏感数据不落 localStorage

> **第 5 周就能让业务方看到：一条线索从发现到处置到留痕的全过程。**
> 所有风险（Token、组件、红线、API 对接）在第 5 周全部暴露。

## 四、技术债台账

MVP 剪裁会留下债务，必须**显式记账**，不能做完就忘。

| 债务 | 产生于 | 偿还于 | 风险 |
|---|---|---|---|
| 静态图代替 ECharts 交互 | MVP-1 | MVP-2 | 无交互，无法下钻 |
| 简化版审计链 | MVP-1 | MVP-5 | 无维度切换器 |
| 单条操作代替批量 | MVP-1 | MVP-2 | 大量数据处理慢 |
| 三步接入向导 | MVP-3 | MVP-4 | DE 建议确认体验不完整 |

> **v1.1 已偿清**：「分页代替虚拟滚动」一条已删除 —— 分页本就是最终方案，不构成债务。

**偿还原则**：每个 MVP 结束时 review 一次台账，确认债务未被遗忘。

## 七、一句话总结

> **MVP-1 是分水岭。**
> 第 5 周打通"看线索 → 处置 → 留痕"，系统就证明了自己存在的价值；
> 后面 13 周都是在这个骨架上加宽——批量、接入、配置、高级能力。

如果时间被压缩，**保 MVP-0 + MVP-1**（5 周）就能得到一个可用的最小办案系统——虽然只能一条条处理，但**每一条的处理都是可采信的**。这正是这套系统区别于普通后台的地方。
