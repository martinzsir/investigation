# 孙武侦查官 · 领域模型解耦 可行性与成本评估

> 版本 **v1.0** ｜ 日期 2026-09-10
> 依据：`ontology_v2` 代码核查（`ClueStatus`、`ClueStatusMachine`、`actions.json`、前端 `fileGate`）
> 核心结论：**可行，且比想象中便宜——最难的部分（动作声明化）已经做完了**
> 但要清醒：**解耦的是"形式"，不是"语义"**

---

## 0. 结论先行

| 问题 | 答案 |
|---|---|
| 能解耦吗？ | **能**，且成本不高（约 5–7 人日） |
| 为什么比想象便宜？ | **状态机已"半声明化"**——状态集中在 `registry.py`，动作在 `actions.json` |
| 真正的成本在哪？ | 不在状态机，在**473 处中文领域词汇** |
| 最大的陷阱？ | **重命名标识符**（表名/API路径）——收益极小、风险极大 |
| 建议做什么？ | **状态声明化 + 文案外置**，标识符不动 |

---

## 1. 关键发现：状态机已经是"半声明化"

### 1.1 现状（`core/registry.py:38`）

```python
class ClueStatus:
    PENDING   = "待查"       # 初始状态
    VERIFYING = "查证中"
    EXCLUDED  = "已排除"
    CONFIRMED = "已固证"
    FILED     = "已立案"     # 仅「已固证 + 法定程序完备」可由正兵显式置位

    ALLOWED = {PENDING, VERIFYING, EXCLUDED, CONFIRMED, FILED}

    # 可由 AI / 自动化设定的状态（不含 已立案，那是受控红线）
    MACHINE_SETTABLE = {PENDING, VERIFYING, EXCLUDED, CONFIRMED}
```

### 1.2 迁移表也集中定义（`registry.py:52`）

```python
class ClueStatusMachine:
    _TRANSITIONS = {
        PENDING:   {VERIFYING, EXCLUDED, CONFIRMED},
        VERIFYING: {PENDING, EXCLUDED, CONFIRMED},
        EXCLUDED:  {PENDING},                    # 排除后可因新证据重开
        CONFIRMED: {EXCLUDED, FILED},
        FILED:     set(),                        # 终态
    }
```

### 1.3 动作已声明化 + 装载期校验

`actions.json` 的 `target_status` 在 `ontology_loader.py:1130` 校验：

```python
if target not in ClueStatus.ALLOWED:
    raise ValueError(f"{ctx}（{name}）target_status='{target}' 非法，"
                     f"允许 {sorted(ClueStatus.ALLOWED)}")
```

**这意味着**：状态值与动作都已有集中定义和校验，**要做的不是从零解耦，而是把 `ClueStatus` 从 Python 常量变成声明文件**。

> 与五间解耦同理：**照搬 `dimensions.json` 的路径**。

## 2. 耦合分布（按"改起来多痛"排序）

| 层 | 规模 | 难度 | 说明 |
|---|---|---|---|
| **状态值** | 集中 1 处 + 18 处表名 | ⭐ 低 | `ClueStatus` + `clue_disposal_status` 表 |
| **动作声明** | `actions.json` 已声明 | ⭐ 低 | 7 个动作，已有装载期校验 |
| **迁移表** | 集中 1 处 | ⭐ 低 | `ClueStatusMachine._TRANSITIONS` |
| **领域词汇** | **473 处** | 🔴 **高** | 线索 142 / 案件 231 / 处置 84 / 立案 36 / 固证 20 / 排除 40 |
| **前端展示** | 7 个组件 | 🟡 中 | `ClueStatusMachine.vue`、`KanbanCard.vue`、`StatusBadge.vue` 等 |
| **`clue` 对象名** | 仅 1 处硬编码 | ⭐ 低 | `server/app/clues_artifact.py` |

**真正的成本在词汇，不在状态机。**

## 3. 🔴 核心判断：词汇有两种，别混为一谈

| 类型 | 例子 | 用户看得见吗 | 要不要改 |
|---|---|---|---|
| **标识符** | `clue_disposal_status`、`/api/v1/cases/{cid}/clues`、`obj_clue` | ❌ 看不见 | **❌ 别改** |
| **展示文案** | "待查"、"已立案"、"线索"、"案件" | ✅ 看得见 | **✅ 可配** |

### 3.1 为什么标识符不该改

| 理由 | 说明 |
|---|---|
| 收益极小 | 用户根本看不到表名和 API 路径 |
| 风险极大 | API 破坏性变更、数据库迁移、前端全量回归 |
| 语义已中性 | `clue` 在英文语境下本就是"线索/提示"的中性词 |

**务实做法：只把展示文案声明化，标识符保持不动。**

### 3.2 前端领域词分布（7 处）

| 组件 | 用途 |
|---|---|
| `ClueStatusMachine.vue` | 状态机 + 已立案四重门禁（**承重墙**） |
| `KanbanCard.vue` | 看板卡片（已立案金色样式） |
| `StatusBadge.vue` | 状态徽标配色 |
| `AuditTimeline.vue` | 已立案节点金橙光晕 |
| `api/endpoints/clues.ts` | 类型定义 |
| `domain/clue.ts` | `fileGate` 红线 + 状态配色 |

## 4. 三个方案的成本与建议

| 方案 | 内容 | 成本 | 效果 | 建议 |
|---|---|---|---|---|
| **A. 状态声明化** | 新增 `states.json` | **~2 人日** | 状态集、迁移表、受控终态可配 | ✅ **做** |
| **B. 文案外置** | 领域词汇标签化 | **~3–5 人日** | 界面词汇可换 | ✅ **做**（按需） |
| **C. 标识符重命名** | 表/API/对象改名 | **~15+ 人日** | 代码"中性化" | ❌ **别做** |

**A 是地基，B 决定用户感知，C 是陷阱。**

## 5. 方案 A：`states.json`（~2 人日）

### 5.1 Schema 设计

```jsonc
{
  "schema_version": 2,
  "_note": "处置状态机声明。状态值/迁移表/受控终态不再硬编码于 core/registry.py，"
           "改由本文件声明；actions.json 的 target_status 必须是此处已声明的 name"
           "（装载期交叉校验，未声明硬失败）。",
  "states": [
    { "name": "待查",   "label": "待查",   "initial": true,
      "tone": "neutral" },
    { "name": "查证中", "label": "查证中", "tone": "info" },
    { "name": "已排除", "label": "已排除", "tone": "muted" },
    { "name": "已固证", "label": "已固证", "tone": "success" },
    { "name": "已立案", "label": "已立案", "tone": "gold",
      "terminal": true,              // ★ 终态
      "requires_role": "human",      // ★ 受控：AI/机器会话不可置
      "requires_basis": true }       // ★ 必须提供法定依据
  ],
  "transitions": {
    "待查":   ["查证中", "已排除", "已固证"],
    "查证中": ["待查", "已排除", "已固证"],
    "已排除": ["待查"],
    "已固证": ["已排除", "已立案"],
    "已立案": []
  }
}
```

### 5.2 改造点

| 位置 | 动作 |
|---|---|
| `core/registry.py:38` `ClueStatus` | 改为从 pack 加载（保留兜底默认） |
| `core/registry.py:52` `_TRANSITIONS` | 从 `states.json` 读取 |
| `core/ontology_loader.py:1130` | 校验白名单改为动态 |
| `core/audit.py:25` `_DISPOSAL_STATUS` | 改为动态 |
| `core/case_library.py:23` `TERMINAL_MAP` | 改为从声明派生 |

### 5.3 关键：受控终态如何保持红线

**问题**：`file`（立案）的 human 专属是硬编码红线。映射到别领域（如 SOC 的"确认事件"），这个约束还在吗？

**答案：必须在**——它是防"AI 自动定性"的核心机制。

**做法**：不是"改名"，而是**声明哪个状态是受控终态**：

```jsonc
{
  "name": "confirmed",
  "label": "已确认事件",        // SOC 语境
  "terminal": true,
  "requires_role": "human",    // ★ 红线保留，只是名字变了
  "requires_basis": true       // ★ 必须提供依据
}
```

**红线不因改名而消失**——它从"硬编码判断 `action == 'file'`"变成"声明驱动的 `requires_role` 校验"。

## 6. 方案 B：文案外置（~3–5 人日）

### 6.1 分层策略

| 层 | 做法 | 成本 |
|---|---|---|
| **状态标签** | 已在 `states.json` 的 `label` | ✅ 随 A 完成 |
| **实体名称** | 线索/案件/处置 → 声明化 | ~1–2 人日 |
| **UI 固定文案** | 按钮、提示、标题 | ~2–3 人日 |
| 代码注释 | ❌ 不改 | — |

### 6.2 最小可用范围

**建议只外置用户高频看到的**：

```
案件 → 工作区 / 项目
线索 → 事项 / 发现
处置 → 处理
立案 → 确认 / 定级
固证 → 确认有效
```

不必追求全部 473 处——**二八原则，覆盖 80% 界面即可**。

### 6.3 实现方式

```jsonc
// labels.json
{
  "entity": { "case": "工作区", "clue": "事项", "disposal": "处理" },
  "action": { "file": "确认", "confirm": "确认有效", "exclude": "排除" },
  "hint":   { "need_confirm_before_file": "需先完成{confirm}" }
}
```

前端用一个 `t()` 函数包一层，**不改组件结构**。

## 7. 方案 C：为什么别做（标识符重命名）

| 反对理由 | 说明 |
|---|---|
| 用户不可见 | 表名、API 路径、变量名用户看不到 |
| 破坏性变更 | 现有部署的数据库迁移、API 兼容性 |
| 收益为零 | 不影响任何业务能力 |
| 引入 bug 风险 | 473 处词汇改动，遗漏即故障 |

**如果实在想让代码"中性"，正确做法是新建领域包时同步新建语义层，而不是改老代码。**

---

## 8. ⚠️ 语义漂移：解耦的真正难点

### 8.1 现象

| 侦查 | SOC | 语义 |
|---|---|---|
| 已立案 | 已确认事件 | 都是"终态 + 高权限" |
| 已排除 | 误报 | 都是"否定结论" |
| 待查 | 新告警 | 初始态 |
| 已固证 | 已验证 | 中间确认态 |

**形式能映射，语义要重新定义。**

### 8.2 关键提醒

> **解耦的是"形式"，不是"语义"。**
>
> 状态从"待查"改叫"新告警"很容易；
> 难的是新领域要自己定义状态机、权限、终态——
> **这部分工作量不会因为解耦而消失，只是从"改代码"变成"写配置"。**
>
> **而写配置同样需要领域专家。**

## 9. 跨领域映射示例（SOC）

```jsonc
{
  "states": [
    { "name": "new",       "label": "新告警",   "initial": true },
    { "name": "triaging",  "label": "分析中" },
    { "name": "fp",        "label": "误报" },
    { "name": "verified",  "label": "已验证" },
    { "name": "incident",  "label": "确认事件",
      "terminal": true, "requires_role": "human", "requires_basis": true }
  ],
  "transitions": {
    "new":      ["triaging", "fp", "verified"],
    "triaging": ["new", "fp", "verified"],
    "fp":       ["new"],
    "verified": ["fp", "incident"],
    "incident": []
  }
}
```

**注意 `incident` 保留了 `requires_role: human`** —— 红线不因改名而消失。

| 编号 | 用例 | 预期 |

## 13. 一句话总结

> **领域模型解耦可行，且比想象中便宜——因为动作声明化和装载期校验你已经做完了。**
>
> 成本约 **5–7 人日**（状态声明化 2 + 文案外置 3–5），
> 换来状态机、迁移表、受控终态、界面词汇全部可配。
>
> **但别做标识符重命名**——那是收益为零、风险极高的陷阱。
>
> 最后记住：**解耦的是形式，不是语义。**
> 换领域后定义状态机与规则的工作量不会消失，只是从"改代码"变成"写配置"——
> 而写配置同样需要领域专家。
