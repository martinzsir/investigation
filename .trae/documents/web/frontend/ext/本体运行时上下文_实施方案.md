# 孙武侦查官 · 本体运行时上下文（RuntimeContext）实施方案

> 版本 **v1.0** ｜ 日期 2026-09-10
> 依据：`ontology_v2` 代码核查（`FunctionExecutor.invoke` 调用点、`load_pack` 无缓存、py 路径约束缺口、`FeatureStore` 设计）
> 核心结论：**运行时"只有一半"——本体定义能访问（但 py 函数没拿到），运行时的值完全不能共享**
> 最大价值：**不是共享执行结果，而是补上 py 路径的红线缺口**

| 问题 | 答案 |

## 1. 现状：运行时的"一半"

### 1.1 已有的：本体定义运行时 ✅

`load_pack()` 返回的 `OntologyPack` 包含：

| 能访问 | 内容 |
|---|---|
| ✅ 本体定义 | `objects`、`links`、`bindings`、`actions` |
| ✅ 领域语义 | `dimensions`、`rules`、`thresholds`、`views` |
| ✅ 策略 | `policies`、遮蔽集合 |
| ✅ 函数规格 | `functions`（含 `inputs`、`parameters`） |

**但 py 函数拿不到它。**

### 1.2 缺失的：运行时值空间 ❌

| 项 | 现状 |
|---|---|
| 中间值 | 只作为 `dict` 返回，**执行完即丢** |
| 跨函数共享 | ❌ 无机制 |
| 值空间 | ❌ 不存在 |

**每个 py 函数都是孤岛**——算完就结束，别的函数看不到其中间结果。

### 1.3 致命细节：py 函数拿不到上下文

```python
# core/functions.py:515 —— 只传两个参数
result = FUNCTION_IMPLS[spec.impl_ref](self.store, merged)
```

而 `FunctionExecutor` 明明持有 `self.pack`、`self.access`、`self.policy`、`self.health`——**全都没传进去**。

**证据**：`jian_cross_level` 为了拿 pack，只能绕道从业务参数取：

```python
def _jian_cross_level(store, params):
    entries = _jian_entries(params.get("pack", "default"))   # ⚠️ pack 是上下文，不是业务参数
```

**pack 应该是运行时上下文，不是业务参数**——这处设计本身就暴露了缺口。

### 1.4 附带发现：`load_pack` 无缓存

```python
def _specs(self):
    return load_pack(self.pack, base_dir=self.base_dir).functions
# invoke() 开头即调用 → 每次重新解析 13 个 JSON
```

全库搜不到 `_CACHE`。**跑 6 条规则 = 至少 6 次全量解析**（且 `_jian_cross_level` 内部再调一次）。

> 在"30 张表 3000 列"规模下，这个开销会被放大。

## 2. 🔴 最大价值：补 py 路径的红线缺口

### 2.1 两条路径的约束严重不对称

| 约束 | SQL 路径 | py 路径 |
|---|---|---|
| 只读断言 | ✅ `_assert_readonly`（禁 DDL/写操作） | ❌ **无** |
| 输入权限检查 | ✅ `spec.inputs` 校验 | ⚠️ **仅覆盖声明过的 inputs** |
| 输出契约 | ✅ `rows` 结构固定 | ❌ 无校验 |
| 超时/资源限制 | ❌ 无 | ❌ 无 |

### 2.2 py 权限检查有洞

`invoke()` 确实检查 `spec.inputs`：

```python
for tbl in spec.inputs:
    if tbl.startswith("obj_"): self.policy.check_object(self.access, tbl[4:])
    elif tbl.startswith("lnk_"): self.policy.check_link(self.access, tbl[4:])
```

**但只检查声明过的**。而 py 函数硬编码查询了未声明的表：

| 函数 | 声明 inputs | 实际查询 |
|---|---|---|
| `tipoff_cross_reference` | `obj_tipoff` | **`obj_org`、`lnk_owns`、`lnk_involved_in`** |

**这部分完全绕过权限检查。**

### 2.3 更直接的问题：`store` 可写

```python
class Store:
    def execute(self, sql, params=()) -> None:      # ← 可写
        self.conn.execute(sql, params)
```

py 函数能拿到 `store`，也就能执行任意 SQL（含 DDL/写操作）。

> 返回值里写的 `"readonly": True` **只是一个字段，不是约束**。

### 2.4 为什么这最急迫

**7/11 = 64% 的计算能力，运行在无护栏的逃生舱里。**

而"只读、可审计、AI 不越界"正是本系统的立身之本——
SQL 路径严防死守（有 `_assert_readonly`），py 路径大门敞开，**这个不对称本身就是风险**。

## 3. 其他价值（按大小排序）

### 🥈 消除硬编码 → 真正的跨包复用

11 处 `obj_call`/`obj_tipoff`/`obj_org` 硬编码。函数拿到 `spec` 后表名可从声明派生
（`jian_cross_level` 已做对）。

**7 个 py 函数从"一次性代码"变成"可复用资产"**——直接提升"纯配置覆盖率"。

### 🥉 性能：省掉重复解析

加缓存后，一次 BUILD 从 N 次解析降到 1 次。**在 30 表 3000 列规模下差距显著。**

### 4️⃣ 诊断与降级可观测

`FunctionExecutor` 持有 `health`，但 py 函数拿不到。现在只有 invoke 外层的异常捕获记诊断，
**函数内部的降级决策无法上报**（除手动返回 `degraded` 字段）。

有了 ctx，函数可主动 `ctx.health.record(...)`——**降级从"被动捕获"变成"主动申报"**。

### 5️⃣ 装载期验证增强

| 新增验证 | 说明 |
|---|---|
| py 函数实际访问的表是否都已声明 | 消除硬编码的根源 |
| 返回是否含 `hit`/`basis`/`diagnostics` | 输出契约校验 |
| 引用的属性是否存在 | 防 BinderException |

### 6️⃣ 支撑上层方案（易被忽略）

| 方案 | 依赖运行时的什么 |
|---|---|
| 五间解耦 | 函数需要读 `jians.json` 声明 |
| 领域模型解耦 | 函数需要读 `states.json` |
| 元数据驱动 P0/P1 | `requires` 依赖声明的注入 |
| 跨场景落地 | py 函数表名参数化 |

**RuntimeContext 是这几件事的共同地基**——不做它，那些方案各自都要绕道。

## 4. 设计：`RuntimeContext`

```python
@dataclass
class RuntimeContext:
    """传给 py 函数的运行时上下文（只读 + 可审计）。"""
    pack: str
    spec: OntologyPack              # 本体定义（只读视图）
    store: ReadOnlyStore            # ★ 只读代理（屏蔽 execute/DDL）
    access: AccessContext           # 权限上下文
    policy: PolicyEngine            # 策略引擎
    health: RunHealth               # 运行诊断
    values: ValueSpace              # ★ 值空间（本次执行内共享）

    # ---- 便捷访问 ----
    def table(self, obj_name: str) -> str:
        """对象名 → 物化表名（消除硬编码）。"""
        if obj_name not in self.spec.objects:
            raise ValueError(f"未声明的对象：{obj_name}")
        return f"obj_{obj_name}"

    def props(self, obj_name: str) -> dict:
        """对象的属性定义（含中文名，供输出可读化）。"""

    def check(self, table: str) -> None:
        """显式权限校验（供函数主动声明访问）。"""
```

### 4.1 只读代理实现

```python
class ReadOnlyStore:
    """包装 Store，仅暴露只读能力。"""
    def __init__(self, store): self._store = store

    def query(self, sql, params=(), **kw):
        _assert_readonly(sql, "py-function")     # ← 复用 SQL 路径同一个断言
        return self._store.query(sql, params, **kw)

    def __getattr__(self, name):
        if name in ("execute", "conn"):
            raise AttributeError(f"py 函数不可访问 store.{name}（只读约束）")
        return getattr(self._store, name)
```

**关键**：复用 `_assert_readonly`，让两条路径**共享同一套只读约束**。

## 5. 值空间设计（二期）

### 5.1 两种共享，复杂度天差地别

| 类型 | 可行性 | 说明 |
|---|---|---|
| **同一次 BUILD 内共享** | ✅ 可行 | 同一进程、同一 store，加上下文即可 |
| **跨 BUILD / 持久共享** | ⚠️ 需新设计 | 版本、失效、存储——**复杂度陡增** |

**强烈建议先做第一种。**

### 5.2 应用场景

```
call_frequency_spike 算出中位数 3
        ↓ ctx.values["通话常态基线"] = 3
后续函数直接取用，不必重算
```

**对动态基线类判据特别有用**——中位数、分布、覆盖率这类"全局参照值"算一次全场景受益。

### 5.3 ⚠️ 跨 BUILD 共享要慎重

需要处理：值何时失效？数据变了怎么办？存哪？**这会让系统变成一个小数据平台项目。**

### 5.4 参照物：`FeatureStore` 已给出答案

`core/features.py` 的 `FeatureStore`：

```
feature_set_hash = sha1(entity_id | time_window | feature_name | 规范化 inputs)
相同输入永远同 hash（AC2）→ 写入后重启仍可按 hash 读回（AC1）
mark_stale() 把旧版本特征置 stale=true（AC3）
评分/规则输入经 feature_ref() 携带 feature_set_hash 引用（AC4 签名断言）
```

**hash 校验 + `stale` 标记 + 进程内缓存** —— 这正是"共享值如何失效"的答案。

> **别另起炉灶，二期直接复用 `FeatureStore`**。
> （它在《已实现未暴露模块全局盘点》中列第 10 项，已实现未接线。）

## 7. 迁移策略：渐进兼容

### 7.1 调用点只有 1 处（生产）

```bash
grep -rn "FUNCTION_IMPLS\[" --include=*.py .
# core/functions.py:515（生产）
# tests/ 3 处（测试）
```

**生产调用点仅 1 处**，改动面很小。

### 7.2 签名兼容方案

```python
import inspect

def _call_py(fn, store, params, ctx):
    sig = inspect.signature(fn)
    if len(sig.parameters) >= 3:
        return fn(store, params, ctx)      # 新签名
    return fn(store, params)               # 旧签名，兼容
```

**7 个 py 函数可逐个迁移，不必一次改完。**

## 8. 风险与对策

| 风险 | 说明 | 对策 |
|---|---|---|
| **签名变更** | 7 个函数要改 | 渐进兼容（§7.2），逐个迁移 |
| **过度设计** | 值空间易做成"小数据库" | 克制在"本次执行内"，跨 BUILD 走 `FeatureStore` |
| **配置即编程** | 运行时越强大，配置错误影响面越大 | 配套装载期校验 + 输出契约 |
| 只读代理被绕过 | 函数可能通过其他途径拿到 conn | `__getattr__` 屏蔽 + 代码审查 |
| 缓存失效 | 改了声明文件读到旧值 | 用 fingerprint 作 key（现成） |

## 9. 验收标准

| 编号 | 用例 | 预期 |
|---|---|---|
| RT-TC-01 | py 函数内调 `store.execute` | **拒绝**（AttributeError） |
| RT-TC-02 | py 函数执行 `DROP TABLE` | **拒绝**（`_assert_readonly` 生效） |
| RT-TC-03 | py 函数访问未声明表 | 权限校验触发（不再静默绕过） |
| RT-TC-04 | py 函数返回缺 `basis` | 输出契约校验告警/拒绝 |
| RT-TC-05 | 一次 BUILD 内多次 invoke | `load_pack` **只解析一次**（缓存生效） |
| RT-TC-06 | py 函数用 `ctx.table("call")` | 返回 `obj_call`，**无硬编码** |
| RT-TC-07 | 换包（对象改名） | py 函数**不崩溃** |
| RT-TC-08 | 函数内 `ctx.health.record(...)` | 诊断可查（主动申报降级） |
| RT-TC-09 | 旧签名函数 | 仍可正常调用（兼容） |
| RT-TC-10 | 现有 6 条规则 | 行为**完全一致**（回归） |
| RT-TC-11 | 值空间（二期） | 同一 BUILD 内可读写共享值 |
