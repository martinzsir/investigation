# 孙武侦查官 · 审计场景适配方案

> 版本 **v1.0** ｜ 日期 2026-09-10
> 依据：`ontology_v2` 代码核查（含新发现 `core/sampling.py`）+ 审计方法论对照
> 核心结论：**适配，且比企业合规管理更适配**——审计方法论与本系统设计哲学同构

---

## 0. 结论先行

| 审计类型 | 适配度 | 判断 |
|---|---|---|
| **舞弊审计 / Forensic Audit** | ★★★★★ | 与本平台几乎同构，**首选** |
| **持续审计 / Continuous Auditing** | ★★★★☆ | 批次构建天然适配 |
| **合规审计**（个保审计等） | ★★★★☆ | 证据链能力可复用 |
| **财报审计** | ★★☆☆☆ | ⚠️ **别碰**，见 §4 |

**一句话**：审计的核心动作是「假设 → 取证 → 交叉验证 → 形成可复核结论」，这**正是本系统的设计哲学**。

**补充**：接入非结构化数据（合同、纪要、发票、举报）后，舞弊审计可从"能查资金流"升级为"能查完整决策链条"——
但**必须先补 span 级溯源再接入**，否则会架空现有的行级溯源体系（详见 §8）。

## 1. 为什么审计比"合规管理"更适配

### 1.1 方法论同构

| 审计方法论 | 本系统对应机制 |
|---|---|
| 风险评估 → 确定审计重点 | 假设声明 + 状态机（待检验/已证实/已证伪） |
| 审计证据充分性 | 五间交叉：独立源 ≥2 升格，单源只作观察 |
| 审计证据适当性 | 行级溯源 `row_uri`，可回到原始数据 |
| 审计轨迹 / 工作底稿 | HMAC 链式审计链 + 版本闭环 |
| 职业判断 | **AI 永不自动定性**，只提草案 |
| 抽样与扩大程序 | `SamplingPreflight`（见 §2） |
| 复核与重做 | `fingerprint` + `data_version` + `REPEATABLE(seed)` |

**关键洞察**：合规管理的核心是"我有没有按制度做"，而**审计的核心是"我怎么知道这是真的"**——后者正是本系统五条红线要解决的问题。

### 1.2 一个被低估的契合点

审计最忌讳的是**审计师无法解释结论来源**。而"可解释、可追溯、可复核"恰恰是本系统的立身之本：

- 每条推断**必挂 `source_rows`**（红线二）
- 每个结论**可回到原始数据行**
- 每次扫描**有版本锚点**（`data_version`）
- 每个动作**有不可篡改的审计链**

**这不是"刚好能用"，是天生契合。**

## 2. 意外发现：已有「按假设抽样预演」

### 2.1 现况

`core/sampling.py` 的 `SamplingPreflight` 是一个**已实现但完全未暴露**的能力：

```python
# 对每个假设做抽样预演
rows = self._take_sample()
for hid in hypothesis_ids:
    hits = sum(1 for r in rows if self.detect_hit(r))
    rate = hits / sampled
    verdict, suggest = _judge(rate)
```

**三档判定逻辑**：

| 命中率 | 判定 | 建议 |
|---|---|---|
| ≥ 5% | **方向明确** | 建议投入全量扫描 |
| 1% ~ 5% | **方向存疑** | 建议扩大采样至 5% 再验证 |
| < 1% | **方向否定** | 建议调整假设，暂缓全量算力 |

**这与审计方法论高度同构**：先评估风险 → 决定投入多少审计程序 → 证据不足则扩大样本。这恰恰是审计师最核心的"职业判断"环节。

还考虑了小样本假阴性：`min_sample_rows=200` 防止"29 行 × 1% = 0 行"退化成假阴性。

### 2.2 两个问题

| 问题 | 严重度 | 说明 |
|---|---|---|
| **完全未接线** | 中 | server 无端点、frontend 无 UI、MCP 无工具 |
| **不可复现** | **高** 🔴 | 用 `USING SAMPLE reservoir(n ROWS)`，**无 seed** |

**为什么不可复现是硬伤**：审计抽样必须可复现——复核者要能重做你的样本。样本不可重做 = 结论不可验证 = 审计失败。

### 2.3 修复方案（成本极低）

```python
def _take_sample(self, seed: int = 20250101) -> List[dict]:
    # DuckDB 原生支持 REPEATABLE
    return self.store.query(
        f"SELECT * FROM ({self.scan_sql}) t "
        f"USING SAMPLE reservoir({target} ROWS) REPEATABLE ({seed})"
    )
```

**改动量约 5 行**，但让整个抽样机制具备审计级可复核性。

> 建议把 `seed` 写入审计链 `params_hash`，使"哪次抽样、什么种子"成为可追溯证据。

## 3. 审计要素对照表

| 审计要素 | 现状 | 说明 |
|---|---|---|
| **证据充分性**（交叉验证） | ✅ 已有 | 五间交叉 = 充分性的量化表达 |
| **审计轨迹** | ✅ 已有 | `row_uri` 行级溯源 + HMAC 审计链 |
| **可复核性** | ✅ 已有 | `fingerprint` + `data_version` + 版本闭环 |
| **职业判断归人** | ✅ 已有 | AI 永不自动定性（红线一） |
| **假设/结论状态管理** | ✅ 已有 | 假设状态机对应审计结论把握程度 |
| **抽样** | ⚠️ 有机制 | **缺 seed（不可复现）+ 未接线** |
| **重要性水平** materiality | ❌ 缺失 | 审计必需，见 §5 |
| **审计程序清单** audit program | ❌ 缺失 | 见 §5 |
| **工作底稿** | ⚠️ 部分 | 审计链 ≠ 底稿，归档格式不同 |
| **两级复核** | ⚠️ 部分 | 只有实体裁决复核，无审计作业复核 |

**结论：底盘齐了（前 5 项全绿），缺的是审计作业层（后 5 项）。**

---

## 4. ⚠️ 明确不要碰的：财报审计

| 原因 | 说明 |
|---|---|
| 准则高度成熟 | 抽样、函证、监盘、重要性水平均有严格规定，无方法论创新空间 |
| 市场被主导 | 四大 + 本土八大所，工具采购逻辑完全不同 |
| 能力不匹配 | 财报审计靠**凭证与准则判断**，不是多源关联——你的强项用不上 |
| 责任风险 | 审计失败的法律责任远高于合规工具 |

**结论**：这是一片红海，且你的能力在这里没有差异化。

## 5. 需要补的能力（按成本排序）

### P0：抽样可复现（约 0.5 人日）

| 项 | 内容 |
|---|---|
| 改动 | `sampling.py` 加 `seed` 参数 + `REPEATABLE()` |
| 配套 | `seed` 写入审计链 `params_hash` |
| 价值 | 抽样结果可被复核者重做 → 具备审计级可信度 |

### P1：抽样能力接线（约 1–2 人日）

| 项 | 内容 |
|---|---|
| 后端 | `POST /cases/{cid}/sampling/preflight` |
| 前端 | 「假设预演」面板：抽样比例、命中率、三档判定、建议 |
| MCP | 暴露给 Agent（与 `ontology.describe` 联动） |
| 价值 | **别家没有的差异化功能**——直接回答"这个方向值不值得全量核查" |

### P2：重要性水平 materiality（约 2 人日）

审计必需概念：低于该金额的错报不影响决策。

```
建议实现：
  1. 在 thresholds.json 增加 materiality 段
  2. 规则判定时支持 amount >= materiality 过滤
  3. 抽样预演支持按 materiality 分层
```

### P3：审计程序清单 audit program（约 3 人日）

把一个审计项目拆成有序程序步骤，每步挂规则 + 状态。

```
建议实现：
  新增 audit_program.json（新增声明文件）
  programs: [{ id, name, steps: [{ rule_id, required, status }] }]
```

> 与《假设声明层方案》的 `assumptions.json` 天然耦合：一个审计程序 = 一组假设的检验计划。

### P4：工作底稿导出（约 2 人日）

审计链 → 底稿格式（含索引、交叉引用、结论、复核签署）。

## 7. 对融资叙事的影响

这个分析**强化**了之前的判断，并给了一个更好的定位：

| 原来 | 建议改为 |
|---|---|
| "合规风险监测" | **"审计与调查的证据引擎"** |
| 客户：合规部 | **+ 内审部**（预算独立、需求刚性） |
| 卖点：查风险 | **卖点：让每个审计结论可复核、可举证** |

**内审部门是比合规部更好的客户**，理由：
1. 有独立预算（不受合规部预算波动影响）
2. 有明确交付物要求（审计报告必须能交）
3. 需求刚性（监管要求内审覆盖）

## 8. 非结构化证据接入路径

### 8.1 为什么审计场景特别需要

审计证据相当大比例是**文档**：合同、发票、决议、会议纪要、往来函件、举报信。而当前系统只吃结构化数据（流水、通话、轨迹）——**这构成了能力天花板**。

一个具体例子：**三单匹配**（合同-发票-付款）是审计最经典的舞弊检测程序，但它需要读合同文本。现在做不了。

更本质地说：

> 结构化数据告诉你**钱怎么流的**
> 非结构化数据告诉你**谁决定让它这么流的**

舞弊审计要的是完整链条，缺了后半段就不闭环。

### 8.2 现状：不是从零开始，是"已实现未暴露"

| 已有 | 状态 |
|---|---|
| `tipoff`（内间）`content_raw`、`osint_article`（死间）`info_text` | ✅ 五间里**两间本来就是文本** |
| `core/search.py` 语义检索 | ✅ **完整实现**：索引、检索、权限过滤、审计留痕；AC2 标了 `solo_evidence_warning` |
| 只存引用不存原文（AC4） | ✅ 设计克制 |
| `policies.json` 已配 `content_raw` 遮蔽 | ✅ 主办及以上可见 |

**但它只被 demo 与测试引用——MCP 和 API 一个都没接。**

所以问题不是"要不要引入"，而是：**已有的能力要不要接通 + 做深**。

### 8.3 能解锁的审计场景

| 场景 | 数据源 | 查什么 |
|---|---|---|
| **三单匹配** | 合同 + 发票 + 付款 | 虚列支出、虚假供应商 |
| 会议纪要核查 | 董事会/总办会纪要 | 重大决策是否集体决策、绕过审批 |
| 公开风险扫描 | 裁判文书、被执行、舆情 | 供应商与关联方风险 |
| 举报核查 | 举报材料 | 已支持（`tipoff`） |
| 邮件/IM 取证 | 内部通讯 | 舞弊直接证据（**需严格授权**） |

### 8.4 🔴 最关键的一点：接早了会反噬

本系统卖的是"**证据可采信**"——每条结论能回到原始数据行。

但 `row_uri` 现在是**行级**的：一份合同 = 一行。

- 溯源到"这份 68 页合同" ≈ **溯源失效**
- 材料里提到十个名字，到底哪个是证据？

> **非结构化数据最大的风险不是技术难度，而是它让"证据"这个概念变模糊——模糊到可能架空你花大力气建的溯源体系。**

另两个坑：

| 坑 | 说明 |
|---|---|
| **源相关性** | 研报互抄、新闻同源转载——硬套五间交叉会系统性高估置信度 |
| **注入攻击** | 举报信是典型不可信外部文本，必须在 **ingest 阶段**就分框（`untrusted_content`），不能等调 LLM 时才防 |

### 8.5 接入顺序（顺序错了会削弱核心优势）

| 序 | 事项 | 为什么 | 成本 |
|---|---|---|---|
| **1** | **span 级溯源**（`doc_id#para_N`） | 不做则溯源失效 | 约 3 人日 |
| **2** | **文件层 `document` 对象**（哈希/路径/页数） | 现在原始文件压根没进系统，溯源断在半路 | 约 2 人日 |
| **3** | **接通 `core/search.py`** | 已写好，零风险 | 约 1–2 人日 |
| 4 | 源相关性声明 | 防交叉计数虚高 | 约 2 人日 |
| 5 | 结构化抽取 | **最克制**，只抽可逆字段 | 延后 |

**先补 span 级溯源，再谈接入。顺序反了，接进来的数据越多，系统越不可信。**

### 8.6 净影响判断

| 做法 | 结果 |
|---|---|
| **按顺序做** | 舞弊审计从"能查资金流"升级为"能查完整决策链条"，真正闭环 |
| **不按顺序** | 数据覆盖增加，但**可采信性下降**——用核心价值换覆盖面，不划算 |

### 8.7 一个好消息

`core/search.py` 的 AC2 已经写了 `solo_evidence_warning`——**设计者早就意识到"embedding 相似度不能作为独立证据"**。架构层有防护意识，只是没接通。

所以第 3 步几乎零风险，约 1–2 人日即可拿到语义检索能力。

## 10. 一句话总结

> **审计是本系统最契合的场景之一——方法论同构、能力现成，只差"审计作业层"这最后一公里。**
> 而 `core/sampling.py` 这个被埋没的模块，加上 5 行代码的 seed 修复，就能立刻变成一个**别家没有的差异化功能**：
> **「按假设抽样预演」——直接回答审计师最头疼的"这个方向值不值得投入全量核查"。**
>
> 再接上非结构化证据，舞弊审计将从"能查资金流"升级为"**能查完整决策链条**"——
> 但切记**先补 span 级溯源再接入**，否则是用"可采信性"这个核心资产去换数据覆盖面，得不偿失。
