## 1. 🔴 前提：计分不能进语义层

### 1.1 AC5 禁令

```python
# core/derived.py:25
_FORBIDDEN_REGISTRY_NAMES = {
    "person.risk_score", "org.risk_score", "person.risk", "clue.score",
}
```

**理由**（docstring 原文）：

> "person.risk_score 这种**启发式打分**不进入 registry（AC5 断言），
> 保持在展示层/MCP 层临时计算，**避免进入对象属性的稳定语义层**。"

### 1.2 为什么卡这么死

风险分是**可调的启发式**——今天权重 0.3、明天 0.5。
若它成为"对象属性"，**对象语义会随参数漂移**，稳定语义层即被污染。

> 这与红线三（事实/推断三栏不合并）是**同一道防线的两个哨位**。

## 2. 现成范例：`prioritize_clues`

### 2.1 实现（`core/lineage.py:193`）

```python
score = confidence*0.4 + jian_coverage*0.35 + data_strength*0.25
```

| 维度 | 权重 | 计算 |
|---|---|---|
| **假设置信度** | 0.4 | 关联假设的最高置信度（H1=0.9，其余 0.7） |
| **间类覆盖度** | 0.35 | 命中间类权重之和归一：`min(1.0, jian/5.0)` |
| **数据强度** | 0.25 | `min(1.0, 溯源行数/10)` —— **封顶，避免"行数多=一定对"** |

间类权重：

```python
_JIAN_WEIGHT = {"内间": 5, "死间": 4, "因间": 3, "反间": 2, "生间": 1}
```

### 2.2 三处设计功力

| 设计 | 说明 |
|---|---|
| 写在 `lineage.py`（**排序层**） | 不是语义层 |
| 写进 `detail.priority_score` | 是**线索的展示字段**，不是对象属性 |
| 注释明写"供操作台排序展示" | 定位清晰 |

**这就是 AC5 想要的那条路**——启发式打分留在展示层，不进语义层。

### 2.3 但它是"已实现未暴露"

| 检查项 | 结果 |
|---|---|
| 实现 | ✅ 完整（含 `priority_rank` 排序） |
| 后端接线 | ❌ `server/` **零引用** |
| 前端 | ⚠️ 仅 Mock 有 `priority_score` 字段 |
| **权重可配** | ❌ **0.4/0.35/0.25 与 `_JIAN_WEIGHT` 全硬编码** |

> 这是第 9 个"已实现未暴露"模块。
> 而**权重硬编码是当前最大问题**——计分规则不可审计，违背"未声明即硬失败"的一贯立场。

## 3. 计分的三层模型（核心答案）

| 层 | 回答的问题 | 例子 | 归属 | 可配性 |
|---|---|---|---|---|
| **① 判定计分** | 命中了吗？ | `次数 ≥ 2×中位数` | 规则层 | ✅ 声明可配 |
| **② 强度计分** | 证据够吗？ | 交叉等级 `n≥3` | 领域层 | ⚠️ 映射**不可配** |
| **③ 排序计分** | 先看哪个？ | `priority_score` | **展示层** | ✅ 应可配 |

**你问的"运算过程当中的计分"主要是第 ③ 层**——它服务的是**人的注意力分配**，不是事实认定。

### 3.1 为什么要分层

| 混淆的后果 | 说明 |
|---|---|
| ①② 混淆 | 用分数代替命中判定 → 可调参数决定事实 |
| ②③ 混淆 | **分数高就升格** → 红线被绕过 |

---

## 4. 🔴 一条必须守的红线

> **计分不得反向影响定性。**

`jian_cross_level` 的等级是**硬规则** `n ≥ 3`（独立源数），**不是分数**。

**如果让"分数高也能升格"，红线就破了**——因为分数是可调的启发式，而等级是防误报的底线。

**打个比方**：

| 机制 | 决定 |
|---|---|
| **分数** | **先查谁** |
| **等级** | **能不能立案** |

**两者必须隔离。**

### 4.1 校验机制

```python
def _assert_score_not_affecting_level(...):
    """装载期/运行期断言：等级只能由独立源数决定，不得由 score 决定。"""
```

建议在 `scoring.json` 装载时校验：**任何计分项都不得声明为级别的输入**。

## 5. 实现路径

### 5.1 第一步：计分放展示层（复用现有）

复用 `prioritize_clues`，写 `detail`，**不进对象属性**。✅ 已满足，无需改动。

### 5.2 第二步：权重声明化 ⭐ 关键

新增 `scoring.json`：

```jsonc
{
  "schema_version": 1,
  "_note": "排序计分声明。计分属展示层（AC5），绝不进对象语义层；"
           "且不得反向影响交叉等级（等级只由独立源数决定）。",
  "dimensions": [
    { "name": "confidence",     "weight": 0.4,
      "source": "assumption_confidence", "note": "假设置信度" },
    { "name": "jian_coverage",  "weight": 0.35,
      "source": "jian_weight_sum", "normalize": 5.0, "note": "间类覆盖度" },
    { "name": "data_strength",  "weight": 0.25,
      "source": "source_rows_count", "normalize": 10.0,
      "cap": 1.0, "note": "数据强度（封顶，避免行数多=一定对）" }
  ],
  "assumption_confidence": { "H1": 0.9, "H4": 0.7, "_default": 0.7 },
  "_constraint": "各 dimension weight 之和必须为 1.0（装载期校验）"
}
```

**间类权重建议放进 `jians.json`**（而非另写一份）：

```jsonc
// jians.json 每项增加
{ "name": "内间", "default_weight": 5, "default_clearance": 3, ... }
```

> 这与《五间解耦实施方案》的 schema 兼容——解耦后间类可配，权重跟着走。

### 5.3 第三步：分数带依据（可解释性）⭐

**当前最大缺口**：一个 92 分的线索，办案人不知道"92 怎么来的"。

**解决**：返回 `score_basis`：

```jsonc
{
  "priority_score": 92,
  "priority_rank": 1,
  "score_basis": {
    "confidence":    { "raw": 0.9,  "weight": 0.4,  "contrib": 0.36 },
    "jian_coverage": { "raw": 1.0,  "weight": 0.35, "contrib": 0.35 },
    "data_strength": { "raw": 0.85, "weight": 0.25, "contrib": 0.2125 }
  },
  "score_formula": "confidence*0.4 + jian_coverage*0.35 + data_strength*0.25",
  "score_source": "scoring.json@v1"
}
```

**为什么必须做**：分数若是黑盒，就与红线一（AI 不产定性结论）冲突。
**可解释性是计分能被采信的前提。**

### 5.4 第四步：接线与展示

| 环节 | 动作 |
|---|---|
| 后端 | `clues_view` 调 `prioritize_clues` 并透传 `detail` |
| 前端 | 用 `priority_score` 排序（Mock 已有该字段，直接对接） |
| UI | 分数旁展示 `score_basis` 明细（hover/展开） |

## 6. 与既有机制的边界

| 机制 | 位置 | 能否被计分影响 |
|---|---|---|
| 规则命中（`hit_when`） | 规则层 | ❌ |
| **交叉等级**（`n≥3`） | 领域层 | ❌ **绝对不可** |
| 假设状态机 | 领域层 | ❌ |
| **排序优先级** | 展示层 | ✅ |
| 派生属性（确定性指标） | 语义层 | ✅（但不含打分） |
| 风险分/可疑度 | **展示层** | —— 本身就是计分产物 |

---

## 7. 风险与对策

| 风险 | 说明 | 对策 |
|---|---|---|
| **计分反向影响定性** 🔴 | 分数高就升格 → 红线破 | 装载期断言 + 等级只认独立源数 |
| **分数黑盒** | 不知分怎么来的 | `score_basis` 必返回（§5.3） |
| 权重被随意调整 | 不同人算出不同分 | `scoring.json` 版本化 + 审计记录 |
| 计分混入语义层 | 违反 AC5 | 禁令名单 + 装载期校验 |
| 数据强度误导 | "行数多=一定对" | 保持 `cap: 1.0` 封顶 |
