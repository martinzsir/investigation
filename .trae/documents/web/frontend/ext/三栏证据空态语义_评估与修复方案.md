# 三栏证据空态语义：评估与修复方案

> 版本 v1.0 ｜ 日期 2026-09-11
> 起因：用户反馈「事实没有找到，推断显示红色提示，莫名其妙」
> 依据：实测三种线索的 evidence 产出 + 前端渲染核查
> 核心结论：**不是错觉，是告警语义错配** —— 系统用「系统故障」的语气，表达「设计如此的正常状态」
> 附带发现：**奇正分工线索缺 source_rows 是真 bug**（不是设计如此）

## 1. 实测复现

### 1.1 三种线索的实际表现

| 线索类型 | 事实栏 | 推断栏 | 待核实栏 |
|---|---|---|---|
| 正常规则线索（有溯源行） | 1 条 ✅ | 1 条 ✅ | 2 条 |
| 奇正分工线索（未传 source_rows） | 空 | 空 + 🔴 红色警告 | 0 条 |
| **异常通道线索**（设计无证据行） | 空 | 空 + 🔴 **红色警告** | 0 条 |

**红色警告文案**：`⚠ N 条推断因缺少溯源（source_rows）已拒绝渲染`

### 1.2 异常线索的后端产出（实测）

```
inference | 规则 R3 零命中（empty_result_suspect）
pending   | 判据已降级：无证据行
pending   | 规则判据：…
```

关键：`is_anomaly=True` **已在 detail 中**，后端 `build_evidence` 能读到，**但未用它做分支**；前端 `ThreeColumnEvidence.vue` **完全无 is_anomaly 判断**（已 grep 确认）。

---

## 2. 为什么"莫名其妙"：三层原因

### 2.1 用「故障语气」表达「设计如此」

异常通道线索 `source_rows` 恒为空是**刻意设计**（`anomaly_channel.py` 明确注释）：

> 它表达的是「**我们没能看到什么**」——如规则零命中的覆盖缺口。

但系统渲染成「**已拒绝渲染**」——这是系统故障的措辞。

> **本来就不该有证据行，却被当成错误。**

### 2.2 警告在推断栏，根因在事实栏（因果断裂）

```
没有源数据行 → 事实栏空 → 推断无溯源 → 被拒绝渲染
```

用户看到的是「事实：暂无」+「推断：🔴 警告」——**因果关系断裂**，无法判断是"压根没数据"还是"数据丢了"。

### 2.3 文案是开发者语言

| 现有文案 | 问题 |
|---|---|
| `缺少溯源（source_rows）` | `source_rows` 是代码字段名，侦查员看不懂 |
| `已拒绝渲染` | 被动语态，不说**该怎么办** |
| `暂无已核事实` | **"已核"是误导** —— 事实栏是原始数据行，未经过核实 |

---

## 3. 根本问题：告警语义错配

前端**异常线索与正常线索完全共用同一套渲染**（`ClueDetailView.vue:195` 无 `is_anomaly` 分支）。

**长期危害 —— 警告疲劳**：

当大量异常线索都显示红色警告，真出问题（数据丢失 / 结构降级）时反而被淹没。
这跟安全产品的"告警疲劳"是同一类问题：**当一切都是警报，就没有警报**。

---

## 4. 修复方案：三态区分

### 4.1 状态模型

| 状态 | 性质 | 显示方式 |
|---|---|---|
| ① 有证据行 | 正常 | 正常三栏 |
| ② 异常通道 / 本就无证据 | **设计如此** | **中性说明，灰色**，不是警告 |
| ③ 应有证据但缺失（降级/丢失） | 真异常 | 🔴 **才用红色警告** |

### 4.2 改动一：异常通道线索单独语境（最关键）

`evidence_builder` 加 `is_anomaly` 分支：

```python
is_anomaly = detail.get("is_anomaly", False)
if is_anomaly:
    # 不产 inference（无溯源会被前端丢弃），改产明确的语境项
    items.append({
        "id": f"a{clue_id}", "kind": "pending",
        "text": _anomaly_context_text(detail),
        "context": "anomaly",
    })
```

**目标文案**：

```
事实：此类线索不含原始证据行
     它表达的是「我们没能观察到什么」，非数据缺失
推断：不适用（异常通道不参与交叉升格）
```

### 4.3 改动二：文案改面向人

| 原 | 改 |
|---|---|
| `N 条推断因缺少溯源（source_rows）已拒绝渲染` | `该推断暂无原始数据行支撑，暂不展示。可先补充侦查或确认数据边界。` |
| `暂无已核事实` | 按情况分述（见 4.4） |
| `暂无挂溯源的推断` | `暂无可展示的推断` |

### 4.4 改动三：事实栏空态解释「为什么空」

| 情况 | 文案 |
|---|---|
| 异常通道线索 | `此类线索本就不含原始证据行（表达"未观察到"）` |
| 数据降级 | `数据降级：原始行暂不可用（{degrade_reason}）` |
| 普通无数据 | `本案暂无该线索的原始数据行` |

## 5. 附带 bug：奇正分工缺 source_rows

### 5.1 定位

`skills/registry_bootstrap.py` 的 `_clue_from_qi_zheng`：

```python
detail = {"奇兵":..., "正兵":..., "依据": basis, "维度": ...}
return [LineageClue(
    skill_id=spec.skill_id, title=title, detail=detail,
    jian_types=list(spec.consumes_jian),
    needs_human_review=True,
    # ❌ 未传 source_rows
)]
```

**而 `q1_rows`（Q1_result）就在手边**（第 97 行已取出并用于拼标题/basis）。

### 5.2 性质

**这是实现缺失，不是设计如此** —— 与异常通道不同。

Q1 时间窗碰撞的数据行本应作为证据支撑，现在丢了，导致：
- 事实栏空
- 推断无溯源 → 被前端丢弃 → **红色警告**

### 5.3 修复

```python
return [LineageClue(
    ...,
    source_rows=[dict(r) for r in q1_rows],   # ★ 补上
    needs_human_review=True,
)]
```

补上后奇正分工线索的证据栏即完整，**不再落入红色警告**。

## 8. 设计原则

> **告警应该表达"出了问题"，而不是"这个东西本来就这样"。**
>
> 异常通道的价值在于诚实表达「我们没能看到什么」——
> 如果它被渲染成系统故障的红色警告，这个诚实的信号就变成了噪音。
>
> **当一切都是警报，就没有警报。**

### 8.1 三态判断树

```
线索无 source_rows
  ├─ is_anomaly=True        → 设计如此 → 中性灰色说明
  ├─ is_degraded=True       → 真异常   → 🔴 红色警告 + degrade_reason
  └─ 其他（应有却无）        → 待查     → 🟡 提示"暂无数据行"
```

---

## 9. 一句话总结

> 这个页面把「**设计如此**」和「**证据缺失**」混为一谈了，红色警告是错的工具。
>
> 修复后：异常通道线索用**中性语境说明**（它本就不该有证据行），
> 奇正分工线索**补上 source_rows**（那是真 bug），
> 只有真正的降级/丢失才保留**红色警告** —— 让告警重新变得有意义。
