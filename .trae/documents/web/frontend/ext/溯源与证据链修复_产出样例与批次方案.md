| 部分 | 内容 | 你要做什么 |

**示例数据说明**：使用 `data/samples/通话记录.json` 真实内容（张卫国→李志强 12 次、张卫国→王五 3 次），走 R3 规则（招投标公示期通话频次突增）。

**URI 示意**：`通话记录@v3#p0/8f3a21`
- 实际 `version` 段是 build_id（uuid），此处简写为 `v3`
- 实际 `rowid` 是行内容哈希，此处简写为 `8f3a21`
- `dataset` 用中文源表名，与 `bindings.json` 的 `source_table` 一致

**计算过程**（`core/functions.py` 实际逻辑）：
```
pairs = [(张卫国→李志强, 12), (张卫国→王五, 3)]
top = 12, rest = [3] → median = 3
hit = 3 > 0 and 12 >= 2×3 = 6  → True
basis = "张卫国→李志强 通话 12 次，为其他对端常态中位数 3 的 4.0 倍"
```

# 第一部分：五个决策点

## §1 决策点一：事实栏粒度

事实栏展示"原始数据"，但**多细**由你定。

### 方案 A：按字段一条（最细）

```json
[
  { "id": "fR3-0-主叫",   "kind": "fact", "text": "主叫：张卫国",
    "source_rows": [{ "row_uri": "通话记录@v3#p0/8f3a21" }] },
  { "id": "fR3-0-被叫",   "kind": "fact", "text": "被叫：李志强",
    "source_rows": [{ "row_uri": "通话记录@v3#p0/8f3a21" }] },
  { "id": "fR3-0-次数",   "kind": "fact", "text": "通话次数：12",
    "source_rows": [{ "row_uri": "通话记录@v3#p0/8f3a21" }] }
]
```

**页面效果**
```
事实（青）
  • 主叫：张卫国      通话记录@v3#p0/8f3a21
  • 被叫：李志强      通话记录@v3#p0/8f3a21
  • 通话次数：12      通话记录@v3#p0/8f3a21
```
✅ 每条独立可下钻，溯源最精确
❌ 字段多时条目爆炸（10 字段 × 5 行 = 50 条）

### 方案 B：按行聚合（推荐）

```json
[
  { "id": "fR3-0", "kind": "fact",
    "text": "主叫 张卫国 · 被叫 李志强 · 通话次数 12",
    "source_rows": [{ "row_uri": "通话记录@v3#p0/8f3a21" }] },
  { "id": "fR3-1", "kind": "fact",
    "text": "主叫 张卫国 · 被叫 王五 · 通话次数 3",
    "source_rows": [{ "row_uri": "通话记录@v3#p0/c72e09" }] }
]
```

**页面效果**
```
事实（青）
  • 主叫 张卫国 · 被叫 李志强 · 通话次数 12
    通话记录@v3#p0/8f3a21
  • 主叫 张卫国 · 被叫 王五 · 通话次数 3
    通话记录@v3#p0/c72e09
```
✅ 一行一条，条数与 `source_rows` 对齐，直觉一致
✅ 点 URI 仍能看完整字段表（溯源信息不丢）
❌ 单行很长时需横向滚动

### 方案 C：按行聚合 + 命中字段前置

在 B 基础上，把命中判据的字段排前面并加粗：

```json
{ "id": "fR3-0", "kind": "fact",
  "text": "通话次数 12 · 主叫 张卫国 · 被叫 李志强",
  "hit_fields": ["通话次数"],
  "source_rows": [{ "row_uri": "通话记录@v3#p0/8f3a21" }] }
```

**页面效果**
```
事实（青）
  • 通话次数 12 · 主叫 张卫国 · 被叫 李志强
    ↑琥珀    通话记录@v3#p0/8f3a21
```
✅ 一眼看出为什么命中
❌ 需额外 `hit_fields` 字段，前端要小改

> **推荐 B**（条数与溯源行一一对应，实现最简）。若你希望"一眼看出命中原因"，选 C（前端改动约 0.5 人日）。

## §2 决策点二：线索标题

现在标题 = 规则标题，6 条规则只有 6 种标题。

### 方案 A：保持纯规则名（不改）

```
招投标公示期通话频次突增    [生间] 待核实
```
✅ 零改动，中性不越界
❌ 20 条线索只有 6 种标题，分不清

### 方案 B：规则名 + 依据摘要副标题（推荐，P0 内）

```
招投标公示期通话频次突增                        [生间] 待核实
张卫国→李志强 通话 12 次，为常态中位数 3 的 4.0 倍
```
✅ 标题保持中性（不越红线一），副标题给业务细节
✅ **零后端改动**——`basis` 本来就产出了，只是列表页没显示
❌ 标题本身仍不区分

### 方案 C：主体前缀 + 规则名（P1，需后端配合）

```
张卫国 · 招投标公示期通话频次突增              [生间] 待核实
张卫国→李志强 通话 12 次，为常态中位数 3 的 4.0 倍
```

需要 Function 额外返回 `subject` 字段：

```python
# core/functions.py 补充
return {"hit": hit, "basis": basis, "diagnostics": diag,
        "subject": top["caller_raw"],        # ★ 新增
        "pairs": [...]}
```
```
Function 改造：11 个函数逐个加，约 1–2 人日
```
✅ 最符合业务直觉（一眼知道是谁）
⚠️ **禁止**写成"张卫国涉嫌串标"——主体名是事实，定性措辞是红线

> **推荐 B**（P0 内，零后端改动；C 列为 P1，可后续补）。

## §4 决策点四：溯源面板字段名

### 方案 A：中文名（推荐）

```json
{ "name": "主叫", "value": "张卫国", "hit": true, "policy": "visible" }
```
✅ 业务可读
⚠️ 映射不全时回落列名

### 方案 B：中英对照

```json
{ "name": "主叫", "raw": "caller_raw", "value": "张卫国", "hit": true }
```
✅ 排查问题时能对应到源列
❌ 界面变挤

> **推荐 A**，`raw` 列名放进 `title` 属性（hover 显示），兼顾两者：
> `<th title="caller_raw">主叫</th>`

**完整溯源面板产出**（R3 命中行）：

```
┌─ 来源：通话记录 ──────────────────────────────────┐
│ 通话记录@v3#p0/8f3a21            [已复制 URI]     │
├──────────────┬───────────────────────────────────┤
│ 主叫         │ ▍张卫国                    （琥珀）│
│ 被叫         │ ▍李志强                    （琥珀）│
│ 通话次数     │ ▍12                        （琥珀）│
│ 通话时长     │ 37 分钟                            │
│ 对方手机号   │ 138****5678                （遮蔽）│
│ 涉密备注     │ ****    需 system 级授权   （拒绝）│
└──────────────┴───────────────────────────────────┘
```

| 字段 | 来源 | 说明 |
|---|---|---|
| 中文名 | `objects.json` 属性名 / `data_elements.json` | 回落列名 |
| 琥珀高亮 | `hit: true` | 命中判据的字段 |
| `138****5678` | `policies.json` 遮蔽 | 前 3 后 4 |
| `****` + 提示 | `policy: "denied"` | **未声明即拒绝**（fail-closed） |

> ⚠️ **遮蔽必须随适配器一起做**。否则修好显示的同时会引入"敏感字段明文"这个更严重的问题。

## §9 立即要做的一件事（5 分钟）

无论选哪套，请先跑这三条 SQL，它决定 B4 是"修 bug"还是"补功能"：

```sql
-- 在 cases/<你的案件ID>/state.sqlite 执行
SELECT COUNT(*) FROM audit_chain;                                  -- 审计链节点数
SELECT COUNT(*) FROM review_decision;                              -- 决策记录数
SELECT COUNT(*) FROM clue_disposal_status WHERE status != '待查';  -- 已处置数
```

| 结果 | 结论 |
|---|---|
| 决策 > 0 且 audit_chain = 0 | **确认接线缺口**，B4 是修 bug |
| 两者都 > 0 | 接线正常，空链仅因未处置 |
| 决策 = 0 | 先点一个处置动作再查 |
