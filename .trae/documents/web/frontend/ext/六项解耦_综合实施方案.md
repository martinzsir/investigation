## 阶段 0：运行时地基

### R1 · RuntimeContext + ReadOnlyStore（py 路径红线补齐）

**问题**：`core/functions.py:519` `FUNCTION_IMPLS[spec.impl_ref](self.store, merged)` 只传 store 和 params，py 函数拿不到 pack/access/policy/health；且 store 可写（`store.execute` 可执行 DDL），py 路径无 `_assert_readonly`。

**改动**：
| 文件 | 动作 |
|---|---|
| `core/runtime_context.py`（新建） | `RuntimeContext` dataclass + `ReadOnlyStore` 代理 |
| `core/functions.py` | `invoke()` 构造 ctx 并传入；`_call_py()` 用 `inspect.signature` 兼容旧签名 |
| `core/functions.py` | `_assert_readonly` 复用（已存在，SQL 路径用的） |

**设计要点**：
- `ReadOnlyStore.__getattr__` 屏蔽 `execute`/`conn`；`query()` 内部调 `_assert_readonly(sql, "py-function")`
- `RuntimeContext.table(obj_name)` → `"obj_{name}"`，未声明对象抛 `ValueError`
- `RuntimeContext.check(table)` 显式权限校验（复用 `policy.check_object`/`check_link`）
- 签名兼容：`inspect.signature(fn)` 参数数 ≥3 走新签名 `fn(store, params, ctx)`，否则旧签名

**验证用例**（新增 `tests/test_runtime_context.py`，注册组 `rtcontext`）：
| 编号 | 用例 | 预期 |
|---|---|---|
| RT-TC-01 | py 函数内 `store.execute(...)` | `AttributeError` |
| RT-TC-02 | py 函数执行 `DROP TABLE` | `_assert_readonly` 抛错 |
| RT-TC-03 | py 函数访问未声明表（`ctx.table("nonexist")`） | `ValueError` |
| RT-TC-04 | py 函数返回缺 `basis` | 输出契约校验告警（`health.record`） |
| RT-TC-06 | `ctx.table("call")` | 返回 `"obj_call"` |
| RT-TC-09 | 旧签名函数（2 参数） | 仍可正常调用 |
| RT-TC-10 | 现有 6 条规则跑通 | 行为完全一致 |

**单独验证命令**：

### R2 · load_pack 缓存

**问题**：`core/ontology_loader.py:70` `load_pack()` 每次调用重新解析全部 JSON；`FunctionExecutor._specs()` 在 `invoke()` 开头即调，一次 BUILD 跑 6 条规则至少 6 次解析，`_jian_entries` 内部还再调一次。

**改动**：
| 文件 | 动作 |
|---|---|
| `core/ontology_loader.py` | 加 `_PACK_CACHE: dict[tuple[str, str], OntologyPack]`，key 为 `(pack, base_dir)` + 文件指纹（mtime 或 sha1） |
| `core/ontology_loader.py` | 暴露 `invalidate_pack_cache(pack=None)` 供测试/声明改动后清理 |

**设计要点**：
- 用 `(pack, base_dir, fingerprint)` 作 key；fingerprint 取 `ontology/<pack>/*.json` 的 mtime 最大值（或 sha1，取轻量的 mtime）
- 指纹变化自动 miss 重算，不依赖手动 invalidate
- 测试环境可显式 `invalidate_pack_cache()` 隔离

**验证用例**（并入 `rtcontext` 组）：
| 编号 | 用例 | 预期 |
|---|---|---|
| RT-TC-05 | 一次 BUILD 内多次 `invoke` | `load_pack` 只解析 1 次（用 `unittest.mock.patch` 计数） |
| RT-TC-05b | 修改声明文件后再次 `load_pack` | 重新解析（指纹变化） |

**单独验证**：`run_tests.py --only rtcontext`

### R3 · FunctionSpec.requires 声明 + loader 校验（元数据驱动 P1）

**问题**：py 函数硬编码表名绕过了 `spec.inputs` 权限校验（如 `tipoff_cross_reference` 声明 `inputs=[obj_tipoff]`，实际还查 `obj_org`/`lnk_owns`/`lnk_involved_in`）。`FunctionSpec` 无 `requires` 字段，装载期无法校验 py 函数的真实依赖。

**改动**：
| 文件 | 动作 |
|---|---|
| `core/ontology.py` | `FunctionSpec` 增加 `requires: dict`（`objects`/`links`/`props`） |
| `core/ontology_loader.py` `_load_functions` | 解析 `requires` 段，校验引用的对象/链接/属性已声明，未声明硬失败 |
| `ontology/default/functions.json` | 为 7 个 py 函数补 `requires` 声明 |

**`requires` schema**：
```jsonc
"requires": {
  "objects": ["call", "tipoff", "org"],
  "links":   ["owns", "involved_in"],
  "props":   {"call": ["caller_raw", "callee_raw"]}
}
```

**装载期校验**：
- `objects`/`links` 必须已声明
- `props` 的属性必须存在于对应对象
- 未声明即硬失败（沿用 fail-closed 立场）

**验证用例**（新增 `tests/test_function_requires.py`，注册组 `fnrequires`）：
| 编号 | 用例 | 预期 |
|---|---|---|
| META-TC-01 | `requires.objects` 引用未声明对象 | 硬失败 |
| META-TC-02 | `requires.props` 引用未声明属性 | 硬失败 |
| META-TC-03 | 合法 `requires` | 装载通过，`FunctionSpec.requires` 非空 |
| META-TC-04 | 7 个 py 函数均声明 `requires` | 全通过 |

**单独验证**：`run_tests.py --only fnrequires`

### R7 · scoring.json 声明化（计分机制 权重外置）

**问题**：`core/lineage.py:182` `_JIAN_WEIGHT` 和 `prioritize_clues` 的 0.4/0.35/0.25 权重全硬编码，不可审计。

**改动**：
| 文件 | 动作 |

| `core/lineage.py` | `prioritize_clues` 改为读 `scoring.json` + `jians.json` 的间类权重 |

**scoring.json schema**：
```jsonc
{
  "schema_version": 1,
  "dimensions": [
    { "name": "confidence", "weight": 0.4, "source": "assumption_confidence" },
    { "name": "jian_coverage", "weight": 0.35, "source": "jian_weight_sum", "normalize": 5.0 },
    { "name": "data_strength", "weight": 0.25, "source": "source_rows_count", "normalize": 10.0, "cap": 1.0 }
  ],
  "assumption_confidence": { "H1": 0.9, "H4": 0.7, "_default": 0.7 },
  "_constraint": "各 dimension weight 之和必须为 1.0"
}
```

**装载期校验**：
- `dimensions[].weight` 之和 = 1.0（±1e-6），否则硬失败
- `assumption_confidence` 必须有 `_default`
- 间类权重从 `jians.json` 读取（不重复声明）

**红线**：计分不得反向影响交叉等级——`scoring.json` 装载时断言任何计分项都不得声明为级别的输入。

## 实施完后的预期结果

### 红线与护栏
1. **py 路径只读闭环**：py 函数无法执行 `store.execute`/DDL，与 SQL 路径共享 `_assert_readonly`——64% 的计算能力从"无护栏逃生舱"变为"只读可审计"。
2. **权限无洞**：py 函数访问的所有表必须在 `requires` 声明，装载期校验；未声明表访问被拦截。
3. **计分不反向影响定性**：装载期断言计分维度不得作为等级输入；等级只由独立源数决定。
4. **受控终态红线保留**：`requires_role: human` 的状态 AI/机器会话无权置位，从硬编码变为声明驱动，红线不消失。

### 元数据驱动
5. **py 函数表名零硬编码**：4 个函数全部用 `ctx.table()`/`ctx.link()` 从声明派生，换包不崩。
6. **五间声明化**：3 处硬编码（顺序不一致）统一由 `jians.json` 驱动；新增间类不改 Python。
7. **状态机声明化**：`ClueStatus`/`_TRANSITIONS` 从 `states.json` 读取；新增状态不改 Python。
8. **计分权重外置**：0.4/0.35/0.25 与间类权重全部声明化，可审计、可改不改代码。

### 能力补全
9. **派生属性暴露**：`derived_properties.json` 声明式注册，查询时派生，带版本锚点可追溯；AC5 禁令守门。
10. **计分可解释**：`score_basis` 逐项展示 raw/weight/contrib，92 分说清怎么来的。
11. **源相关性表达**：`source_independence` 解决"同源转载被当成两个独立源"的系统性高估。
12. **性能**：`load_pack` 一次 BUILD 只解析一次。

### 回归与兼容
13. **73 组测试全绿**（含新增 5 组）。
14. **6 条规则行为完全一致**（golden 回归）。
15. **现有处置流程一致**（disposal 回归）。
16. **标识符未改动**：`clue_disposal_status`/`obj_clue` 等表名与 API 路径不变，无破坏性变更。

### 为后续方案铺路
17. RuntimeContext 成为五间/领域/元数据/派生/计分的共同地基，各方案不再各自绕道取 pack。
18. `requires` 声明让"隐式耦合变成显式契约"——本系统最擅长的设计哲学贯彻到 py 函数层。
