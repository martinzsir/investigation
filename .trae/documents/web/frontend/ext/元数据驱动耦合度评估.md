# 孙武侦查官 · 元数据驱动耦合度评估

> 版本 **v1.0** ｜ 日期 2026-09-10
> 核查范围：`ontology_v2` 全仓，重点 `core/` SQL 分布（176 处）+ 声明文件 + 函数注册表
> 核心结论：**分层评估——五层做到了元数据驱动，`py` 函数层是唯一实质性泄漏**
> 判断：**架构意图清晰且在大部分层执行彻底，泄漏只发生在"py 函数"这一个逃生舱里**

---

## 0. 一句话结论

> **符合，但只符合到 `py` 函数这一层为止。**
> 物化、绑定、清洗、值类型、SQL 函数——五层都做到了元数据驱动；
> 唯独 `py` 函数把 `obj_*/lnk_*` 表名硬编码进了代码。
>
> 这不是"架构错了"，而是**"逃生舱没有划边界"**——
> 修复成本很低，且 P1 那条恰好是本系统最擅长的做法：**把隐式约束变成显式契约**。

---

## 1. 分层评估总表

| 层 | 耦合度 | 关键证据 |
|---|---|---|
| **物化层**（obj_/lnk_ 建表） | ✅ 完全驱动 | `CREATE TABLE lnk_{name} AS {build_sql}`，表名由声明派生 |
| **绑定层**（数据从哪来） | ✅ 完全驱动 | `bindings.json` 2 对象 + 9 链接的 SQL 全是声明数据 |
| **清洗层** | ✅ 完全驱动 | `clean_ops.register_op` 注册表 + `compile_sql_expr` 编译 |
| **值类型层** | ✅ 完全驱动 | 9 种 `TYPE_SQL` 集中在 `ontology.py:52-60` |
| **SQL 函数层** | ✅ 完全驱动 | 4 个函数 `impl: sql`，SQL 写在 `functions.json` |
| **🔴 py 函数层** | ❌ **硬编码** | `obj_call`/`obj_tipoff`/`lnk_owns`/`obj_org` 写死在代码 |
| **⚠️ 部分模块源表** | 🟡 默认值硬编码 | `graph.py:97 "银行流水"`、`entity.py:401 "工商信息"` |

## 2. 五层达标：证据

### 2.1 物化层 ✅

```python
# core/ontology.py:425-426
conn.execute(f"DROP TABLE IF EXISTS lnk_{ltype.name}")
conn.execute(f"CREATE TABLE lnk_{ltype.name} AS {lb.build_sql}")
```

表名由 `ltype.name`（声明）派生，SQL 来自 `link_bindings.build_sql`（声明）。**改声明即改物化，零代码改动。**

### 2.2 绑定层 ✅

`bindings.json` 中 SQL 完全是声明数据：

| 类型 | 数量 | 示例 |
|---|---|---|
| object_bindings 含 SQL | 2 | `person`（178字符，6 路 UNION）、`account`（57字符） |
| link_bindings 含 SQL | 9 | `transfers`(278)、`calls_to`(196)、`co_located`(430) … |

**这正是"换数据源只改 bindings.json"承诺的技术基础。**

### 2.3 清洗层 ✅

```python
# core/clean_ops.py
def register_op(name, *, impl, layer="clean"): ...
def compile_sql_expr(ops, col_expr) -> str: ...
def clean_layer_names() -> set[str]:
    """clean 层可用 op 名（CLEAN_RULE_NAMES 的数据源）"""
```

**op 名由注册表实时派生**（注释明写"AC-1 动态集合"），不是硬编码白名单。声明合法集合与实现严格对齐。

### 2.4 值类型层 ✅

```python
# core/ontology.py:52-60（REQ-041 扩展）
"timestamp":     "TIMESTAMP",
"duration_days": "INTEGER",
"enum":          ...,
"json":          ...,
```

9 种值类型集中定义，`objects.json` 只声明类型名。**新增值类型改一处。**

### 2.5 SQL 函数层 ✅

`functions.json` 中 `impl: sql` 的 4 个函数：

```
quarter_end_integer_deposits   integer_transfer_aggregates
co_located_pairs               time_window_collision
```

SQL 写在声明里，含 `render_sql_template` 参数化渲染 + `sql_placeholders` 占位符校验 + `_assert_readonly` 只读断言。**换本体包无需改代码。**

### 2.6 装载期校验的强度

`core/ontology_loader.py` 有约 **145 个 fail-closed 校验点**，全部 `raise ValueError`：

```
dimensions.json dimensions[i] 缺 name 字段
dimensions.json 维度名重复
enum_space.json space.{k} 必须是非空数组
clean_rules.json mode='{mode}' 非法
...
```

**"未声明即硬失败"的一贯立场，在装载层执行得非常彻底。**

## 3. 🔴 唯一实质泄漏：py 函数硬编码表名

### 3.1 函数分布

| impl | 数量 | 耦合情况 |
|---|---|---|
| `sql` | 4 | ✅ SQL 在声明里 |
| `py` | **7** | ❌ 部分函数表名硬编码 |

### 3.2 硬编码完整清单

| 函数 | 硬编码表名 | 位置 |
|---|---|---|
| `call_frequency_spike` | `obj_call` | `functions.py:151, 195` |
| `call_pair_coverage` | `obj_call` | `functions.py:195` |
| `tipoff_cross_reference` | `obj_tipoff`、`lnk_owns`、`lnk_involved_in`、`obj_org` | `functions.py:305, 311, 314, 317` |
| `org_interest_links` | `obj_org` | `functions.py:420` |
| **`jian_cross_level`** | ✅ **参数化**（`{table}` 来自 `_jian_entries(pack)`） | `functions.py:278` |
| `overpass_two_hop` | 委托 `graph.overpass_two_hop_sql` | 见 §3.4 |
| `location_colocated` | 委托 `core/geo.py` | — |

**典型代码**：
```python
# functions.py:151
"SELECT caller_raw, callee_raw, COUNT(*) AS c FROM obj_call "
# functions.py:305
rows = store.query("SELECT * FROM obj_tipoff")
# functions.py:311
"SELECT DISTINCT owner_raw AS raw_name FROM lnk_owns"
```

### 3.3 后果

**换一个本体包（对象改名、结构不同），这些函数直接 `BinderException`。**

而 `sql` 函数不会——它们的 SQL 在 `functions.json` 里，改声明即可。

> ⚠️ 这直接违背"换数据源只改 bindings.json"的承诺：
> 你确实只改了 `bindings.json`，但 **py 函数照样崩**。

### 3.4 两个反例（说明问题可解）

**`jian_cross_level` 是正面样板** ✅：

```python
entries = _jian_entries(params.get("pack", "default"))
for table, jian, src in entries:
    n = store.query(f"SELECT COUNT(*) AS n FROM {table}")[0]["n"]
```

表名来自 `_jian_entries(pack)`——遍历**声明**得到 `obj_*`/`lnk_*` 表名，再动态拼 SQL。**完全参数化，换包不崩。**

**`overpass_two_hop` 有降级容错**：检查 `tbl.startswith("obj_")`/`"lnk_"`，函数消费的语义表缺失时降级（REQ-020 golden / REQ-G-003）。

**结论**：同一个文件里，`jian_cross_level` 做对了，其余四个没做对——**不是能力问题，是规范没贯彻**。

## 4. 次要问题：源表默认值硬编码

| 位置 | 代码 | 性质 |
|---|---|---|
| `core/graph.py:97` | `flow_table: str = "银行流水"` | 函数默认参数 |
| `core/graph.py:204` | `flow_table: str = "银行流水"` | 同上 |
| `core/entity.py:401` | `table: str = "工商信息"` | 同上 |

**缓解因素**：都是**函数默认参数**，调用方可覆盖，不是死编码。且注释显示有降级容错（"不同数据源的工商信息表列名各异，缺失列自动跳过并降级"）。

**严重度**：🟡 中。不阻断换包，但默认值泄漏了业务语义。

## 5. 但要公允地说：架构意图是清晰的

三处设计表明**这不是疏忽，是刻意分层**：

| 设计 | 说明 |
|---|---|
| **`FUNCTION_IMPLS` 注册表** | `functions.py:135`。py 实现注册进去，声明用 `impl_ref` 挂钩，**装载期校验存在**。声明与实现分离 |
| **`clean_ops` op 注册表** | 清洗规则名由注册表实时派生，非硬编码白名单 |
| **145 个 loader 校验点** | 未声明即硬失败，fail-closed |

**准确评价**：

> **架构的"元数据驱动意图"非常明确，且在五层执行彻底；
> 泄漏只发生在 `py` 函数这一个逃生舱里。**

## 6. 要不要修？我的判断

**不要全修，但要划边界。**

py 函数的存在是合理的——中位数计算、降级判定、覆盖率诊断这类逻辑，SQL 表达不了。
**问题不是"有 py 函数"，而是"py 函数里的表名硬编码"。**

### 6.1 改造优先级

| 优先级 | 措施 | 说明 |
|---|---|---|
| **P0** | **表名参数化** | 把 `obj_call`/`obj_tipoff` 等改成从 spec 传入的 `table` 参数（或仿 `_jian_entries` 从声明派生） |
| **P1** | **声明加 `requires` 段** | py 函数声明依赖哪些对象/链接，loader 装载期校验存在 |
| **P2** | 源表默认值外置 | `graph.py`/`entity.py` 的中文表默认值移到声明文件 |
| ❌ 不做 | py 函数全改写 SQL | 不现实也没必要 |

### 6.2 P0 方案：表名参数化

**参照 `jian_cross_level` 的写法**：

```python
# 现在
"SELECT caller_raw, callee_raw, COUNT(*) AS c FROM obj_call"

# 改为（伪码）
_callable = _table_of(spec, "call")     # 从声明派生 obj_<name>
f"SELECT caller_raw, callee_raw, COUNT(*) AS c FROM {_callable}"
```

**或**在 `functions.json` 增加：
```jsonc
{
  "name": "call_frequency_spike",
  "impl": "py",
  "impl_ref": "call_frequency_spike",
  "requires_objects": ["call"],       // ★ 新增
  "params": {...}
}
```
执行器按 `requires_objects` 注入表名。

### 6.3 P1 方案：依赖声明与装载期校验 ★ 推荐

在 `functions.json` 为 py 函数增加：

```jsonc
"requires": {
  "objects": ["call", "tipoff", "org"],
  "links":   ["owns", "involved_in"],
  "props":   {"call": ["caller_raw", "callee_raw"]}
}
```

`ontology_loader` 装载期校验：
- 引用的对象/链接是否已声明
- 引用的属性是否存在
- **未声明即硬失败**（沿用既有 fail-closed 立场）

### 6.4 为什么 P1 比 P0 更重要

> **P0 消除耦合，P1 让耦合可被校验。**
>
> 而 P1 恰好是本系统最擅长的做法——
> 从"未声明即硬失败"到"红线不读配置"，这个项目的设计哲学就是
> **把隐式约束变成显式契约**。

即便未来还有 py 函数需要硬编码（总有例外），只要它在 `requires` 里声明了依赖，
loader 就能在装载期发现"这个包缺了 obj_call"——**耦合被显式化，风险就可控了**。

## 8. 一句话总结

> **本系统的元数据驱动做得比多数同类项目更彻底——五层全驱动、145 个硬校验、注册表动态派生。**
