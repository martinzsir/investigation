# 孙武侦查官 · 跨场景落地评估框架

> 版本 **v1.0** ｜ 日期 2026-09-10
> 依据：`ontology_v2` 代码核查（13 个声明文件、11 个函数、物化与规则链路）
> 用途：**拿到一个新场景，先算"纯配置覆盖率"，再决定是"配置"还是"开发"**

---

## 0. 修正你的说法：不是两层，是三层半

### 0.1 运行时处理链

```
数据 → 物化(obj_*/lnk_*) → 规则匹配 → 函数计算 → 交叉定级 → 状态流转
        ①本体层              ②领域层      ③能力层      ②领域层    ②领域层
```

| 层 | 声明文件 | 职责 |
|---|---|---|
| **① 本体层**（结构） | `objects` / `links` / `bindings` / `views` / `policies` / `data_elements` | 有什么、从哪来、谁能看 |
| **② 领域层**（语义） | `dimensions` / `jians`(待建) / `states`(待建) / `thresholds` / `rules` | 怎么判、怎么分级 |
| **③ 能力层**（计算） | `functions.json` + **Python 实现** | 怎么算 |

**第三层是你原说法里漏掉的，而它最容易卡住落地。**

### 0.2 还有半层：数据本身

即便三层都配好，没有数据就是空壳——这正是「案件尚未产出线索（先运行 BUILD/RESCAN）」的成因。

**完整落地条件是四条**：

```
① 本体模型（structure）   ← 配置
② 领域模型（semantics）   ← 配置
③ 能力函数（computation） ← 配置 或 代码  ⚠️
④ 数据接入（bindings + 实际文件）← 配置 + 上传
```

## 1. 🔴 关键缺口：11 个函数里 7 个是 Python

| impl | 数量 | 能否纯配置新增 |
|---|---|---|
| `sql` | 4 | ✅ 写进 `functions.json` 即可 |
| `py` | **7** | ❌ **必须写 Python + 注册进 `FUNCTION_IMPLS`** |

### 1.1 四个 SQL 函数（可纯配置）

```
quarter_end_integer_deposits   integer_transfer_aggregates
co_located_pairs               time_window_collision
```

**表达力示例**（`quarter_end_integer_deposits`）：
```sql
SELECT date_trunc('quarter', CAST(date AS DATE)) AS q,
       COUNT(*) AS cnt, SUM(CAST(amount AS DOUBLE)) AS amt
FROM obj_transaction
WHERE CAST(amount AS BIGINT) % {{round_unit}} = 0
  AND to_raw = {{cash_summary_tokens}}
  AND ({{quarter_end_window_days}} = 0 OR ...)
```

支持 `{{param}}` 模板渲染 + `sql_placeholders` 占位符校验 + `_assert_readonly` 只读断言。
**聚合、取模、日期窗口、JOIN 都能表达。**

### 1.2 七个 py 函数（必须写代码）

```
call_frequency_spike    org_interest_links    overpass_two_hop
jian_cross_level        location_colocated    tipoff_cross_reference
call_pair_coverage
```

**为什么它们不能用 SQL 表达？** 看 `call_frequency_spike`：

```python
top, rest = pairs[0], pairs[1:]
if rest:
    median = statistics.median(r["c"] for r in rest)     # 中位数
    hit = median > 0 and top["c"] >= 2 * median
else:
    hit = top["c"] >= threshold                          # ★ 降级判据
```

三个 SQL 难以表达的点：

| 难点 | 说明 |
|---|---|
| **动态基线** | 中位数基于"其余数据"计算，不是固定阈值 |
| **降级逻辑** | 数据不足时切换到绝对阈值，并给出 `degrade_reason` |
| **中文诊断文本** | `basis` 是自然语言，供人读 |

**注意**：全库无 `MEDIAN`/`quantile`/`percentile` 使用——说明这类统计确实走了 Python。

### 1.3 更糟的是：py 函数还硬编码了表名

`obj_call` / `obj_tipoff` / `obj_org` / `lnk_owns` 等共 **11 处**硬编码（详见《元数据驱动耦合度评估》）。

**后果**：换一个本体包，即使逻辑通用，py 函数照样崩。

## 2. 核心指标：纯配置覆盖率

```
纯配置覆盖率 = 能用声明完成的规则数 ÷ 总规则数
```

| 覆盖率 | 判断 | 投入 |
|---|---|---|
| **≥ 80%** | 确实是"建两层就能落地" | 配置为主 |
| 50% ~ 80% | 需要少量函数开发 | 配置 + 少量代码 |
| **< 50%** | 本质是开发项目 | 需专业投入 |

**新场景评估时先算这个数**——它决定了这次落地是"配置"还是"开发"。

## 3. 四问判断法

拿到新场景，按顺序问：

| # | 问题 | 若"是" | 若"否" |
|---|---|---|---|
| 1 | 实体和关系能用对象/链接表达吗？ | 本体层可配 | 需改 `ontology.py` |
| 2 | **判据能用 SQL 表达吗？** | `functions.json` 可配 | **需写 py 函数** ⚠️ |
| 3 | 分级能用现有交叉模型吗？ | 领域层可配 | 需扩展模型 |
| 4 | 状态机能映射吗？ | `states.json` 可配 | 需扩展状态机 |

**第 2 问是分水岭**。

## 4. 三个候选场景实际测算

### 4.1 SOC 网络安全

| 规则示例 | 能否 SQL | 说明 |
|---|---|---|
| 单 IP 短时间大量失败登录 | ✅ | 聚合 + 时间窗口 |
| 异常外联（非工作时间/非常用端口） | ✅ | 条件过滤 |
| 同源告警去重 | ✅ | GROUP BY |
| ATT&CK 技术链匹配 | ✅ | JOIN 技术表 |
| **基线偏离（相对历史均值）** | ❌ | 动态基线 → py |
| **告警关联图（多跳）** | ❌ | 图遍历 → py |
| 独立源交叉（IDS+EDR+情报） | ⚠️ | `jian_cross_level` 可复用，但需适配 |

**估算：约 60–70%** —— 中等，需 2–3 个 py 函数

### 4.2 药物警戒 PV

| 规则示例 | 能否 SQL | 说明 |
|---|---|---|
| 个例报告数超阈值 | ✅ | 聚合 |
| 特定不良反应聚集 | ✅ | 分组计数 |
| **ROR/PRR 信号检测** | ❌ | 需统计计算（比例失衡） → py |
| **多源信号合并（报告+文献+病历）** | ⚠️ | 可复用交叉模型 |
| 时间窗（用药→反应） | ✅ | `time_window_collision` 可复用 |

**估算：约 50–60%** —— 信号检测是核心，必须写 py

### 4.3 保险反欺诈

| 规则示例 | 能否 SQL | 说明 |
|---|---|---|
| 短期内多次出险 | ✅ | 聚合 |
| 维修厂与事故关联 | ✅ | JOIN |
| 金额整数/顶格投保 | ✅ | 取模（现成函数可复用） |
| **关系网络团伙识别** | ❌ | 图算法 → py |
| **文本理赔描述相似度** | ❌ | 需语义检索（`search.py` 已实现但未接线） |

**估算：约 55–65%**

| 场景 | 覆盖率 | 说明 |
|---|---|---|

## 5. 提高覆盖率的三个措施

| 优先级 | 措施 | 收益 | 成本 |
|---|---|---|---|
| **P0** | **py 函数表名参数化** | 现有 7 个 py 函数可跨包复用 | 1–2 人日 |
| **P1** | **沉淀通用 py 函数库** | 基线偏离、图遍历、覆盖率等做成通用函数 | 每个 1–2 人日 |
| **P1** | **SQL 能力增强** | DuckDB 支持 `median()`/`quantile_cont()`，可把部分 py 改写为 SQL | 视情况 |

### 5.1 P0 为什么最划算

现在 py 函数硬编码 `obj_call`，换个包就崩。参数化后：

```python
# 现在
"SELECT ... FROM obj_call"
# 改为
f"SELECT ... FROM {table}"    # table 来自声明
```

**7 个函数立刻变成可复用资产**，不需要为每个新场景重写。

### 5.2 P1 的思路：识别"跨场景通用模式"

从现有 7 个 py 函数抽象出通用能力：

| 现有函数 | 抽象为通用能力 | 可用于 |
|---|---|---|
| `call_frequency_spike` | **动态基线偏离检测** | SOC 流量异常、PV 信号 |
| `overpass_two_hop` | **图多跳遍历** | 团伙识别、关联网络 |
| `call_pair_coverage` | **覆盖率诊断** | 数据完备性检查 |
| `jian_cross_level` | **独立源交叉定级** | 所有场景 |

**这四项抽象出来，新场景覆盖率可提升 20–30 个百分点。**

解耦后有新风险：**配置本身变成了代码**。

- 需要版本管理
- 需要测试
- 需要校验

**你的 loader 已有 145 个 fail-closed 校验点**——这个数字本身就说明配置的复杂度不低。

> **别把"配置化"等同于"零成本"。**

> **而写配置同样需要领域专家。**

## 7. 修正后的准确说法

### 7.1 你的原说法

> "解耦后形成本体模型 + 领域模型两个层次，领域模型可按业务扩展；
> 落地时先建立对应场景的本体模型和领域模型，就能实现业务。"

### 7.2 准确表述

> **解耦后形成分层可配架构**（本体层 / 领域层 / 能力层 / 数据接入）。
> 落地新场景时，先建本体模型 + 领域模型，
> **再用「纯配置覆盖率」评估还差多少代码**。
>
> 若判据均可用 SQL 表达 → 纯配置即可落地；
> 若涉及动态基线、图算法、降级判定 → 需开发 py 函数。

### 7.3 准确性评分

| 你的判断 | 评估 |
|---|---|
| 会形成本体+领域两个层次 | ✅ 对，但**实际是三层半** |
| 领域模型可按业务扩展 | ✅ **对**（解耦后确实可配） |
| 先建本体+领域模型就能实现业务 | ⚠️ **部分成立**——取决于规则能否用 SQL 表达 |

## 8. 落地检查清单

新场景启动时，逐项打勾：

| # | 检查项 | 通过标准 |
|---|---|---|
| 1 | 实体/关系能否用 objects/links 表达 | 能画出对象图与链接图 |
| 2 | 数据源是否可接入 | 有结构化文件或可映射的表 |
| 3 | **判据能否 SQL 表达** | 列出所有规则，标注 SQL/py |
| 4 | 纯配置覆盖率 ≥ 目标值 | 计算并确认可接受 |
| 5 | 交叉模型是否适用 | 独立源定义清晰 |
| 6 | 状态机是否可映射 | 能列出状态与迁移 |
| 7 | 受控终态是否定义 | `requires_role: human` 已声明 |
| 8 | 权限与遮蔽策略 | `policies.json` 已配置 |

## 9. 一句话总结

> **解耦后确实是分层架构，领域模型也确实可扩展——但不止两层，且"建两层就能落地"只在判据可用 SQL 表达时成立。**
>
> 真正的分水岭是**「纯配置覆盖率」**：
> 用 `functions.json` 能表达的判据越多，落地越接近"配置"；
> 需要动态基线、图算法、降级判定的，仍要写代码。
>
> **所以先做 P0（py 函数表名参数化），把现有 7 个函数变成可复用资产——
> 这是提升所有未来场景覆盖率的最便宜一步。**
