## 1. 盘点方法

对每个模块检查四类引用：

| 检查项 | 含义 |
|---|---|
| `core/` 内部引用 | 是否已被其他 core 模块间接使用 |
| `server/` 引用 | 是否有 HTTP 端点 |
| `scripts/mcp_server.py` | 是否暴露给 Agent |
| `frontend/` | 是否有 UI |

**分类标准**：
- 🔴 **完全未接线**：内部 0、server 0、mcp 0（仅测试/CLI 引用）
- 🟡 **CLI 可用、Web 不可用**：只在 `run_all.py` 等脚本流程中调用
- 🟢 **已接线**：server 或 mcp 有出口

## 4. 三个最高价值模块详解

### 4.1 🥇 `sampling` —— 按假设抽样预演

**为什么值五颗星**：它直接回答审计师最核心的职业判断问题——**"这个方向值不值得投入全量核查"**。

```
对每个假设 → 抽样（默认 1%，至少 200 行）→ 算命中率 → 三档判定
  ≥5%   方向明确 → 建议投入全量扫描
  1~5%  方向存疑 → 建议扩大到 5% 再验证
  <1%   方向否定 → 建议调整假设，暂缓全量算力
```

已考虑小样本假阴性（`min_sample_rows=200` 防"29行×1%=0行"退化）。

**接线前必做一件事**：加 `REPEATABLE(seed)`。

当前用 `USING SAMPLE reservoir(n ROWS)` **无 seed** → 抽样不可复现 → **审计场景不可用**。
DuckDB 原生支持 `REPEATABLE(seed)`，改动约 5 行。

### 4.2 🥈 `case_library` —— 案例片段沉淀与检索

**为什么值五颗星**：这是**审计经验复用**的核心机制，而且设计得非常克制。

沉淀需过**四道质量门**：
1. **终态门** —— 线索必须已固证/已排除，待查/查证中**不得入库**
2. （其余门见源码 `settle_fragment`）

沉淀字段含 `confidence`、`legal_basis`、`redaction_hash`、`audit_event_id`——**脱敏哈希 + 审计链锚点**，设计考虑周全。

检索支持 `rule_id` / `outcome` / `keyword`（LIKE）。

> **这是"从一个个案到一类案"的桥梁**，也是审计机构最需要的能力（历史案例库）。

### 4.3 🥉 `rule_dsl` —— 复合规则 DSL

**为什么值五颗星**：现在的规则都是**单条独立**的，而 DSL 支持组合：

```
AND(
  R1,
  WITHIN(R6, 30d),
  NOT(R3)
)
```

含义举例：「资金异常 **且** 30天内中标-资金碰撞 **且** 无公示期通话」——这类**复合判据**正是降低误报的关键。

还带：
- `explain()` —— 可读的自然语言解释（审计友好！）
- `MAX_DEPTH=5` —— 防表达式炸弹
- 校验 `rule_ref` 必须指向已存在规则

**测试已通过**（`tests/test_rule_dsl.py`，`run_tests.py` REQ-026）。

> ⚠️ 注意：DSL 是**已实现并有测试**的，但 `rules.json` 里现用 6 条规则都没走 DSL——说明它是为未来准备的，接线即可启用。

## 5. 为什么会出现这个模式

从代码结构看，**不是疏忽，是刻意的架构选择**：

```
core/   ← 内核，纯逻辑，无 Web 依赖，可测试、可 CLI 调用
server/ ← 薄适配层，对外开放
```

设计者把能力都写在 `core/`，`server/` 只做暴露。**问题是暴露进度跟不上实现进度**——内核建得快，接口没跟上。

**这其实是好事**：说明 `core/` 的质量高（有测试、无框架耦合），接线风险低。
