> 版本 v1.0 ｜ 日期 2026-09-11

## 3. 🔴 硬 bug 证据：`clue_id` 筛选失效

### 3.1 实测（真实 `AuditChain` 建库）

```python
# 写入 2 条事件（复刻 registry.py:189 真实参数）
chain.append(operator="正兵", before={"status":"待查"}, after={"status":"查证中","note":"初查"}, ...)
chain.append(operator="主办", before={"status":"已固证"}, after={"status":"已立案","legal_basis":"X案号"}, ...)

timeline(clue_id="C001")    # 真线索 ID  → 命中 0 条   ❌ 应为有结果
timeline(clue_id="张卫国")  # 主体名     → 命中 2 条   ❌ 误命中，会串线
```

### 3.2 为什么是 bug 而不是取舍

**`clue_id` 是对外暴露的 API 参数**，不是内部死代码：

```
GET /cases/{id}/audit?clue_id=xxx
# server/app/routers/audit.py:95  Query 参数
```

任何调用方都能传。**"功能不 work" + "产生错误结果"两条全占。**

### 3.3 误命中比查不到更危险

`timeline()` 的匹配逻辑（`core/audit.py:471`）：

```python
haystack = f"{before_json}{after_json}{source_row_ids_json}"
if clue_id not in haystack: continue
```

`source_row_ids` 里含**主体名**（如"张卫国"）。同一主体名出现在多条线索里 → **审计轨迹跨线索串线**。

> 在需要举证的场合，这是实质伤害。

## 4. 四层根因

| 层 | 位置 | 事实 |
|---|---|---|
| 1 | `audit_chain` 表 | **无 `clue_id` 列**，只有 `case_id` |
| 2 | `AuditChain.append()` | 签名**无 `clue_id` 参数** |
| 3 | `set_status` / `set_filed` | `after={"status":..., "note":...}` **不含 clue_id** |
| 4 | `timeline(clue_id=...)` | 只能做 JSON 字符串包含匹配 |

代码注释自陈：「审计链无独立线索列，按 before/after/source_row_ids 的 JSON 包含匹配」。

**审计链是"案件级"的**——一条串起整个案件的哈希链，事件间靠 `source_row_ids` 弱关联，**无实体主键**。

### 4.1 为什么这样设计（不是疏漏）

- **REQ-G-007**：强调"不改表结构"——版本锚点 unknown 时打在 `after_state` 内标注，而非加列。
  此约束后被泛化：连 `clue_id` 也走"塞进 JSON"路子——**但没人真的往里塞**。
- **REQ-G-025**（历史）：此前 `audit_chain` 漏传，导致处置动作只写内存、持久链零记录。
  那次修好了"传不传"，**但"传了什么"没管**，`clue_id` 至今缺失。

## 6. 修复方案

### 6.1 P0：修 `clue_id` 筛选（0.5 人日）

**好消息：不用改表结构。**

已验证 `_compute_signature` 输入**包含 before 和 after** —— 往里加 `clue_id`，签名自然覆盖，链校验照样通过（重算时用同样的 before/after）。

**改动 1**：`core/registry.py` 两处写入

```python
# set_status（:189）
before={"status": self.status, "clue_id": self.clue_id},
after={"status": target, "note": note, "clue_id": self.clue_id},

# set_filed（:215）
before={"status": self.status, "clue_id": self.clue_id},
after={"status": ClueStatus.FILED, "legal_basis": legal_basis, "clue_id": self.clue_id},
```

`self.clue_id` 本就存在（`set_status` 是 `LineageClue` 方法），**取值零成本**。

**改动 2**：`core/audit.py:477` 改精确匹配（同时检查 before/after，旧事件回落包含匹配）

```python
before_d = json.loads(before_json) if before_json else {}
after_d = json.loads(after_json) if after_json else {}
if clue_id is not None:
    cid_in_event = before_d.get("clue_id") or after_d.get("clue_id")
    if cid_in_event is None:
        # 旧事件无 clue_id 字段 → 回落包含匹配（保留可追溯性）
        haystack = f"{before_json or ''}{after_json or ''}{source_row_ids_json or ''}"
        if clue_id not in haystack:
            continue
    elif cid_in_event != clue_id:
        continue
```

### 6.2 存量数据兼容（必须决定）

存量审计事件**无 `clue_id` 字段**，改精确匹配后全部查不到。

| 方案 | 做法 | 评价 |
|---|---|---|
| **保守（建议）** | 新事件精确匹配，旧事件回落包含匹配（双模式） | 保留可追溯性，但保留误命中风险 |
| 干净 | 一次性迁移，从 `source_row_ids` 反查线索回填 | 可能反查不全，丢失可追溯性 |

> **建议前者**：不为了干净而丢失可追溯性。

### 6.3 P1：前端无需额外工作（P0 修复后线索级查询自动生效）

前端已有完整能力：
- `AuditChainView.vue`：审计链页面，支持案件级/线索级维度切换，线索级带 `clue_id` 查询参数
- `ClueDetailView.vue:207`：详情页「查看本线索审计链 →」链接，带 `?clue_id=` 直达

**P0 修复后，上述入口的线索级查询自动恢复正常**，无需前端改动。

可选增强（非必须）：在详情页内嵌 `audit_log` 摘要（`operator` / `from_status → to_status` / `timestamp` / `note`），减少跳转。

### 6.4 P0-3：哈希链线索级（audit_log 关联 audit_chain event_id）

**问题**：`set_status`/`set_filed` 双写 `audit_log`（内存，随产物落盘）与
`audit_chain`（持久哈希链），但两者**无关联**——`audit_log` 的
`StatusAuditEntry` 不含 `event_id`，无法关联到受哈希保护的链上事件。
举证时 `audit_log` 可被篡改而不被检测。

**方案**：给 `StatusAuditEntry` 加 `event_id` 字段，`set_status`/`set_filed`
把 `audit_chain.append()` 返回的 `event_id` 写入 `audit_log` 对应记录。

**效果**：
- `audit_log` 每条记录带 `event_id`，可在 `audit_chain` 中定位受哈希保护的事件
- 线索详情页展示的处置轨迹可逐 event_id 校验签名完整性
- 复用 P0-1 成果（`clue_id` 已写入 before/after，签名已覆盖）

**改动**：
1. `core/registry.py` `StatusAuditEntry` 加 `event_id: str = ""`
2. `set_status`/`set_filed`：先调 `audit_chain.append()` 拿 `event_id`，
   再构造 `StatusAuditEntry(event_id=event_id)` 写入 `audit_log`

## 9. 一句话总结

> **严格说：不是"没有线索审计链"，而是「一个真 bug + 一个下游表现 + 一个哈希保护缺口」三件事混在一起。**
>
> - 🔴 **真 bug**：`clue_id` 是对外 API 参数却不 work——真 ID 查 0 条，主体名误命中 2 条（**会串线**）
> - ⚠️ **下游表现**：前端已有审计链页面（`AuditChainView`）和线索级入口（详情页「查看本线索审计链」），但 `timeline(clue_id=)` bug 导致线索级查询失效——真 ID 查 0 条、主体名误命中；**P0 修复后自动恢复，无需前端改动**
> - ✅ **P0-3 哈希链线索级**：`audit_log` 关联 `audit_chain` 的 `event_id`，让线索内存审计记录可定位到受哈希保护的链上事件，举证时可逐 event_id 校验签名完整性
>
> **P0-1/P0-2 修对外能力（0.5 人日），P0-3 补哈希保护（0.2 人日）**——三者合计约 0.7 人日。
