## 第一部分：通用五态规范

26 张原型绘制的均为**正常态**。以下四态由前端统一实现，逐页套用。

| 状态 | 规则 |
|---|---|
| **正常** | 如原型所示 |
| **空态** | 必须有引导动作，不能只写"暂无数据"。须区分「真的没有」与「被权限挡住」 |
| **加载** | 骨架屏，不留白。**禁止** spinner + 空白 |
| **异常** | 展示降级原因 + 可操作出口。须区分「数据缺失」与「匹配失败」 |
| **无权限** | 明确显示"无访问权限"，**不得**用空态代替 |

**无权限态不得伪装成空态**——两者视觉相同会让用户推断出"这个资源存在但我不该看"，构成隐蔽信息泄漏。

### 1.1 数据治理类页面的三态特殊规则

页面 18–22 涉及数据装载与丢弃，除通用五态外另有三个特殊态：

| 特殊态 | 适用页 | 规则 |
|---|---|---|
| **部分成功** | 19 / 21 / 22 | 装载完成但有行被隔离时，**必须同时展示成功与失败两部分**，不得只报成功数 |
| **零隔离** | 22 | 空态须明确写"本次装载无数据被丢弃"，而非留空——留空无法区分"没跑"和"没丢" |
| **阻断** | 19 / 20 | 1:1 校验失败时整个装载被阻止，须定位到具体冲突列并给出可操作出路 |

### 1.2 平台通用类页面的三态特殊规则（v1.3 新增）

页面 23a–25 涉及认证、案件上下文与系统配置，另有三个特殊态：

| 特殊态 | 适用页 | 规则 |
|---|---|---|
| **未认证** | 23a | 认证完成前**不得请求或渲染任何案件数据**，页面不存在案件占位、骨架或空态 |
| **筛选无结果** | 23b / 24 | 须与「真的没有」区分开，并提供"清除筛选"出口 |
| **只读** | 25 | 非管理员角色进入系统设置时，配置项为只读态并说明原因，不得静默禁用 |

**关于「登录与案件选择」拆分为两页的说明**（v1.3 决策）：

原方案将认证与案件列表放在同一页面，存在一处绕不过去的安全矛盾——**认证尚未完成时，案件列表已渲染**，案件名、编号、状态、版本号在登录前即暴露。这直接违反 REQ-W-030（多租户隔离）与通用五态中"无权限态不得伪装成空态"的约束。

拆分后另有两点收益：

1. 案件门户可升级为**案件上下文枢纽**——不只是登录后的过渡页，系统内切换案件时也回到此处（通过顶部案件选择器「全部案件」入口），一次投入两处复用。
2. 案件门户可承载**跨案件待办汇总**（有多少线索待处置、多少实体待裁决、多少超期项），让用户在进入具体案件前就知道全局工作量。合并页无处安放此区块。

## 第三部分：八条红线的界面级验证

> **v1.2 说明**：红线六与红线七均作用于页面 21，但处置逻辑方向相反。实现前须先按文末「判别流程」判定检查项归属，不得一律按"只告警"处理。

以下场景可直接转为 E2E 用例。红线若不在界面上可验证，迭代两轮即会破功。

### 红线一：未声明 = 拒绝（页面 13）

```gherkin
场景：权限矩阵中存在未声明的格子
  当 前端渲染「人员 × 主办」权限矩阵
  那么 未声明的格子应显示斜纹底 + 锁图标 + "拒绝"
  并且 不得显示为空白、横线或"未配置"

验证方法（E2E）：
  cy.get('[data-testid="perm-cell-person-host"]')
    .should('have.class', 'state-denied')
    .and('not.have.text', '')
```

视觉上留白 = 语义上放行，这是 fail-closed 最容易死掉的地方。

### 红线二：异常线索不参与交叉等级（页面 11）

```gherkin
场景：候补池中有 N 条待转正条目
  当 进入庙算工作台
  那么 交叉等级数值不得因候补池条目数量而变化
  并且 候补池区域应有虚线边框与其他区域视觉隔离
  并且 候补条目不得携带等级贡献标记

验证方法（快照对比）：
  清空候补池 → 记录交叉等级 A
  注入 10 条候补 → 断言交叉等级仍为 A
```

若此条失守，"缺的东西越多等级越高"，数据最不完整的报告看起来最像可立案。

### 红线三：审计链空链不得显示"正常"（页面 06）

```gherkin
场景：案件尚未产生任何处置动作
  当 打开审计链页
  那么 完整性校验状态条应显示为"空链"警示态（非绿色）
  并且 记录总数显示 0
  并且 不得显示"校验通过"

验证方法：
  新建空案件 → 断言状态条 class 为 warn 而非 ok
```

来自实测发现的真实缺陷（`expected=0, actual=0` 被判为 `chain_ok=true`）。

### 红线四：映射 1:1 约束不得被绕过（页面 20 · v1.1 新增）

```gherkin
场景：两个属性映射到同一源列
  当 在 ETL 管道配置器中保存映射
  那么 应显示红色阻断横幅，装载被阻止
  并且 冲突表格须列出冲突双方（属性 A / 属性 B / 源列名）
  并且 须给出可操作出路（上游 source_sql 拆分 或 声明 composite）
  并且 不得提供"忽略并继续"的绕过选项

场景：用户尝试声明列拆分规则
  当 在规则列表中选择 split 类操作
  那么 该操作应不可选，或选择后硬失败
  并且 提示须说明"映射层保持 1:1 以保证可追溯"

验证方法（E2E）：
  cy.get('[data-testid="mapping-conflict-banner"]')
    .should('have.class', 'state-blocking')
  cy.get('[data-testid="rule-op-split"]').should('be.disabled')
```

**这条红线的业务理由**：一个属性必须能明确回答"它来自哪一列"。若允许一列拆多列，映射变成 1:N，审计链无法说清属性来源，REQ-D-002 的"依据什么数据"就断了。

**注意它不是限制能力，而是约束位置**：复合列的拆分被推到上游 `source_sql`，声明层保持 1:1，可追溯性完整。

### 红线五：任何数据丢弃必须可见（页面 22 · v1.1 新增）

```gherkin
场景：装载过程中有行被清洗剔除或 CAST 隔离
  当 装载任务完成
  那么 结果页须同时展示"成功装载 N 行"与"丢弃 M 行"
  并且 丢弃部分须可下钻到具体行（原始值 / 失败原因 / 规则名 / 脱敏样本）
  并且 四类丢弃（清洗剔除 / CAST 隔离 / 空值拒绝 / 合规违规）须分别计数
  并且 丢弃数须进入健康度小节

场景：本次装载无任何丢弃
  当 打开隔离区与留痕页
  那么 须显示"本次装载无数据被丢弃"
  并且 不得显示为空白或"暂无数据"

验证方法（E2E）：
  构造 100 行含 40 行脏数据 → 断言同时显示 60 与 40
  构造 100 行全干净数据 → 断言显示"无数据被丢弃"而非空态
```

**这条红线的业务理由**：现有 `exclude_org_tokens` 把行静默丢弃——用户看到的 `obj_person` 里没有"A建材"，以为数据本来就这样。这与 R5 静默失效、审计链空链假通过是**同一病根**：系统做了事但不告诉你。

**三种静默形态都要消灭**：静默过滤（`exclude_org_tokens`）、静默 NULL（`TRY_CAST`）、静默通过（星号卡号假装清洗成功）。

### 红线六：启发式检查只告警、不阻断（页面 21 · v1.2 拆分）

```gherkin
场景：敏感字段扫描发现未声明遮蔽的身份证列
  当 执行数据质量检查
  那么 应显示告警条目并给出"建议补充遮蔽声明"
  并且 装载流程不得被中断
  并且 告警须标记为"建议"而非"错误"
  并且 须标注判定依据（列名启发式 / 值模式识别）

场景：单位一致性检查怀疑金额单位混用
  当 执行检查
  那么 应显示告警并说明"金额突增 10000 倍，疑为元/万元混用"
  并且 装载流程不得被中断
  并且 须标注此判断为启发式，需人工确认

验证方法（E2E）：
  构造含未声明敏感列的表 → 断言装载成功且有告警
  断言告警条目的 severity 为 suggest 而非 error
  断言装载结果中该列数据完整保留
```

**适用范围（启发式检查）**：

| 检查项 | 依据 | 误报可能 |
|---|---|---|
| 敏感字段扫描（D-018） | 列名启发式 + 值模式识别 | **有** |
| 单位与口径一致性（D-020） | 分布异常推断 | **有** |

**业务理由**：启发式判断依赖模式匹配，误报不可避免。若做成阻断，正常数据会因误报装不进来——这比漏检的代价更大。所以这类检查的职责是**让人注意到**，不是自动判定。

### 红线七：确定性检查必须按策略处置、不得静默通过（页面 21 · v1.2 新增）

```gherkin
场景：值域合规检查发现身份证校验位错误
  当 执行检查
  那么 违规行须被检出并记录
  并且 处置方式取决于 on_cast_error 配置（fail / null / quarantine）
  并且 不得静默通过
  并且 违规数进入健康度，可下钻到具体行

场景：金额为负、日期为未来时间
  当 执行检查
  那么 按声明策略处置
  并且 即使策略为 null，NULL 数量也须被统计（不得无声无息）

验证方法（E2E）：
  构造校验位错误的身份证 → 断言违规被记录且按策略处置
  构造策略为 null 的违规场景 → 断言 NULL 计数可见
  断言无任何违规行在"无记录"情况下进入目标表
```

**适用范围（确定性检查）**：

| 检查项 | 依据 | 误报可能 |
|---|---|---|
| 值域与格式合规（D-016） | 数据元的格式/值域/校验位定义 | 无 |
| 业务键重复（D-015） | 声明的 key columns | 无 |
| 空值策略（D-014） | 声明的 null_policy | 无 |

**业务理由**：确定性检查基于数据元标准的显式定义，不存在误报空间。因此违规行**必须有明确去处**——隔离、拒绝或显式计入 NULL。

**为什么必须从红线六拆出**：两类检查的处置逻辑**方向相反**。合在一条里最大的风险是前端实现为"所有质量检查都只告警"，于是身份证校验位全错也能一路通过装载，而这个问题在统计上完全看不出来（空值率低、基数正常），到下游才会以"实体对齐全线出错"的形式爆发，且极难回溯。

### 红线八：认证失败不泄露账号存在性（页面 23a · v1.3 新增）

```gherkin
场景：用户输入不存在的账号
  当 提交认证
  那么 提示应为"账号或密码错误"
  并且 不得提示"用户不存在"或"账号未注册"

场景：用户输入存在但密码错误
  当 提交认证
  那么 提示应完全相同（"账号或密码错误"）
  并且 两次提示的文案、样式、响应耗时均须一致

场景：连续多次认证失败
  当 失败次数超过阈值（如 5 次）
  那么 应触发锁定或验证码
  并且 锁定提示同样不得透露账号是否存在

验证方法（E2E）：
  分别提交不存在的账号与错误密码 → 断言提示文案完全一致
  断言两者 HTTP 状态码相同
  断言响应耗时差异在可接受范围内（防止时序侧信道）
```

**业务理由**：若区分"用户不存在"与"密码错误"，攻击者可据此**枚举有效账号**。在政法系统里，账号列表本身就是敏感信息——知道谁在用这个系统，往往比破解某个账号更有价值。

**这条红线与红线一的共同点**：它们防的都是"通过界面反馈的差异推断出本不该知道的信息"。红线一防的是权限推断，红线八防的是账号推断，属于同一类信息泄漏的两个面。

```
   ↓
发现异常

是否基于数据元标准的显式定义？
   ├─ 是 → 红线七：按 on_cast_error / null_policy 处置，记录，不静默

        └─ 否 → 按常规流程处置并留痕
```
